# v0.1.0 milestones — from the six-axis publish audit (2026-07-25)

6軸 publish 監査(言語本体 / stdlib・packages / tsukasa / tool chain / コード品質 / CI・docs)の全指摘を、
v0.1.0 tag までのマイルストーンに編成したもの。方針は「blocking 以外もなるべく対応する」。

編成原理:

1. breaking になり得る変更(新 compile error、stdlib/package の署名変更)は tag より前に置く。
2. リポジトリ依存順: compiler → packages → registry → web/examples → tag。
3. 同一レーンの作業はまとめて 1 コミット圏に。

規模感: S = 1時間以内 / M = 半日 / L = 1日超。★ = 監査 Blocker 由来。

## 決定事項(owner, 2026-07-25)

1. **wire callable authz**: v0.1.0 は「MCP は信頼済みサーバのみ」を仕様として明記し、admin store `set` の
   raw callable decode を遮断するのみ。フル authz(fiber/ACS)は v0.2。
2. **slack `ask`**: 実装する。
3. **imagegen**: `generate_image` を追加する(同 endpoint に image 抜き)。
4. **approval gate**: package 拡張はせず「一般機構 + 具体は data」の公式 idiom として文書化。
5. **outbox 順序列**: 0000 migration へ squash 同乗(ユーザー 0 人の squash 方針は確定済み)。
6. **`use` binder 型供給(PAIN 6)**: v0.2 送りを撤回し v0.1.0 スコープへ昇格(M1-8)。
   owner の仮説: `use` の右辺は handler / 関数名 / 関数適用のいずれかなので、それぞれから
   binder 型を extract できるはず(関数適用なら continuation の引数型)。大機構なしで実装可能と見込む。
7. **calendar update/delete + gmail スレッド返信**: tsukasa 機能拡張として別トラック(Track T)で整備。
8. **region watch レース**: mailbox flush 猶予ではなく「watch 設置まで escalation をバッファする」
   意味論へ。watch は大幅に遅延して設置され得るため。現行機構の調査 → 設計から着手(M2-6)。
9. **`local` request マーカーは撤去**(2026-07-25 夕): 言語表面を 1 語増やす価値なし — root へ何が
   escalate するかは check の escalation report が既に見せている。K3027 は欠番。
10. **root-served exclusive は v0.1.0(tag 前)へ前倒し**(同): api-reactor が task closure を
   delegation として起動し project 単位の durable FIFO で直列化して answer。直列単位 = project 1 本を
   root domain の恒久意味論とする(per-workspace は将来の additive API)。task の panic は自 run のみ fail。

11. **chat surface の再設計 + approval package の削除**(2026-07-26、owner 指示「真に必要な機構を考え直し、
   破壊的変更を入れてよいので最大限抽象化・composable に」): chat surface を **message 平面(watch/send)+
   interaction 平面の `ask` 1 本**に縮約。`ask` は「controls(データ直和: button|select|form)を提示し、
   最初に完了した interaction を answer(直和: clicked|chose|submitted)として返す」一般機構で、
   **承認 / 自由記述 / draft 編集 / 複数選択が同じ ask + 異なるデータ**になる。**approval package は削除**
   (実体は fork+ask+branch の複合。ask が一般化されれば残りは app が元から持つべき分岐と、app 内に既にある
   spawn idiom = `launch_watch` 形。app 内なら ceiling が具体なので PAIN 19-22 の effect-generic + 二重
   `lacks` + two-tail の難所が丸ごと消え、tsukasa は二重 nursery/watch から 1 本に戻る)。
   時間・撤回・耐久性は合成に落ちる(`time.with_deadline` / `region.cancel_by_id` / unserved request の
   root escalation park)。discord=0.2.0 / slack=0.3.0、twin は**厳密同形 + divergence 文書化**方針
   (package 間依存ゼロなので共有語彙 package は作れない。provider 差し替えは「app が request を宣言し
   root の adapter 1 つが serve」= infer_step 型 layering)。**interaction 平面は message 流と別経路なので、
   自律ターン中の質問がソースとレースしない** — これが 2 平面に分けた設計上の要。

## v0.1.x / v0.2 送り(スコープ外の確定)

- 言語: module-private(PAIN 3 の本命解)/ handler 幾何 diagnostics 実装 / 匿名 agent 式 /
  文位置 if の else 省略 / positional 互換 / park×deadline clock / conditional scope discharge /
  closed row / code-frame 診断
- runtime: wire authz フル実装(fiber/ACS)/ 複数プロセス lease / DbPersistence 実 DB テスト /
  route 統合テストのデフォルト化(root-served exclusive は決定 10 で v0.1.0 へ前倒し済み)
- **runtime / scope 所有権の残 2 件**(2026-07-26 の 3 修正で family の fork 側は閉じた。以下は意図的に据え置き):
  - **park された環境が、まだ生きている raiser の書き込み中に解放され得る**: provide の drop は自分の所有分を
    reclaim するが、escalation で届いた callback の環境は「生成元の instance がまだ走っている間」provide 所有に
    なり得る(tool が carry on しながら fiber が決める非同期 gate の形)。**region が tool より先に終わる場合のみ**
    露出するので、nursery が session 全体を生きる常在パターンでは踏まない。修正は fix 1 の liveness retain を
    `reclaimScopesOwnedBy` / `teardownInstance` にも広げることだが、**in-memory delete と durable な
    FK cascade(`scopes.owner_instance_id ON DELETE CASCADE`)が desync する**ため「durable な所有権とは何か」の
    決定が要る。10 行パッチではない。
  - **単一所有が根本制約**: この family の穴は全て「1 scope・1 owner・寿命の違う 2 消費者」の同型で、これまでの
    修正は全て「寿命の長い側を owner に選ぶ」で解いた。長い側が同定できる限り機能するが、2 消費者が互いを
    別方向に outlive する形になった時点でモデルに答えが無い。refcount か reachability ベースの reclaim が
    要る場所で、v0.2.0 の議題。
- stdlib/packages: regex・HTML→text primitive / 乱数・UUID / DST civil calendar /
  削除動詞の統一(breaking)/ tavily・imagegen の 401 区別 / port framing のバージョン付与 /
  `json.try_validate[T]`(total な validate — 永続 spec の読み戻しで恒常的に要る。PAIN 23)
- その他: Check.hs 分割 / `-Werror` / CONTRIBUTING・issue templates・dependabot / CHANGELOG 運用

   models に渡る tool 名なので `ai.view_file` に改名(ai 0.2.0、破壊的)。

   注入時刻も生 epoch のみで「あと N 日」をモデルに誤らせる。→ `created` 記録・完了ログ・
   civil 時刻併記・`update_task`。
3. **ワンショット reminder**。`cron_watch` の着地で定時繰り返しは埋まったが「30 分後に一度だけ」は

### 「実装しないのが正しい」と判断したもの(再提案されたら却下の根拠)

- **メッセージからの締切/予定の自動抽出 → 自動 add_task / 自動 create_event**。DESIGN §2 が
  gmail→calendar reflex として明文で否定した "is this meeting-shaped?" parser。能力は tool、判断はモデル。
- **朝 brief の残日数カウントダウンをコードで組み立てる**。日付データを渡せばモデルが計算する。
  `summary_note` の「件数 + 最寄り due」がコード側の上限。
- **全会話の自動アーカイブ + 全文検索**。会話の SoT は `ai.session_state`。第 2 コピーは drift し、
  私的文脈の恒久堆積は membrane 事故の燃料。
- **herald への read-only ビュー**(タスク件数など)。read-only でも membrane crossing。
  herald が知ってよいのは operator が gate を通した文言だけ。
- **desk status ダッシュボード**。soul 自身が "dashboards nobody reads" を嫌う。
  デスク横断の状態 registry は同期ロジックの温床。
- **gate のタイムアウト / 低リスク自動承認**。"nothing is freed by giving up on a question"(DESIGN §5)。
  gate に期限が無いのは仕様。
- **Notion ⇄ tasks の双方向同期**。SoT が 2 つになる。tasks は store、日記は Notion、片方向で読む。
- **tsukasa の MCP サーバ化**(`mcp.serve`)。gate を迂回する第 2 の inbound 境界を作り、membrane と正面衝突。
- **汎用 `http.post` / 汎用 store read-write を core の tool に**。「実世界への書き込みは gated named tool」
  という規律と、workspace 幾何そのものである membrane を壊す。
