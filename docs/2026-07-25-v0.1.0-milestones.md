# v0.1.0 milestones — from the six-axis publish audit (2026-07-25)

6軸 publish 監査(言語本体 / stdlib・packages / tsukasa / tool chain / コード品質 / CI・docs)の全指摘を、
v0.1.0 tag までのマイルストーンに編成したもの。方針は「blocking 以外もなるべく対応する」。

編成原理:

1. breaking になり得る変更(新 compile error、stdlib/package の署名変更)は tag より前に置く。
2. リポジトリ依存順: compiler → packages → registry → web/examples → tag。
3. 同一レーンの作業はまとめて 1 コミット圏に。

規模感: S = 1時間以内 / M = 半日 / L = 1日超。★ = 監査 Blocker 由来。

## 決定事項(owner, 2026-07-25)

1. **wire callable authz**: v0.1.0 は「MCP は信頼済みサーバのみ」を仕様として明記し、admin store `set` の
   raw callable decode を遮断するのみ。フル authz(fiber/ACS)は v0.2。
2. **slack `ask`**: 実装する。
3. **imagegen**: `generate_image` を追加する(同 endpoint に image 抜き)。
4. **approval gate**: package 拡張はせず「一般機構 + 具体は data」の公式 idiom として文書化。
5. **outbox 順序列**: 0000 migration へ squash 同乗(ユーザー 0 人の squash 方針は確定済み)。
6. **`use` binder 型供給(PAIN 6)**: v0.2 送りを撤回し v0.1.0 スコープへ昇格(M1-8)。
   owner の仮説: `use` の右辺は handler / 関数名 / 関数適用のいずれかなので、それぞれから
   binder 型を extract できるはず(関数適用なら continuation の引数型)。大機構なしで実装可能と見込む。
7. **calendar update/delete + gmail スレッド返信**: tsukasa 機能拡張として別トラック(Track T)で整備。
8. **region watch レース**: mailbox flush 猶予ではなく「watch 設置まで escalation をバッファする」
   意味論へ。watch は大幅に遅延して設置され得るため。現行機構の調査 → 設計から着手(M2-6)。
9. **`local` request マーカーは撤去**(2026-07-25 夕): 言語表面を 1 語増やす価値なし — root へ何が
   escalate するかは check の escalation report が既に見せている。K3027 は欠番。
10. **root-served exclusive は v0.1.0(tag 前)へ前倒し**(同): api-reactor が task closure を
   delegation として起動し project 単位の durable FIFO で直列化して answer。直列単位 = project 1 本を
   root domain の恒久意味論とする(per-workspace は将来の additive API)。task の panic は自 run のみ fail。

11. **chat surface の再設計 + approval package の削除**(2026-07-26、owner 指示「真に必要な機構を考え直し、
   破壊的変更を入れてよいので最大限抽象化・composable に」): chat surface を **message 平面(watch/send)+
   interaction 平面の `ask` 1 本**に縮約。`ask` は「controls(データ直和: button|select|form)を提示し、
   最初に完了した interaction を answer(直和: clicked|chose|submitted)として返す」一般機構で、
   **承認 / 自由記述 / draft 編集 / 複数選択が同じ ask + 異なるデータ**になる。**approval package は削除**
   (実体は fork+ask+branch の複合。ask が一般化されれば残りは app が元から持つべき分岐と、app 内に既にある
   spawn idiom = `launch_watch` 形。app 内なら ceiling が具体なので PAIN 19-22 の effect-generic + 二重
   `lacks` + two-tail の難所が丸ごと消え、tsukasa は二重 nursery/watch から 1 本に戻る)。
   時間・撤回・耐久性は合成に落ちる(`time.with_deadline` / `region.cancel_by_id` / unserved request の
   root escalation park)。discord=0.2.0 / slack=0.3.0、twin は**厳密同形 + divergence 文書化**方針
   (package 間依存ゼロなので共有語彙 package は作れない。provider 差し替えは「app が request を宣言し
   root の adapter 1 つが serve」= infer_step 型 layering)。**interaction 平面は message 流と別経路なので、
   自律ターン中の質問がソースとレースしない** — これが 2 平面に分けた設計上の要。

### port pin のずれ: 二段の訂正を経た確定版

**確定した事実**: パッケージの `@katari-lang/port` pin は **typecheck だけを支配し、出荷される port
ではない**。`typescript/bundle/src/index.ts` の `portSingletonPlugin` が全 import を
**バンドラ自身**のディレクトリに解決する(port はプロセス全体の状態を持つので単一でなければならない)。
実測: rc8 が自分の node_modules に入った vendored discord を実バンドラで束ねると出力は
`$katari_ref`(1)/`$ref`(0)。test 専用の `portResolveDir` seam で強制的に rc8 に向けると
`$ref`(1)/`$katari_ref`(0)。差の原因はこのプラグイン 1 つ。

経緯(判断の記録として残す):

1. 「rc8→rc10 は刻印のみで実害ゼロ」と記録 → **誤り**。`git log --oneline` で `65f5fd91`
   (region nursery / **blob hoist** / AI integration)を刻印と読み飛ばした。実際 port rc7/rc8 は
   file handle を `$ref` で出し、rc9/rc10 は `$katari_ref`。runtime は後者しか読まず、
   `$ref` の後方互換はコードベースに存在しない。
2. そこで「discord/slack が rc8 pin なので Discord 添付が届かない実バグ」と escalate → **これも誤り**。
   pin は配備に届かないため。**見落としていた決定的な反証**: rc8 が本当に配備されていれば
   `$katari_closure` が復号されず `deliver_to.call(...)` が最初のメッセージで失敗して watch ごと倒れる。
   つまり bot はファイルだけ壊れるのではなく全く動かない。**bot が動いている事実だけで仮説は否定できた。**
   実測でも rc8 の inbound は `file.bytes is not a function` を handler の try/catch が拾って
   typed `api_error` に変え、`try_send` が設計通りそれを飲むので**添付つき投稿が無言で消える**形になる
   (panic ではない)。

**実在する(より狭い)欠陥**: pin が typecheck 専用なので、両 sidecar は
**永久に話さない ABI に対して型検査されていた** = CI の false-green。discord/slack/e2b を rc10 に
揃えて解消(sidecar のコード変更は不要 — rc8→rc10 の typings 差 74 行のうち signature 形は 2 行だけで、
どちらの sidecar も `FileHandle` のフィールドに触らない)。

**残る本物の stale pin は 1 つだけ**: `katari-verify` の `@katari-lang/bundle@0.1.0-rc8`。
バンドラこそが配備される port を決める側なので、ここだけは pin が実際に出荷に影響する(M6-6 で 0.1.0 へ)。
`imagegen` は `package.json` を持たない(sidecar 無し)ので pin は存在しない。
discord-bot-example は port が `link:` + bundle rc10 で問題なし。

**教訓 2 つ**: (a) 版差の判定を `git log --oneline` の見た目で行わず公開 artifact を直接比較する。
(b) それ以前に「その仮説が真なら他に何が壊れているはずか」を先に問う — 今回は

### ★ 実運用で起きた停止から出た言語レベルの発見(PAIN 30)

2026-07-26 夜、tsukasa が digest 公開のたびに再起動するループに入った。表面の原因は modal の
field ラベルが 45 文字上限を超えたこと(67 文字)。だが**本当の発見は封じ込めが効かなかった理由**。

tsukasa の `spawn_gate` ブリッジは fork した gate を `classify_crash` で分類する throw ハンドラで
包んでおり、`discord.api_error` は `restartable` に分類される。**つまり封じ込め機構は存在し正しく
書かれていた。** それでも run が死んだのは、`ask_operator` が request で、`discord.ask` を実際に
呼ぶのは **root のハンドラ本体**だから。ハンドラ本体は perform 地点ではなく**インストール地点**で
走るので、throw は gate fiber のガードより**上**のフレームで起き、ガードは永久にそれを見られない。

法則: **fiber の throw ガードは、自分より上のハンドラで起きた失敗を封じ込められない。
fiber が perform する request はすべて、それに答えるハンドラと同じ大きさの穴をガードに開ける。**
しかも今回、その穴は gate にとって最も失敗しやすい呼び出し(人間に問うこと)にちょうど開いていた。

**ただしこの法則は新発見ではない(owner 指摘)。** 既に合意済みの
**outcome-as-value 規約**(request を処理する handler の throw は、なるべく直和 result 形で返す)
そのものであり、しかも**同じ構造的理由がコードベースに明記されていた**。e2b package(12 日前):

> BOTH failure surfaces hand the failure back as a VALUE, never a throw: …
> **the provider's deep handler cannot throw back into the tool that performed `session`,
> so the tool must be able to READ the failure** …
> This is the same outcome-as-value move the `ai` package's `infer_step` seam makes,
> and for the same reason.

`store.get` の `found | absent`、`json` の reader 群、`memory`/`persona` の TOTAL な読み、
e2b の `session_ready | session_unavailable` はすべてこの規約の実例。
**`ask_operator` が従っていなかっただけ**であり、PAIN 30 は規約を引用せず停止事故から再導出していた。

したがって正しい総括は 2 つ:

1. **なぜ破られたか**: 規約が package のコメントと個々の実例の中にしか無く、
   **プロジェクトの規則として書かれていなかった**。だから新しい site(`ask_operator`)が従わなかった。
   規則として明文化することが修正の一部。
2. **型システムは間違っていない**。`ask_operator` の row は `-> discord.answer` で、
   呼び出し側のフレームでは実際に何も throw されないので正しい。語られていないのは
   **escalation がハンドラ側の失敗によって「返ってこない」ことがある**という別の軸。
   → v0.1.x の wish は「新しい診断」ではなく**規約の lint**: ハンドラ本体の row が回復可能な throw を
   持つのに、その request の応答型がそれを表現していないとき警告する。これがあれば
   今回の停止はコンパイルエラーだった。PAIN 18(provider の類例)、24 と連結。

**分類の線(この機会に確定させる)**: 直和に入れるか、なお loudly 止めるかは
**自己回復しうるか**で決める。回復しうる(一時的なネットワーク、上流 5xx)→ 値。
回復しない(設定・欠陥。`discord.auth_error`、`env.missing_secret`、`ai.duplicate_tool`)→ 止める。
黙って mute になった常駐 bot は、自己回復しない欠陥に対しては loud な crash より悪い。

対処(app 側): `ask_operator` を total にした — 問えなかった質問は throw ではなく
`unasked(reason)` として返り、`read_form`/`read_click` が `refused` に畳む(fail-closed。
人間が見ていないのに「人間が断った」と core に伝えないこと、人間の行動を偽造しないことが要件)。
実ランタイム上で 4 走行で証明済みで、効いているのは**対照実験** — 同じガード・同じ失敗で
フレームだけ変えると結果が逆になる。

**同種の穴がもう 1 つ**: `launch_watch` は fork するだけでガードが無く、`watch_gmail` の row は
`prelude.throw[gmail.api_error | ...]`。つまり**背景 watch での一時的な Gmail 500 が 1 回で
常駐システム全体を再起動させる**。対処中(封じ込め + spec は残す + core に「止まった」と伝える。
spec を消すと一時障害で監視が永久に失われ、黙って死ぬと監視しているつもりで止まる)。

### ★ 最大の v0.1.x 入力: Katari アプリは durable time をテストできない(PAIN 29)

tsukasa 側で reminder を実装した agent の結論。**Katari アプリの作者には、制御可能な clock も
restart hook も無い**ので、「停止中に時刻が過ぎた sleep は復帰時に即発火する」という性質を
**アプリのテストとして書けない**。今回それを確認できたのは runtime の内部
(`ManualClock` で `ProjectActor`/`TimeReactor` を直接駆動)に降りたからで、これは
アプリ作者には無い手段。

これは軽い不便ではない。**Katari が売っているものが durable execution そのもの**なので、
その性質をアプリ側で検証できないなら、作者は自分のプログラムの最重要な振る舞いを信じる根拠を

### 直和を tool 引数にすると schema から doc が消える(compiler 側の実測、v0.1.x 入力)

digest の kind をどう表現するか探るために IR を実測した結果(PAIN 27 に詳細):

- **直和引数は動く**が、生成 schema は `anyOf` の各枝が
  `{"$katari_constructor": {"const": "tsukasa.probe.alpha"}, "$katari_value": {…}}` になり、
  モデルに予約 wire ラッパー + 完全修飾コンストラクタ名を書かせる。さらに
  **インライン展開でフィールドの `@"…"` doc が全部落ちる**(コンストラクタ単体の schema では
  `"description"` が残るのに、union の中では素の `{"type":"string"}` になる)。
- **リテラル和**(透過シノニム経由)は本物の enum(`anyOf` の `const` 列)になり兄弟の doc も残る。
  範囲外の値は境界の `const` 検証で弾かれ `call_error` がモデルに返る。
- リテラル和の代償 2 つ: 4 つ全部を並べた `match` が**網羅と判定されない**(`K3001 expected: never`)、
  リテラルは引数では型を保つが**戻り値では `string` に広がる**ので `kind_of(entry) -> kind` が書けない。

**doc が落ちるのは schema 生成の欠陥**で、直せば直和引数が本来の Katari らしい選択になる。
つまりこれは「どちらの書き方が正しいか」を今後変える種類の修正。v0.1.0 では触らない。

### v0.1.x 入力(このウェーブが洗い出した stdlib / runtime 級の穴)

- ~~`time.zone_offset(zone, at)`~~ → **v0.1.0 に landed(6d94cfdd)**。`zone_offset(epoch_milliseconds, zone)
  -> integer | null`、prim 1 本 + prelude 宣言のみ(`crypto.sha256` と同じ配線、compiler table 不要)。
  設計判断 2 点: (1) 不正 zone は **throw でなく `null`** — 不正な zone 名は「呼び出し側が再構成できない情報」を
  運ばないので `docs/2026-07-03-throw-error-model.md` の基準では throw に当たらず、かつ
  `to_rfc3339(offset_minutes = zone_offset(...))` が**型検査を通らない**ので、zone 名の打ち間違いが
  静かに UTC へ劣化することが構造的に起こらない。(2) `PST` のような略称も受理 — 拒否すると `cron` と
  受理集合が分岐するため。罠(`PST` は DST を含む zone 全体で 7 月は -420)は doc + test で固定。
  cron との受理集合一致は仮定せず実測で証明。DST は 2026 年の両遷移の前後 1 分 + Lord Howe の 30 分 +
  Kathmandu 345 + 1880 年東京 559。runtime 572 / compiler 800 green。
  **tsukasa の採用は runtime 公開後**(rc10 上には prim が無い)なので、当面は env の固定 offset。
- **memory の index 注入キャップ(v0.1.x 判断待ち)**: 現状 index は per-turn 全 summary 注入で無 cap。
  調査の結論は「**件数キャップは単純には入れてはいけない**」。理由が非自明なので記録する —
  **モデルは存在を知らないものを検索しない**ので、件数キャップは「高価だが完全な認識」を
  「安価で静かに不完全な認識」に変える。`memory.search` では救えない(search は会話に既に手がかりが
  ある時しか効かない)。もし入れるなら 3 点すべてが必要: `+N more` の明示マーカー、`list_memories` を
  無 cap の完全一覧として維持、そして**弁護できる順序** — 現在の key 順を切ると
  アルファベット順に切り捨てることになり無意味で、recency 順にするには index の行ごとに timestamp が
  必要(= 既存行に対して degrade する schema 変更)。これが真の blast radius。
  安全で安価な手は**行ごとの上限**(長すぎる summary を marker つきで切る)で、こちらは
  病的ケースだけを抑え、記憶を認識から消さないので v0.1.0 に入れた。
