AI エージェントのオーケストレーションを書くための言語 **Katari** を開発しています。コンパイラは Haskell、実行系は TypeScript で、現在 v0.1.6 です。

- サイト: https://katari-lang.dev
- リポジトリ: https://github.com/katari-lang/katari

この記事では、言語の仕組みから実際に動いている Discord エージェントの構成まで、現段階でできることを順に紹介します。

# モチベーション

AI エージェントを普通の言語で書くと、書きたいロジックの周りに毎回同じものを書くことになります。ツールの JSON スキーマ、ツール呼び出しループ、会話状態の保存、リトライ、並行制御、人間の承認待ち。どれもアプリケーションの本題ではないのに、コード量では本題を上回りがちです。

Katari はここを言語機構で消しに行きます。柱は 2 つで、**effect system** (能力を型で追跡し、実装を後から注入する) と **永続 runtime** (実行状態を毎ステップ永続化する常駐サーバー) です。この 2 つが揃うと「1 週間 sleep する」「人間の返事を待って止まる」「落ちたら続きから再開する」が、そのままコードとして書けるようになります。

# 言語の仕組み — プログラムは runtime にアップロードして動かす

Katari の実行モデルは「コンパイルしてバイナリを作る」ではなく「コンパイルして runtime にアップロードする」です。ソース (`.ktr`) はコンパイラが IR に落とし、常駐 runtime がそれを実行・管理します。アップロードのたびに immutable な snapshot が作られるので、ロールバックは古い snapshot に戻すだけです。

```sh
katari init my_agent && cd my_agent
katari check                 # 型検査 (effect の被覆検査を含む)
katari apply                 # コンパイル・バンドルして runtime に snapshot をデプロイ
katari run my_agent.main --detach
```

Katari の関数は `agent` と呼びます。次のプログラムは、毎週月曜 9:00 に処理を実行し続けるワークフローです。

```katari
@"Every Monday 09:00 JST, post the weekly digest."
agent main() -> never {
  use discord.provider(source = credentials.env(key = "DISCORD_TOKEN"))
  agent tick(time: number) {
    discord.try_send(channel = "123456789", text = build_digest())
  }
  time.watch(
    schedule = time.cron(expression = "0 9 * * 1", timezone = "Asia/Tokyo"),
    deliver_to = tick,
  )
}
```

`time.watch` の次回発火時刻は runtime 側に永続化されます。runtime を再起動してもスケジュールは維持され、停止中に過ぎた発火は復旧時に 1 回だけ実行されます。`time.sleep` で 1 週間止まるのも同じ仕組みです。プロセスの生存とワークフローの生存が切り離されているのが、この runtime の役割です。

細かい話ですが、時刻の取得 (`time.now()`) も runtime への呼び出しです。取得した値は観測した時点で永続化されるので、リトライや再起動時の replay で値が変わることはありません。

並列はデータの形で書きます。各要素が独立したスレッドで走ります。

```katari
let bodies = parallel for (let url in urls) { next web.fetch_page(url = url) }
```

# effect と handler — 「人間に聞く」が言語機構になる

能力は `request` として宣言し、実装は handler が与えます。

```katari
@"Approval before an irreversible action."
request approve(description: string) -> boolean

agent deploy_if_approved() -> string {
  if (approve(description = "deploy to production")) {
    run_deploy()
  } else {
    "cancelled"
  }
}
```

`approve` にどう答えるかは呼び出し側の文脈が決めます。Discord のボタンで operator に聞く handler を挟んでもいいし、テストではつねに true を返す handler を挟んでもいい。そして handler を挟まなかった場合が面白くて、request は実行の外側に浮上 (escalation) し、管理コンソールや `katari answer` から人間が回答するまでワークフローは停止して待ちます。「人間への問い合わせで止まって待つ」が言語機構と永続化の組で成立しているので、承認フローのために外部のワークフローエンジンを併設する必要がありません。

型システムは effect row を追跡します。ある agent がどの request を実行しうるかは `with approve` のように型に現れ、handler の被覆はコンパイル時に検査されます。書き味としては「パッケージの公開面では明示し、アプリ内部では推論に任せる」くらいの温度感です。

# 関数がそのまま AI のツールになる

`agent` は追加のアノテーションなしで AI のツールになります。docstring (`@"..."`) と型シグネチャからツールスキーマが導出されるので、スキーマ定義というものを別に書きません。引数にも docstring が付きます。

```katari
@"Tool: search the web and return the top results as a compact digest."
agent search(@"The search query." query: string) -> string {
  tavily.digest(query = query)
}

agent answer(question: string) -> string {
  ai.infer_with_tools(
    history = [types.turn(role = "user", text = question)],
    tools = [search, web.fetch_page, e2b.run_python],
    max_steps = 8,
  )
}
```

`tools` に渡しているのはただの agent 値です。自作の agent も、パッケージの agent (`web.fetch_page`) も、後述する MCP 由来の agent も、同じ型なので同じリストに混ざります。ドキュメントとスキーマの出どころが 1 箇所 (docstring と型) なので、実装とツール定義がずれるという事故が構造的に起きません。

`ai.infer_with_tools` はツール呼び出しループです。モデルが要求したツール呼び出しは並列に実行され、引数はスキーマで検証され、ツールの失敗はループを壊さずエラー結果としてモデルに返ります。モデルプロバイダは handler として注入します。

```katari
use anthropic.provider(model = "claude-sonnet-5", source = credentials.env(key = "CLAUDE_API_KEY"))
```

`gemini.provider` / `openai.provider` に差し替えても、ループとツールのコードは変わりません。プロバイダとループの接点は「1 ステップ推論する」という request 1 つだけで、ここも effect system です。

# MCP を型付き関数として読み込む

外部の MCP サーバーのツール群は、2 通りの方法でプログラムに接続できます。

静的に使うなら `katari mcp pull` で型付きバインディングを生成します。

```sh
katari mcp pull --url https://mcp.notion.com/mcp --out src/my_agent/notion.ktr
```

生成後は `notion.notion_create_pages(...)` のように、サーバーのツールを型付きの関数として直接呼べます。補完も効くし、引数を間違えればコンパイルエラーです。

動的に使うなら `use mcp.provide` です。接続先のツール一覧を実行時に取得し、agent 値の record として手に入れます。

```katari
let tools : mcp.toolbox[mcp.scope] = use mcp.provide[mcp.scope](
  url = "https://mcp.notion.com/mcp",
  auth = mcp.oauth(name = "notion"),
)
```

中身はふつうの agent 値なので、そのまま AI のツールリストに混ぜられます。`provide` は scoped で、取得したツールは `use` したブロックの中でしか使えません — ツールを呼ぶと `mcp.scope` という effect が上がり、ブロックを抜けるところで discharge される、という形で型システムが生存期間を強制しています。

逆方向もあります。`mcp.serve` は自分のプログラムの agent 群を MCP サーバーとして公開します。Katari で書いたワークフローを、外部の AI クライアントのツールにする方向です。

# 外界との接続 — Webhook と OAuth

インバウンドは `webhook.inbound` です。公開 URL をその場で発行し、届いた POST を callback の呼び出しに変換します。

```katari
@"The delivery handler: doubles the delivered value."
agent double(value: integer) -> integer {
  value * 2
}

agent main() -> string {
  webhook.inbound(callback = double, subscriber = register_with_external_service)
}
```

JSON ボディは callback のシグネチャで検証され、合わないものは境界で 400 として弾かれます。callback が不正な入力で走ることはありません。URL の寿命は subscriber の実行期間で、抜ければ自動で無効になります。

OAuth は runtime 管理です。`credentials.oauth(name = "google")` のように名前で参照し、トークンはプログラムに一切入りません。未認可のままその credential を使うと、実行は認可待ちで park し、管理コンソールからブラウザで認可を済ませると続きから再開します。これも escalation と同じ「止まって待つ」の応用です。API キー類も同様に `katari env set CLAUDE_API_KEY --secret` で runtime に置き、`credentials.env` で参照します。secret は `string of private` という型になり、ユーザー境界に流出する経路があるとコンパイルで落ちます。

# 実例: Discord 常駐エージェント

ここまでの部品を組むと、常駐型のマルチエージェントが書けます。僕が実際に運用している Discord ボット ([tsukasa](https://github.com/yukikurage/discord-bot-example)) の構成を簡略化したものがこれです。

```katari
// AI に渡すツール。ただの agent で、スキーマは docstring と型から導出される
@"Tool: post a message to the home channel."
agent post_discord(@"The message text." text: string) {
  let _outcome = discord.try_send(channel = env.get_or(key = "CHANNEL", fallback = ""), text = text)
  null
}

// watcher: チャンネルの新着メッセージを AI へのメールに変える
agent channel_source(self: string) -> never {
  discord.watch_messages(
    channel = env.get_or(key = "CHANNEL", fallback = ""),
    deliver_to = agent (value: discord.message) {
      let _posted = ai.mail(to = self, source = f"discord:${value.channel}", content = value.text, hop = 0, files = value.files)
      null
    },
  )
}

// watcher: 毎朝の cron も同じ形で「AI へのメール」になる
agent morning_source(self: string) -> never {
  time.watch(
    schedule = time.cron(expression = "30 7 * * *", timezone = "Asia/Tokyo"),
    deliver_to = agent (time: number) {
      let _posted = ai.mail(to = self, source = "cron:morning", content = "朝のブリーフ: 今日やることを整理して報告して。", hop = 0)
      null
    },
  )
}

// この AI のツール群が実行しうる request の和 (実物は使うパッケージのぶんもう少し長い)
type app_row = discord.credential | store.get | store.set | store.delete | store.list | io

agent main() -> never {
  use discord.provider(source = credentials.env(key = "DISCORD_TOKEN"))
  use anthropic.provider(model = "claude-sonnet-5", source = credentials.env(key = "CLAUDE_API_KEY"))
  use store.workspace(path = "assistant")
  // fiber の死は型付きイベントとしてここに届く。扱う handler がないとコンパイルが通らない
  use handler {
    request region.crashed(id: string, name: string, message: string) {
      let _notice = discord.try_send(channel = env.get_or(key = "CHANNEL", fallback = ""), text = f"(${name} died: ${message})")
      next null
    }
    request region.failed(id: string, name: string, error: unknown) {
      let _notice = discord.try_send(channel = env.get_or(key = "CHANNEL", fallback = ""), text = f"(${name} failed)")
      next null
    }
  }
  let root = use ai.route[app_row]()
  let _core = ai.spawn[app_row](
    name = "core",
    tools = [post_discord, web.fetch_page, memory.remember, memory.recall, memory.search],
    sources = [channel_source, morning_source],
    workspace = "core",
    max_steps = 16,
  )
  region.watch(nursery = root)
}
```

構成要素を順に見ます。

**ツールを渡す。** `tools` はただの agent 値の配列です。ここでは Discord への投稿、Web ページの取得、永続メモリの読み書きを渡しています。ツール集合がそのまま権限の境界になります — 渡していない能力は、モデルがどう頼まれても実行できません。

**AI を召喚する。** `ai.spawn` の 1 行が AI 1 体です。名前、ツール、情報源 (`sources`)、ストレージの区画 (`workspace`) を渡すと、自分の会話・自分のメールボックス・自分の作業領域を持った常駐 AI が route の中に fork されます。もう 1 体増やすのももう 1 行で、実運用の tsukasa では、私的な文脈を全部持つ `core` と、公開チャンネルに立つ `herald` (メモリもタスクも渡さない — ツール集合がプライバシー境界) の 2 体が固定で立っていて、さらに core が自分のツールから `ai.spawn` を呼んで使い捨ての worker AI を実行時に雇い、`ai.mail` で報告を受け取り、`ai.dismiss` で解雇します。

**watch の仕組み。** 常駐の背骨は `region` — 構造化並行性でいう nursery です。`sources` の各エントリは watcher として fork され、チャンネルの購読 (`discord.watch_messages`) も cron (`time.watch`) も「イベントを `ai.mail` で AI に届ける fiber」という同じ形になります。fiber から上がるイベントは 1 箇所 (`region.watch`) に集約され、fiber の crash も型付きイベントとして同じ場所に届きます。これを扱う handler がないプログラムはコンパイルが通らないので、「watcher がいつの間にか死んでいて、チャンネルがずっと無音だった」が型レベルで防がれます。

会話の状態は handler の状態変数として永続化されるので、runtime を再起動しても会話は途中から続きます。モデル API が落ちている間の着信は上限つきのバックログに保持され、復旧後にまとめて処理されます。

# ツールチェーン

言語本体の周りに、一通りの道具が揃っています。

- **CLI** — `katari init / check / apply / run / status / cancel / answer / env / mcp / ...`。npm から `npm install -g @katari-lang/cli` で入ります。
- **LSP + VSCode 拡張** — 診断、補完、hover。拡張は VS Marketplace と Open VSX に出しています。
- **Runtime Image** — runtime は Docker イメージとして配布していて (GHCR)、PostgreSQL と S3 互換ストレージを添えれば自前のサーバーに置けます。
- **Admin Console** — runtime に付属する Web コンソール。run の一覧と実行トレース (delegation ツリー)、escalation への回答 (inbox)、OAuth credential の認可、env と secret、snapshot の管理、store の中身までここで見えます。
- **Package manager** — 依存は registry からの snapshot 固定で解決します。`katari add PKG` で宣言し、`katari.lock` が正確な閉包を記録し、`check` / `build` / `apply` は lock だけを読みます。`ai` / `discord` / `slack` / `gmail` / `google_calendar` / `memory` (永続メモリ) / `e2b` (Python サンドボックス) / `tavily` (検索) などを公開しています。TypeScript の FFI サイドカーを持つパッケージも、`katari apply` が依存ごとバンドルします。

# Docs for AI

Katari はどのモデルの学習データよりも新しいので、AI アシスタントに「Katari を書いて」と頼むと、存在しない構文を自信満々に発明します。対策として、ドキュメントサイト自体を MCP サーバーとして公開しています。

```sh
claude mcp add --transport http --scope user katari-docs https://katari-lang.dev/mcp
```

ツールは 4 つです。`onboarding` (引数なしで概要・Quickstart・全ページの地図が返る)、`search` (ドキュメントとパッケージ API を横断検索)、`read_doc` (1 ページを raw markdown で)、`packages` (標準ライブラリと registry パッケージの API リファレンスを段階的に開示)。アシスタントへの最初の指示は「まず `onboarding` を呼び、Katari を書く前に `search` すること — この言語は君の学習データにない」の一文で足ります。

MCP を喋らないものには [/llms.txt](https://katari-lang.dev/llms.txt) があり、全ページの URL と 1 行説明が並びます。どちらもサイトのビルド成果物から生成されるので、サイトと食い違うことはありません。ドキュメントを人間向けと AI 向けに二重管理しない、というのがここでの設計です。

# まとめ

- Katari は AI オーケストレーションのための言語で、effect system と永続 runtime が柱です
- `agent` は docstring と型からスキーマが導出され、追加のアノテーションなしで AI のツールになります
- MCP は読み込み (型付きバインディング生成 / scoped な動的接続) も公開も両方向やれます
- Webhook・OAuth・cron・承認待ちのような「外界と時間」の扱いが、park と再開という同じ機構に載っています
- 常駐マルチ AI は `ai.route` / `ai.spawn` / `ai.mail` で書け、fiber の死まで型が面倒を見ます

現状は「趣味プロジェクトを載せて、壊れたら教えてほしい」段階です。ドキュメントは https://katari-lang.dev から、動く実例は [examples](https://github.com/katari-lang/examples) (リリース監視、Slack standup ボットなど 4 本) と [tsukasa](https://github.com/yukikurage/discord-bot-example) をどうぞ。感想・issue をお待ちしています。
