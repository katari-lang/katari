## STOP 1 — cut the registry snapshot (owner)

In `katari-registry`: update `package-sets/staging.toml` to the 13 versions/commits above (the tooling
fetches each codeload tarball and fills in `sha256`), bump `katari_compiler` to `0.1.6`, then
`tsx scripts/verify.ts staging` and `tsx scripts/cut-snapshot.ts`. `approval` is already absent from
staging.toml — nothing to remove. Then re-pin the consumers: `katari lock` in each examples app and in
tsukasa, commit, push (turns their CI green), and regenerate the site reference:
`pnpm run generate:reference` in katari-web, commit, push (a second deploy).

## STOP 2 — tag the language (owner)

In `katari`: `node scripts/stamp-version.mjs --version 0.1.6`, `git commit -am "release: 0.1.6"`,
`git tag v0.1.6`, `git push && git push --tags`. The tag push is the only publish trigger — the
release workflow builds, publishes every channel (npm / GHCR runtime image / Open VSX / VS Marketplace),
and creates the GitHub Release only after all succeed. A half-published release is never visible.

## Notes carried out of the review (non-blocking, owner's call)

- The 8→64 MiB `KATARI_MAX_REQUEST_BYTES` default is buffered ~3× on a deploy; a snapshot now also
  travels gzipped (~10×), so the raise is a safety net, not the normal path.
- inbox-butler writes its dedup marker before the model call, so a mail that first hits an unset
  `ANTHROPIC_API_KEY` is not retried — a pre-existing design trade-off the docstring states.
- concierge reads its channel ids from live env on every use; a mid-run `katari env set` of a channel
  is honored. Boot still refuses equal channels.
