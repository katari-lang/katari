# Katari Protocol 仕様

版：0.2-draft　／　設計の過程と判断の理由は `../records/2026-10-23-katari-protocol-design-record.md`（設計記録）を参照する。両者が食い違う場合は本仕様を正とする。

---

## 0. 概要

### 0.1 目的

Katari Protocol は、Katari のエンドポイント（Katari Runtime、Timer、外部サービスのプロキシなど）の間で、次のことを行うためのプロトコルである。

- リソースへの権限（grant）を、object-capability の規律に従って渡し、再配布し、失効させる。
- component を起動し（activation）、引数を差し替え（revision）、停止する（dispose）。その間、引数として渡したリソースの寿命を activation の寿命に結びつける。

### 0.2 設計の要点

1. **既存の標準のプロファイルとして作る。** 独自に定めるのは、永続する参照（§3）とライフサイクル（§4）だけである。
2. **Ref は木を下にだけ流れる。** 他人の Ref を渡せるのは activation の引数だけであり、上に流れるのはデータだけである。これにより、すべての Ref の寿命がいずれかの activation のスコープに収まる。
3. **親から子へは状態を、子から親へはイベントを伝える。** 親は引数（revision）で子のあるべき状態を伝え、子は引数で受け取った Ref への操作と `activation/report` で起きたことを伝える。revision は状態の置き換えなので、子は途中の revision を飛ばしてよい。
4. **寿命は activation が決める。** holder が「もう使わない」と伝える仕組み（release）は持たない。
5. **沈黙では止まらない。** 相手が応答しないことを理由に、勝手に終了したり失効させたりしない。終わらせるのは、所有者の明示的な操作か、否定の応答（JSON-RPC のエラー）だけである。

### 0.3 前提

- どのエンドポイントも、任意の時点で再起動しうる。本仕様が定める状態は、すべて永続化する。
- 常時接続のセッションは仮定しない。二者間の関係は、鍵と永続化された表で表す。

### 0.4 層

| # | 層 | 内容 | 節 |
|---|---|---|---|
| 1 | 認証 | DID とその解決、トークン、HTTP binding | §1 |
| 2 | RPC | JSON-RPC、冪等性、outbox と再送、エラーオブジェクト | §2 |
| 3 | capability | 名前（URI）、grant と Ref、値、種別の枠 | §3 |
| 4 | ライフサイクル | `component` 種別、activation、revision、panic、寿命の規則 | §4 |
| 5 | Katari Language | 別の仕様で定める（§7 は本仕様からの要求） | — |

- 各層は、下の層だけに依存する。
- リソースの種別は、それを使う層か、別の文書が定める（§3.5）。本仕様が定める種別は `component` だけであり、Katari の標準の種別（`sink`、`blob`）は `standard-kinds.md` が定める。
- 自分のリソースを提供するだけのエンドポイント（投稿用の sink を提供するプロキシ、blob の置き場など）は、1〜3 層と、提供する種別だけを実装すればよい。他人の Ref を受け取って持ち続けるエンドポイントは、component を提供することになるので、1〜4 層を実装する。
- 一つの処理の中で、複数の層の表を一つのトランザクションで確定させる場面がある（§2.4、§3.2 の R3、§4.2）。そのため、各層は永続ストアを直接持たず、下の層から渡されるトランザクションの単位（Unit of Work）を通じて自分の表を読み書きする。

### 0.5 表記

要件の強さは、BCP 14（RFC 2119、RFC 8174）に対応させて次のように書く。

| 本仕様の表現 | BCP 14 |
|---|---|
| 〜しなければならない ／ 〜してはならない | MUST ／ MUST NOT |
| 〜すべきである ／ 〜すべきでない | SHOULD ／ SHOULD NOT |
| 〜してよい | MAY |

「**根拠**」の項は規範ではない。規則を変えるときに、何を壊すかを判断するための説明である。

### 0.6 準拠する標準

| 用途 | 標準 | 節 |
|---|---|---|

| 署名 | Ed25519（RFC 8032）。JOSE での識別子は `Ed25519`（RFC 9864） | §1.4 |
| トークン | JWT（RFC 7519）を JWS Compact Serialization（RFC 7515）で表したもの。`typ` による明示的な型付け（RFC 8725）。HTTP では Bearer トークン（RFC 6750）として運ぶ | §1.4、§1.6 |

| 型 | JSON Schema 2020-12 ＋ `katariRef` キーワード | §3.6 |
| 参照の意味論 | object-capability（CapTP、Cap'n Web） | §3 |

### 0.7 用語

| 用語 | 意味 |
|---|---|
| エンドポイント | 通信の主体。DID で識別する |
| リソース | エンドポイント（issuer）が保持する実体。URI で識別する |
| 種別 | リソースの種類。リソースが受け付けるメソッドを決める |
| grant | あるリソースを、特定のエンドポイント（holder）が使ってよいという認可。issuer が管理する |
| Ref | grant の URI。値の中で受け渡される |
| component | 起動できる定義。`component` 種別のリソース |
| activation | component の起動一回分。所有者（親）は一つ |
| revision | activation の引数を丸ごと差し替える一回分。通し番号 `rev` を持つ |
| データ | Ref を含まない値 |
| トークン | 送信者が自分の鍵で署名し、リクエストに付ける JWT（§1.4） |
| 再送 | 正規の送信者が、同じ `rpc.id` のリクエストを送り直すこと |
| リプレイ | 第三者が、写し取ったリクエストやトークンを使って送ること（攻撃） |

## 1. 認証層

### 1.1 識別子

- エンドポイントの識別子は DID とする。
- エンドポイントは did:key（Ed25519）を受け付けなければならない。それ以外の方式（did:web など）を受け付けるかは設定とする。
- 実装は、did:key を前提にしてはならない。
  - DID は、中身を解釈しない文字列として扱う。
  - 公開鍵は、常に解決器 `resolve(did) → DID 文書` から得る。解決器は、文書の `id` が DID と一致することを確かめなければならない。did:key の解決器は、DID から文書を組み立てる（通信しない）。
  - 自分の DID と、現在の署名鍵を、別々に持つ。

```
did:key:z<base58btc(0xed 0x01 ‖ Ed25519 公開鍵 32 バイト)>
```

did:key の解決器が組み立てる文書は、この公開鍵を一つだけ持つ。鍵の `id` は、DID に `#` と DID の `z` から後ろの部分をつなげたもの（`did:key:z6Mk…#z6Mk…`）とし、`authentication` に載せる。

### 1.2 状態

```
self     : { did, 署名鍵 }
peers    : did → url                 運用者の設定。送り先の経路
policy   : did の集合                運用者の設定。通信を伴う解決をしてよい DID（解決器を加えた場合）
resolved : did → DID 文書             解決器のキャッシュ（解決器を加えた場合）
```

### 1.3 送り先の解決

送り先の URL は、DID から次の順で決める。

1. `peers` にあれば、その URL。
2. `policy` にあり、受け付ける方式の解決器があれば、DID 文書の `service` の URL。
3. どちらでもなければ、送らない。上の層に「送り先を解決できない」と知らせ、そのエントリは一時的な障害として outbox で待つ（§2.4）。解決器の失敗も一時的な障害として扱う。

規則：

- **接続先の URL を、第三者から渡された値（Ref など）から得てはならない。**
- `peers` の URL は、運用者が書いたものなので、そのまま用いる。
- 解決器を加える場合：
  - 通信を伴う解決は、`policy` にある DID に限る。送り先の解決にも、受け取る側の解決（§1.5）にも、これを当てはめる。`policy` の既定は空とする。`peers` は経路だけを決めるので、`peers` に載せた did:web でも、鍵を得るには `policy` に載せる。
  - DID 文書の `service` の URL は、その文書を取得した URL と同じオリジン（スキーム、ホスト、ポート）でなければならない。違えば、その `service` を用いない。
  - 文書の取得と、文書から得た URL への接続では、TLS の証明書の検証を省いてはならず、HTTP のリダイレクトに従ってはならない。
  - DID ごと・送信元ごとに解決の回数を制限し、結果（失敗を含む）をキャッシュしなければならない。
  - 署名の検証に失敗したら、一度だけキャッシュを捨てて解決し直してよい。

**根拠**
- 第三者が書いた URL に接続すると、内部ネットワークへの接続を誘導される（SSRF）。上の規則では、接続先のホストは運用者が書いたもの（`peers` の URL か、`policy` に載せた DID）に限られる。相手が DNS を内部の IP に向けても、TLS のホスト名の検証で止まる。リダイレクトに従うと行き先のホストを相手のサーバーが選べるので、従わない。これにより、接続先の IP を見て拒否する仕組みは要らない。
- `service` を文書と同じオリジンに限るのは、DID の持ち主にホスト名を書かせないためである。書かせると、`policy` に載せた相手が乗っ取られたときに、こちらの内部の名前（`https://jenkins.corp.internal/…`）を書かれ、こちらのネットワークから内部へ送らされる。同じオリジンに限れば、乗っ取りの被害はその相手に渡したもの（データと grant）に収まる。エンドポイントを文書と別のホストに置きたい相手は、そのホストの DID を使うか、運用者が `peers` に書く。
- 送り先は `peers` と `policy` に載せた DID に限られる。Ref の issuer の DID はデータが実際に送られる先そのものなので、これで流出先も絞れる。

### 1.4 トークン

リクエストの送信者は、自分の鍵で署名した JWT（トークン）を、JWS Compact Serialization で表して付ける。トークンは本文を含まない。本文は JSON-RPC のオブジェクトそのものである（§2.1）。

**保護ヘッダ**

```json
{ "alg": "Ed25519", "typ": "katari+jwt", "kid": "<送信者の DID 文書の authentication に載っている鍵の id（絶対形の DID URL）>" }
```

鍵そのもの（`jwk`）をヘッダに入れてはならない。

**クレーム**

| クレーム | 内容 |
|---|---|
| `iss` | 送信者の DID。`kid` の `#` より前の部分と一致しなければならない |
| `aud` | 受信者の DID |
| `iat` | 作った時刻（Unix 秒） |
| `exp` | 有効期限（Unix 秒）。`exp - iat` は有効期間の上限（付録 A）以下とする |
| `kv` | プロトコルの版（整数）。本仕様では `1` |

- 送信者は、有効期間の内であれば、同じ受信者への複数のリクエストに同じトークンを用いてよい。
- 応答には、トークンを付けない。

**根拠**
- トークンを本文と分けるのは、本文を普通の JSON-RPC のままにするためである。curl などの既存の道具で試せ、記録をそのまま読め、他人が実装するときに要るのはトークンの検証だけになる。MCP（OAuth の Bearer トークン）や AT Protocol のサービス間認証と同じ形である。
- 本文の完全性と、応答が送り先から来たことは、輸送路（§1.6）に任せる。本文と応答に署名しても、それで防げる相手は TLS を終端する中継機器だけである。署名鍵は応答するホストの上にあるので、ホストを乗っ取った攻撃者は鍵も得る。送り先の設定の誤りは、受信者が `aud` の不一致で拒否する。
- 有効期間に上限を置き、`aud` で宛先を縛るのは、写し取られたトークンを使える時間と相手を狭めるためである。
- トークンを使い回せるので、送信者はリクエストごとに署名しなくてよい。人や AI は、トークンを一度作れば試しの呼び出しを繰り返せる。
- `jti` は持たない。受信者は `jti` の表を持たず、トークンは使い回すためである。重複の排除は `rpc.id` で行う（§2）。
- AT Protocol の `lxm`（トークンをメソッドに縛るクレーム）は持たない。ATP では PDS が利用者の代わりにトークンを作って第三者のサービスに渡すが、Katari では送信者が自分のリクエストのためにだけ作る。
- `jwk` を入れないのは、埋め込まれた鍵を信じてしまう脆弱性の型を、構造的に避けるためである。鍵は常に、`kid` の DID の文書から取り出す。
- `iss` は JWT の慣習に従って置き、`kid` との一致を確かめる（§1.5）。

### 1.5 検証

受信者は、リクエストのトークンを次の順に検証しなければならない。

1. トークンが JWS Compact として解釈でき、`alg` が `Ed25519`、`typ` が `katari+jwt` で、`kid` が絶対形の DID URL である。
2. `kid` の `#` より前を、送信者の DID（`sender`）とする。`sender` が受け付けない方式の DID であるか、通信を伴う解決が要るのに `policy` にない（§1.3）なら、解決せずに拒否する。それ以外は `sender` を解決し、解決できなければ拒否する。
3. その文書の `authentication` に載っている鍵から、`id` が `kid` と等しいものを探す。なければ拒否する。文書の中の相対的な `id`（`#key-1` など）は、文書の `id` を基にして絶対形にしてから比べる。
4. その鍵で署名を検証する。
5. `iss` が `sender` である。
6. `aud` が自分の DID である。
7. `kv` が受け付ける版である。
8. 現在時刻が `iat` から `exp` までの間にあり（時計のずれは付録 A の範囲で許す）、`exp - iat` が有効期間の上限以下である。
9. `sender` と本文を上の層に渡す。

手順 1〜4 で読むのは保護ヘッダだけであり、署名を確かめていないクレームは読まない。

応答は認証しない。応答が送り先から来たことは、送り先の URL（§1.3）と輸送路（§1.6）による。

**根拠**
- DID 文書は、鍵ごとに用途（検証関係）を宣言する。トークンの署名は送信者が本人であることを示すためのものなので、`authentication` の鍵だけを受け付ける。これにより、暗号化用などとして載せた鍵では署名が通らない。
- `kid` は `sender` から始まるので、使える鍵は `sender` 自身の文書に定義されたものに限られる。`authentication` が別の DID の鍵を参照していても、その鍵の `id` は `kid` と一致しない。
- 解決は認証より前に起きるので、誰でもこちらに文書を取りに行かせることができる。`policy` にない DID を解決せずに拒否するのは、これを防ぐためである。
- クレームを署名の検証の後に読むのは、確かめていない値で判断しないためである。
- `kv` を確かめるのは、版の違う相手の本文を、自分の版の意味で解釈しないためである。

**拒否の理由**（Problem Details の `type` は `tag:katari-lang.dev,2026:error:<理由>`）

| 理由 | 状況 | 性質 |
|---|---|---|
| `malformed` | トークンがない、JWT として解釈できない、`kid` が絶対形の DID URL でない、`iss` が `sender` でない | 再送しても変わらない |
| `unsupported` | `alg`・`typ` が異なる、受け付けない DID（受け付けない方式、`policy` にない）、`kv` が受け付けない版 | 再送しても変わらない |
| `bad-signature` | 署名が検証できない、`kid` の鍵が `sender` の文書の `authentication` にない | 再送しても変わらない |
| `misdirected` | `aud` が受信者でない | 再送しても変わらない |
| `stale` | 有効期間の外である、または有効期間が上限を超える | 新しいトークンでの再送で変わりうる |
| `unavailable` | 受信者の側で今は検証や処理ができない（一時的な障害、`sender` を解決できない） | 待ってからの再送で変わりうる |

拒否は、JSON-RPC の応答ではなく、binding の層の応答として返る（HTTP では §1.6）。送信者はこれを再送の判断にだけ用いる。どう再送するかは §2.4 が定める。

**リプレイ**：同じリクエストを送り直すことは、§2 の冪等性によって無害になる。トークンを写し取った者は、有効期間の間、送信者として別のリクエストを送れる。これは輸送路で防ぎ、防げない範囲は §6 に挙げる。

### 1.6 HTTP binding

一つのリクエストを、一つの HTTP リクエストと応答で運ぶ。トークンは `Authorization` ヘッダの Bearer トークン（RFC 6750）として運ぶ。

```
POST <§1.3 で決めた URL>
Authorization: Bearer <トークン>
Content-Type: application/json

<JSON-RPC のリクエスト>
```

| 状況 | HTTP | 本文 |
|---|---|---|
| `malformed`・`unsupported`・`bad-signature`・`misdirected`・`stale` | 401 | `application/problem+json` |
| `unavailable` | 503（`Retry-After` を付けてよい） | 同上 |
| 本文の Content-Type が `application/json` でない | 415 | 同上 |
| 検証に通った | 200 | JSON-RPC の応答（`application/json`）。JSON-RPC のエラーも 200 で返す |

- 401 には `WWW-Authenticate: Bearer` を付けなければならない。トークンが付いていた場合は、`error="invalid_token"` を加える（RFC 6750 §3）。
- すべての応答に `Cache-Control: no-store` を付けなければならない。
- 実装は、`Authorization` ヘッダを記録に残すべきでない。

**輸送路**：本文の完全性と、応答が送り先から来たことは、輸送路に任せる。機密性も同じである。

| 経路 | 要件 |
|---|---|
| 同じホストの中 | 平文の `http` を用いてよい |
| ホストをまたぐ閉じたネットワーク | TLS か、相手を認証する下の層での暗号化（WireGuard、サービスメッシュの mTLS など）を用いなければならない |
| インターネット | `https` を用いなければならない |

トークンの形と検証（§1.4〜§1.5）は輸送路に依存しない。別の binding（WebSocket など）を足すときは、トークンの渡し方をその binding が定める。

## 2. RPC 層

### 2.1 メッセージ

メッセージは、JSON-RPC 2.0 のリクエストまたは応答のオブジェクトである。binding はこれをそのまま本文として運ぶ（§1.6）。

- `rpc.id` は必須の文字列（UUIDv7）とし、送信者が付ける。通知（`id` のないリクエスト）は用いない。
- メソッドの名前空間は、層と種別ごとに分ける（`grant/` は §3、`activation/` は §4、種別のメソッドは `<種別>/`。§3.5）。

### 2.2 状態

```
outbox   : エントリ → { request, status: pending | done | failed, path: data | control,
                         channel?, attempts, next_attempt_at, lease? }
seen_rpc : (sender, rpc.id) → { status: processing | done, fingerprint?, response }
```

### 2.3 受信の処理

受信者は、§1.5 に通ったリクエストを次の順に判定し、最初に該当した行の応答を、JSON-RPC の応答として返す。

| # | 状況 | 応答 | `seen_rpc` |
|---|---|---|---|
| 1 | 本文が JSON として解釈できない | -32700 | 記録しない |
| 2 | JSON-RPC のリクエストとして不正 | -32600 | 記録しない |
| 3 | `(sender, rpc.id)` が処理中 | 1001 | — |
| 4 | 処理済みで、fingerprint が異なる（照合する場合） | 1002 | — |
| 5 | 処理済み | 保存した応答 | — |
| 6 | 新しく、上の層の処理が一時的なエラー | 2001 | 記録せず、処理をロールバックする |
| 7 | 新しく、上の層の処理がそれ以外のエラー | そのエラー | 記録する |
| 8 | 新しく、予期しない内部エラー | -32603 | 記録せず、処理をロールバックする |
| 9 | 新しく、成功 | `result` | 記録する |

- `seen_rpc` への登録は原子的に行い、処理結果の記録は、上の層の状態の変更と同じトランザクションで確定させなければならない。
- 保存するのは JSON-RPC の応答オブジェクトである。
- fingerprint の照合は任意とする（RFC 8785 で正規化したリクエストの SHA-256）。

**根拠**：送信者に再送させる応答（1001・-32603・2001）は記録しない。記録すると、再送には行 5 で同じ応答が返り続け、再送の意味がなくなる。記録しない応答では、処理による状態の変更も確定させない。確定させると、再送で同じ処理がもう一度行われる。

### 2.4 送信と再送

- 配送は at-least-once とする。送るリクエストは outbox に永続化し、再起動後に再送する。
- `rpc.id` は outbox に積んだ時点で決め、再送しても変えない。再送には、有効期間の内のトークンを用いる（§1.4）。
- 一つのエントリについて、同時に送るのは一本までとする。タイムアウトの後に再送するときは、先に前のリクエストを中断する。複数のプロセスで outbox を共有する場合は、リースで排他する。
- 再送の間隔は、ジッター付きの指数バックオフとする。`unavailable` の待ち時間の指定があれば従う。
- **経路**：

  | 経路 | メッセージ | 再送の上限 | 上限に達したら |
  |---|---|---|---|
  | データ | 制御以外のすべて | あり | `failed` とし、上の層に知らせる |
  | 制御 | `activation/*`、寿命の規則による `grant/revoke` | なし（間隔の上限のみ） | — |

- 送信をやめてよいのは、上限に達したときか、**JSON-RPC の**応答が返ったときだけである。データの経路では、再送しても変わらない拒否（`malformed`・`unsupported`・`bad-signature`・`misdirected`）でただちに `failed` としてよい。制御の経路では、そうした拒否でも再送を続け、運用者に知らせなければならない。
- 送り先を解決できない（§1.3）エントリは、捨てずに再送の規則に従って待つ。
- `failed` のエントリの `rpc.id` を再利用してはならない。
- 制御の経路の再送は、送り先ごとにまとめるべきである。
- **チャネル**：エントリには任意でチャネルのキーを付けられる。同じチャネルのエントリは積んだ順に一つずつ送る。チャネルのエントリが `failed` になったら、そのチャネルを止め、上の層に知らせる。
- **応答の受け取り**：エントリを完了にすることと、上の層が結果を確定させることは、同じ Unit of Work で行わなければならない。応答の `rpc.id` が一致しないとき、または JSON-RPC の応答として解釈できないときは、応答を破棄して再送する。エントリがすでに完了していれば、応答を破棄する。
- 受信者は、`seen_rpc` を、データの経路の再送の期限とトークンの有効期間の上限を足したものより長く保持しなければならない。

**根拠**：制御の経路を諦めないのは、`panic` の報告や寿命の後始末が途中で消えると、相手が永遠に待つためである。制御のメッセージは意味上の冪等キー（`aid`、`(aid, rev)`）を持つので、`seen_rpc` の保持期間を超えて二度処理されても害がない。

**重複の排除は層ごとに行う**

| 仕組み | 防ぐもの | 層 |
|---|---|---|
| トークンの有効期間の上限 | 写し取ったトークンの長期の使用 | 1 |
| `(sender, rpc.id)` | 再送・リプレイによる二重処理 | 2 |
| `aid`、`(aid, rev)` | 同じ操作の重複 | 4 |

### 2.5 エラー

**二つの種類**

- **型に現れるエラー**：component の型に従って、データとして返す。プロトコルは関与しない。
- **型に現れないエラー**：次の **Katari のエラーオブジェクト**で表す。トークンの段階では binding の層の応答の Problem Details（§1.6）、リクエストの失敗は JSON-RPC の `error`、activation の失敗は `panic` の報告（§4.6）で運ぶ。

```json
{ "code": 1103, "message": "Grant has been revoked",
  "data": { "type": "tag:katari-lang.dev,2026:error:revoked", "title": "Grant has been revoked" } }
```

- `code` は扱い方の分類（再送するか、どの層の問題か）を表し、エラーの種類は `data.type` で識別する。
- 本仕様のエラーの `type` は `tag:katari-lang.dev,2026:error:<名前>` とする。拡張は、自分が持つドメインに基づく URI を用いなければならない。
- `code` は本仕様だけが定める。範囲は層ごとに割り当てる（-32700、-32600〜-32603：JSON-RPC 標準、1000 番台：RPC 層、1100 番台：capability 層、1200 番台：ライフサイクル層、それ以外：予約）。拡張は新しい `code` を作らず、2000 か 2001 を用いる。知らない `code` は 2000 として扱う。
- 拡張は、他人のドメインや、本仕様の `tag:katari-lang.dev,...` の名前空間を `type` に用いてはならない。

| `code` | `type` の名前 | 意味 |
|---|---|---|
| -32700 | `parse-error` | 本文が JSON として解釈できない |
| -32600 | `invalid` | リクエストの形式が不正 |
| -32601 | `no-method` | メソッドが存在しない、またはリソースの種別に合わない |
| -32602 | `invalid-params` | 引数が不正（型が合わない、データの位置に Ref がある、など） |
| -32603 | `internal` | 内部エラー（同じ `rpc.id` で再送してよい） |
| 1001 | `in-progress` | 同じ `rpc.id` が処理中 |
| 1002 | `id-reused` | 同じ `rpc.id` で内容の異なるリクエストが処理済み |
| 1101 | `unknown-grant` | grant が存在しない、または URI と対象が一致しない |
| 1102 | `unauthorized` | holder が送信者でない |
| 1103 | `revoked` | grant またはその祖先が失効している |
| 1201 | `unknown-activation` | 該当する activation がない（送信者が所有者・子でない場合を含む） |
| 1202 | `faulted` | `faulted` の activation に `dispose` 以外を送った |
| 1203 | `panic` | `panic` の既定の種類 |
| 2000 | （拡張が定める） | 拡張のエラー。再送しない |
| 2001 | （拡張が定める） | 拡張のエラーのうち一時的なもの。再送してよい |

## 3. capability 層

### 3.1 名前

```
リソース   : katari:<issuer の DID>/<種別>/<ローカル ID>
grant      : <リソースの URI>/grant/<grant の ID>
activation : katari:<親の DID>/activation/<aid>          表示用
リクエスト : katari:<sender>/rpc/<rpc.id>                 表示用
```

- 各区切り（種別、ローカル ID、grant の ID）は `/` を含まない。DID も `/` を含まないので、最初の `/` までが DID である。
- `katari:` の後に `//` を置かない（RFC 3986 の一般的な構文で扱えるようにするため）。
- **URI の権威（DID の部分）は、その名前を作り、一意性に責任を持つエンドポイント**である。リソースと grant では、権威は送り先（issuer）でもある。activation では、権威（親）は送り先（子）と異なる。
- 通信の中で URI を使うのは、第三者に渡る名前（Ref）だけとする。activation とリクエストの URI は、ログや表示のための表記である。
- URI は識別子であり、権限ではない。権限の判断に URI を用いてはならない。URI に秘密の情報を含めてはならない。
- 種別の名前は、本仕様と `standard-kinds.md` が定めるもの（`component`、`sink`、`blob`）は短い名前、それ以外は逆ドメイン形式とする。リソースの種別は変わらない。

### 3.2 値

```
Value := null | bool | number | string | [ Value, ... ]
       | { key: Value, ... }      -- key が "$" で始まる単一キーのものを除く
       | { "$ref": Ref }          -- 参照
       | { "$lit": Value }        -- "$" で始まるキーを持つオブジェクトのエスケープ

Ref   := { "grant": <grant の URI> }
```

- `$ref` を含まない値を**データ**と呼ぶ。
- Ref は内容のハッシュを持たない。内容が変わらないことは、種別の定義が issuer の義務として定める（`standard-kinds.md`）。
- Ref は issuer の URL を持たない。送り先は grant の URI の DID から §1.3 で決める。

**Ref の規則**

- **R1（流れる場所）**：Ref を含めてよいのは、activation の引数（§4 の `activation/init`・`activation/revise` の `args`）だけである。それ以外の値（種別のメソッドの params と result など）はデータでなければならず、Ref を含む値を受け取ったら -32602 を返す。例外は `grant/derive`・`grant/redeem` の結果である。
- **R2（holder）**：activation の引数に含める Ref は、受信者を holder とする grant でなければならない。自分のリソースなら自分で作り、他人のリソースなら `grant/derive` で作らせる。これを行うのはライフサイクル層である（§4.10）。
- **R3（応答で作る grant）**：`grant/derive`・`grant/redeem` で grant を作るときは、`seen_rpc` への応答の記録と同じトランザクションで確定させなければならない。

**根拠**：R1 により、Ref は親から子へ下にだけ流れ、データは上に流れる（React の props とコールバックと同じ形）。Ref が上に流れると、受け取った側のどの activation のスコープにも属さない Ref ができ、「activation が終われば、渡したリソースは解放してよい」が成り立たなくなる。呼び出しより長く残す結果の扱いは §4.8 に示す。

### 3.3 状態

issuer だけが状態を持つ。holder は、本層の表を持たない（Ref は自己完結した値である）。

```
grants : grant の ID → { holder: DID, target: リソースの URI, derived_from?: grant の ID, revoked: bool }
tokens : 招待トークン → { target, redeemed: bool, expires_at }
```

- リソースの表は持たない。種別は URI からわかる（§3.1）。リソースの中身と種別に固有の情報（component の定義、sink のイベントの型など）は、上の層が持つ。
- grant と上の層の概念（activation など）との対応は、上の層の表で持つ。

### 3.4 メソッド

holder から issuer に送る。`grant` は grant の URI である。

| メソッド | params | result | 条件 |
|---|---|---|---|
| `grant/derive` | `{ items: [ { grant, holder } ] }` | `{ refs: [ { "$ref": Ref } ] }`（同じ順） | holder・祖先が有効 |
| `grant/revoke` | `{ grant }` | `null` | 送信者が issuer 自身か、`derived_from` をたどった真の祖先の holder（holder は自分の grant を失効させられない） |
| `grant/redeem` | `{ token }` | `{ "$ref": Ref }` | トークンが有効で未使用 |

**検証**：grant を受け取るメソッド（`grant/derive` と種別のメソッド）では、送信者を `s`、grant の URI を `g` として次を確かめる。

1. `g` の DID が自分であり、`g` のリソースの部分が `grants[g].target` と一致する。満たさなければ 1101。
2. 「holder・祖先が有効」：`grants[g].holder = s` であり（でなければ 1102）、`g` と `derived_from` をたどった祖先がすべて失効していない（でなければ 1103）。

**その他の規則**

- `grant/derive` は、一部の項目が失敗したら全体を失敗とし、grant を一つも作らない。sub-grant の `target` は元と同じ、`derived_from` は元の grant とする。
- grant を失効させると、`derived_from` をたどるすべての sub-grant も失効する。
- 受信者は、メッセージを受け取ってから一定時間（付録 A）以内に応答すべきである。

**ブートストラップ**：最初の grant（root grant）は、設定による発行か、招待トークン（128 ビット以上の乱数、一度だけ使える）の `grant/redeem` で得る。それ以外の grant は、すべて activation の引数として受け取る。

### 3.5 種別

本層は種別を一つも定めず、種別を定めるための枠だけを持つ。種別は、それを使う層か、別の文書が定める。

| 種別 | 定める文書 |
|---|---|
| `component` | 本仕様の §4 |
| `sink`、`blob` | `standard-kinds.md` |
| 利用者の種別 | 利用者 |

**種別を定める文書が書くこと**

- メソッドの名前（`<種別>/<操作>`）と、params・result の形。params は `grant` を持つ。
- 受理する前に行う検査。
- 型引数をとる場合は、その意味（§3.6 の `targs`）。
- メソッドの意味。

**種別のメソッドの処理**

1. 本層は、§3.4 の検証を行う。
2. メソッドが grant の対象の種別のものでなければ、本層は -32601 を返す。
3. 本層は、params を復号する（R1 により、Ref があれば -32602）。
4. 本層は、メソッドをその種別を定める層に渡す。その層は、自分の検査（型など）に通らなければ、受理する前に -32602 を返す。

**種別のメソッドの制約**

- 種別のメソッドは、データを受け取るか、持っている内容を返す短い操作とし、応答時間の上限（付録 A）の中で応答する。計算して結果を返す処理は、component として起動する（§4）。本層には、汎用のメソッド呼び出しはない。
- 結果に外部の URL（外部ストレージの署名付き URL など）を含め、holder にそれを取得させる種別は、その取得で接続してよい先を自分で定めなければならない。その URL は第三者が書いたものであり、§1.3 の規則（接続先のホストは `peers` と `policy` から得る）の外にある。

**権限の絞り込み**：grant ごとに異なる権限は持たせない。絞った権限が必要なら、issuer が操作の一部だけを転送する別のリソース（facet）を作る。

### 3.6 型

- 型は JSON Schema 2020-12 で表し、復号した後の値（`$ref` を Ref に、`$lit` を元の値に戻したもの）に適用する。
- プロトコルの上を流れる型は単相である（型引数はすべて具体化されている）。
- Ref は `katariRef` キーワードで表す。

```json
{ "katariRef": { "kind": "sink", "targs": [ { "$ref": "#/$defs/Event" } ] } }
```

| 項目 | 検証 |
|---|---|
| `kind` | する。値が Ref であり、URI の種別が一致すること |
| `targs` | しない（説明のため。意味は種別が定め、Ref の中身の型は issuer が検査する） |

### 3.7 上の層への API

| API | 内容 |
|---|---|
| `check(grant, sender)` | §3.4 の検証を行い、対象のリソースを返す |
| `issue(resource, holder)` | 自分のリソースへの grant を作り、URI を返す |
| `revoke(grant)` | grant と、それから派生した sub-grant を失効させる |
| `encode(value)` / `decode(value)` | 値を §3.2 の形式に変換する。R1 を適用する（R2 の grant は §4.10 で用意する） |

## 4. ライフサイクル層

### 4.1 概念

- **component**：起動できる定義。本層が定める種別（§3.5）であり、メソッドを持たない。その grant が「新しく起動してよい」という権限になり、`activation/init` に渡す。component の grant を失効させても、起動済みの activation には影響しない（引数から外すときは、L3 により先に終わらせる）。受け付ける型引数・引数と、起動した後の動作は、component を提供する上の層が決める。
- **activation**：component の起動一回分。所有者（親のエンドポイント）は一つである。名前は `katari:<親の DID>/activation/<aid>`。
- **revision**：activation の型引数と引数を丸ごと差し替える一回分。

### 4.2 状態

```
hosted  : (parent_did, aid) → { component, targs, applied_rev, applied_args, instance, status }
            子として動かしている activation。parent_did は init の送信者

started : aid → { child, component, targs, sent_rev, acked_rev, status, spawned_by }
            親として起動した activation。child は component の issuer
            spawned_by : この activation を起動した hosted の activation の集まり

arg_grants  : (aid, grant_id) → { revs }
            started の activation の引数として、自分が発行した grant
arg_derived : (aid, issuer, grant_id) → { source, revs }
            started の activation の引数のために、他の issuer に derive させた sub-grant
            source : 派生元の grant（spawned_by の activation が引数として受け取ったもの）
```

- `spawned(X) = { Y ∈ started | X ∈ spawned_by(Y) }`（逆引きで得る）。
- `spawned_by` の辺が、エンドポイントの中の**局所 activation DAG** をなす。共有はエンドポイントの中でだけ行う。エンドポイントをまたいで一つの処理を共有したい場合は、所有者ごとに別の activation を作り、提供する側が中で共有する。
- 自分自身が提供する component を起動した activation は、`started` と `hosted` の両方に現れる。
- grant の作成と `arg_grants`・`arg_derived` への記録は、同じトランザクションで確定させなければならない。
- 親は、`started` の行を削除するとき（`disposed` を受け取ったとき、強制終了したとき、init が JSON-RPC のエラーで拒否されたとき）、その activation の `arg_grants` の grant を失効させ、`arg_derived` の sub-grant の `grant/revoke` を outbox に積む。

### 4.3 メソッド

| メソッド | 向き | params |
|---|---|---|
| `activation/init` | 親 → component の issuer | `{ component, aid, targs, args }`（`component` は grant の URI） |
| `activation/revise` | 親 → 子 | `{ aid, rev, targs?, args }`（`targs` を省略したら変えない） |
| `activation/dispose` | 親 → 子 | `{ aid }` |
| `activation/report` | 子 → 親 | `{ aid, event }` |

`event` は `{ kind: "revised", rev }`、`{ kind: "disposed" }`、`{ kind: "panic", error }` のいずれか。いずれのメソッドも、result は受理の確認（`null`）だけである。

**認可**

| メソッド | 受信者が確かめること |
|---|---|
| `activation/init` | `check(component, sender)` が通る |
| `activation/revise`・`activation/dispose` | `hosted` に `(sender, aid)` がある |
| `activation/report` | `started` に `aid` があり、その `child` が `sender` |

該当がなければ、存在の有無を区別せずに 1201 を返す。

**冪等性**

- `aid` は親の中で一意とし、終わった後も再利用してはならない。同じ `(親, aid)` の init は、二度目以降は何もせず受理する。
- revise の冪等キーは `(aid, rev)` とする。子は、受け取った revise のうち最大の `rev` を適用する。それより古い revise は適用せずに捨ててよい。`revised` は適用した `rev` を返す。

**順序**

- 親は、同じ activation への `activation/init`・`activation/revise`・`activation/dispose` を、activation の名前（§3.1）をキーとする一つのチャネル（§2.4）で送らなければならない。

**根拠**：init より先に revise・dispose が届くと、子は 1201 を返し、親は JSON-RPC の応答を受けたので送信をやめる。その後に届いた init で activation が動き出し、親は届くことのない `revised`・`disposed` を待ち続ける。

**受理の検査**

- 本層は、init・revise を受理するとき、同じ Unit of Work の中で上の層のフック `onInit`・`onRevise`（§4.10）を呼ぶ。上の層は、受け付けない型引数・引数をエラーで拒否する（型が合わない場合は -32602）。拒否されたら、本層は何も永続化せず、そのエラーを応答にする。init が拒否されたら、activation は作られない。
- component は、受け付けない型引数・引数を、永続化する前に拒否しなければならない。何を受け付けるかは component が決める。
- `targs` は、component の型引数に与える型を、単相の JSON Schema（§3.6）として並べた配列である。本層は中身を解釈しない。

**根拠**：型の合わない値が永続化されると、後の再生のときに初めて誤りが表に出る。そのため、受理の時点で拒否させる。本層が定めるのは、拒否できる時点と、拒否の伝え方だけである。

### 4.4 状態遷移

```
working ──panic──▶ faulted ──dispose──▶ disposing ──disposed──▶ 終了
   └─────────────────── dispose ───────────────┘
```

| 状態 | 意味 | 受け付けるもの |
|---|---|---|
| `working` | 実行中 | revise、dispose |
| `faulted` | `panic` を報告し、親の dispose を待っている | dispose（revise には 1202） |
| `disposing` | dispose を処理している（L4） | dispose（重複は何もせず受理する）。revise は受理して無視する |
| 終了 | `disposed` を報告した。行を削除する | — |

親の側の終了の理由：`completed`（`working` から dispose）、`failed`（`faulted` から dispose、応答のないまま強制終了、または init の拒否）、`cancelled`（強制終了による打ち切り）。

### 4.5 寿命の規則

revision n の引数の参照の集合を `A_n`、hosted の activation を `X` とする。

**L1（grant の単位）**：親は、引数に含める参照ごとに、`(holder, target, aid)` を単位として grant を一つ作る。同じ activation の revision をまたいで同じ参照を渡すときは、同じ grant を再利用する。

**L2（渡せるもの）**：started の activation `e` の引数に含めてよいのは、`spawned_by(e)` の activation が引数として受け取った参照（derive した sub-grant として。`arg_derived` に `source` とともに記録する）と、自分のリソースだけである。

**L3（revision の反映）**：閉じられる参照を `C = A_n \ A_{n+1}` とする。

1. 本層は、revise を受理するときに `onRevise(aid, rev, targs, args)` を呼ぶ（§4.3）。
2. 上の層は、自分の方針で反映する（§4.7）。必要なら `spawned(X)` に revise を送り、`revised` を待つ。`revised` を返すまでは `C` を使い続けてよい。
3. 上の層は `commitRevision(aid, rev)` を呼ぶ。これは「`X` はもう `C` を使わない」という宣言であり、`X` の実行の中で作ったリソース（closure など）を経由した使用も含む。本層が確かめるのは 4 の条件 I3 だけで、それ以外の経路は上の層が守る。
4. 本層は、**条件 I3** を確かめる：`spawned(X)` のどの activation も、`C` から derive した参照（`source ∈ C`）を、適用済みの引数にも、`revised` を受け取っていない revision の引数にも含んでいない。また、`C` に含まれる component を起動した activation が、`spawned(X)` に残っていない。
   - 満たさなければ、上の層のバグとして `X` を `panic` させる（`data` に、外される参照と、それを含む、またはそれから起動した子孫の activation と revision を入れる）。
   - 満たせば、`revised(n+1)` を報告する。
5. 親は `revised(n+1)` を受け取ったら、`C` に対応する `arg_grants` の grant を失効させ、`arg_derived` の sub-grant の `grant/revoke` を outbox に積む。

**L4（dispose）**

1. 本層は、上の層のフック `onDispose(aid)` を呼ぶ（`faulted` でも呼ぶ）。
2. 上の層は、解放処理を好きな順に行う。この間は、引数の Ref と子孫を使ってよい。
3. 上の層は `commitDispose(aid)` を呼ぶ。
4. 本層は、まだ終わっていない `spawned(X)` に dispose を送り、すべての `disposed` を待つ。`spawned_by` のいずれかが dispose された activation は、dispose する。
5. 本層は、`disposed` を報告する。
6. 親は `disposed` を受け取ったら、行を削除する（grant の失効は §4.2）。

**L5（並行性）**：エンドポイントは、`revised`・`disposed` を待つ間も、他の activation のメッセージを処理し続けなければならない。

**根拠**：L3・L4 は、本層が自動で行う手順ではなく、本層が守らせる条件と、上の層が呼ぶ API として定める。子孫に送る新しい引数や、解放処理の順序は、プログラムにしか決められないためである。本層は、寿命の安全を壊さないことを確かめ、最後の後片付けを受け持つ。sub-grant は、それを引数に含めた親が、子が手放した時点で失効させる。派生元が閉じるときには、I3 と L4 の 4 により子孫はすでに手放しているので、派生元の側で改めて失効させる必要はない。

### 4.6 失敗（panic）

- activation の中で回復できない失敗が起きたら（言語の中で処理されなかった失敗、資源の上限、条件 I3 の違反など）、その activation は `panic` を起こす。
- `panic` を起こした activation は、次を行わなければならない。
  1. 自分の計算を止める。
  2. `spawned(X)` にすべて dispose を送る（キャンセルを下へ伝える）。
  3. `panic` を親に報告する（子孫の `disposed` を待たなくてよい）。
  4. `faulted` で親の dispose を待つ。自分では終了しない。引数の Ref は、dispose まで保持する（使わない）。
- `faulted` の activation が issuer であるリソースへの操作は、受理して捨ててよい。
- `faulted` の activation から新しいメッセージ（種別のメソッド、`activation/init` など）を送ってはならない。`faulted` になる前に outbox に積まれたものは配送する。
- **本層の中で起きる失敗**：activation の代わりに送った、結果を待たないメッセージが失敗したら（再送の上限、再送しても変わらない拒否、失効、型の不一致）、本層はその activation を `faulted` にし、`panic` を報告する。`faulted` への遷移と報告を outbox に積むことは、同じ Unit of Work で確定させる。そのうえで、上の層にフック `onFault(aid, error)` で知らせる。結果を待つメッセージの失敗は、呼び出し元にエラーとして返す。
- 親は `panic` を受け取ったら上の層に知らせる。処理するなら子を dispose する。処理しないなら、自分も `panic` を起こす。

**根拠**：失敗は木を上に、キャンセルは木を下に伝わる（structured concurrency と同じ形）。子孫を止めるのは、失敗した activation の下で外部への作用が続かないようにするためである。終わらせるのは所有者だけ、という原則は保たれる（子孫の所有者は、失敗した activation 自身である）。

### 4.7 revise の反映の方針（指針）

revise について定めるのは「適用し終えたら `revised` を返す」だけであり、いつ・どう適用するかは子が決める。代表的な方針：

| 方針 | 動き |
|---|---|
| 区切りで反映する | 処理のフェーズの区切りで、最新の revise を適用して `revised` を返し、次のフェーズを新しい引数で続ける |
| 完了してから最新を実行 | 今の実行を終えてから、最新の引数で実行し直す |
| キャンセルして最新を実行 | 今の実行を止め、最新の引数で始める |
| メモ化 | 引数が前と同じなら、何もせずに `revised` を返す |

- dispose も区切りまで待たされうる。すぐに止めたい処理は、中断できるように作るべきである。
- 型引数の変更をどう反映するか（状態を捨てるか、移行するか）は、component が決める。型引数に依存する Ref（`Sink<T>` など）は、親が新しい Ref を revise で渡す。
- 古い引数で計算した結果を区別したい場合は、親が revision ごとに別の sink を渡せばよい。

### 4.8 スコープより長く残す結果（指針）

Ref は上に流れないので、子が作ったリソースの Ref を親に返すことはできない。

- **揮発してよい結果**：結果を使う処理（継続）を component として下に渡し、結果の Ref を引数にして起動する（bracket と同じ形）。
- **長く残す結果**：呼び出した側が置き場（プール）の Ref を引数で渡し、子はそこに書き込み、項目の ID をデータとして返す。取り出すときは、プールの Ref と ID を組にする。権限はプールの Ref にあり、ID はデータである（呼び出し側の region に確保するのと同じ規律）。

### 4.9 強制終了と孤児

- `revised`・`disposed` が一定時間（付録 A）届かないとき、本層は上の層にフック `onStuck(aid)` で知らせる。**自動で強制終了してはならない。**
- 強制終了は、上の層か運用者が明示的に行う。親は行を削除する（grant の失効は §4.2）。その後に届いた `activation/report` には 1201 を返す。
- 強制終了の後は、失効したリソースへの操作が起こりうる。受け取った側は、1103 を正常な経路として処理しなければならない。
- 子が自分で activation を終わらせてよいのは、親から JSON-RPC の 1201 が返ったときだけである。そのとき子は、L4 の 1〜4 を行う。
- 親が応答しないことを理由に、子が終了してはならない。親に届かない activation（孤児）は自動では片付けない。実装は、親に届かなくなってからの時間を運用者に示し、運用者が局所的に強制終了する手段を提供すべきである。

### 4.10 上の層への API

**親の側**

| 名前 | 呼ぶ側 | 内容 |
|---|---|---|
| `start(spawned_by, component, targs, args)` | 上の層 | 子の activation を起動し、`aid` を返す |
| `revise(aid, targs?, args)` | 上の層 | 子に新しい revision を送る |
| `dispose(aid)` | 上の層 | 子を dispose する |
| `terminate(aid)` | 上の層 | 子を強制終了する（§4.9） |
| `onChild(aid, event)` | 本層 | 子のことを知らせる。`event` は `revised(rev)`・`panic(error)`・`ended(reason)` のいずれか（`reason` は §4.4 の終了の理由） |
| `onStuck(aid)` | 本層 | §4.9 |

`start` と `revise` では、本層が次を行う。

1. 引数の中の Ref（`start` では `component` も）が、`spawned_by` の activation が引数として受け取った Ref か、自分のリソースの Ref であることを確かめる（L2）。満たさなければ、何も送らずにエラーを返す。
2. 引数の中の Ref ごとに、子を holder とする grant を用意する（R2、L1）。自分のリソースなら `issue` して `arg_grants` に記録する。他人のリソースなら `grant/derive` を送り、応答を `arg_derived` に `source` とともに記録する。前の revision で同じ参照に用意した grant は、そのまま使う。
3. 引数の中の Ref を用意した grant に置き換え、`activation/init` または `activation/revise` を outbox に積む（§4.3 の順序）。

derive の応答を待つ間の状態と、derive が失敗したときの扱いは、まだ決めていない（付録 B）。

**子の側**

| 名前 | 呼ぶ側 | 内容 |
|---|---|---|
| `onInit(aid, component, targs, args)` | 本層 | init を受理するときに呼ぶ（§4.3）。受け付けたら、上の層は計算を始める |
| `onRevise(aid, rev, targs, args)` | 本層 | revise を受理するときに呼ぶ（§4.3）。反映は L3 に従う |
| `commitRevision(aid, rev)` | 上の層 | L3 の 3 |
| `onDispose(aid)` | 本層 | L4 の 1 |
| `commitDispose(aid)` | 上の層 | L4 の 3 |
| `panic(aid, error)` | 上の層 | activation に `panic` を起こさせる（§4.6） |
| `onFault(aid, error)` | 本層 | §4.6 |

## 5. 保証

- **権限の安全性**：権限のない操作は通らない。issuer が使用時に自分の grant 表で判断するので、他のエンドポイントの状態に依存しない。activation の制御も、受信者が自分の表で判断する。
- **寿命の安全性**：強制終了を用いない限り、解放済みのリソースへの操作は起きない。R1 により、root grant 以外のすべての grant はある activation の引数として渡されたものであり、L3・L4 によって、そのスコープが閉じる前に使い終えられる。
- **完了通知の停止性**：局所 DAG の辺は「先に存在した activation から、その実行中に作られた activation へ」向き、大域的にも非循環である。L5 と合わせ、`revised`・`disposed` を待つ連鎖は有限で終わる（全エンドポイントがいずれ応答することが前提）。
- **リークの範囲**：derive したエンドポイントが戻らない場合、sub-grant は残りうる。sub-grant は `derived_from` によって派生元の寿命に縛られるので、権限の安全性は損なわれない。

## 6. 脅威モデル

**想定する攻撃者**：ホストをまたぐ経路のネットワーク上の攻撃者、自分の鍵を持つ悪意のあるエンドポイント、漏れた Ref を手にした第三者、不正な Ref を渡す親、DID の解決を悪用する相手（解決器を加えた場合）。

| 防ぐもの | 対策 |
|---|---|
| なりすまし | 送信者の鍵で署名したトークン（§1.4） |
| 改ざん、応答の偽造 | 輸送路の暗号化と、送り先の URL を `peers` か DID 文書から得ること（§1.3、§1.6） |
| 埋め込み鍵によるなりすまし、送信者の DID の偽装 | 鍵は `kid` の DID の文書から引き、`iss` がその DID であることを確かめる（§1.4、§1.5） |
| 別の宛先への流用 | `aud`（§1.5） |
| 同じリクエストの送り直し | 冪等性（§2） |
| 写し取ったトークンの長期の使用 | 有効期間の上限と `aud`（§1.4） |
| 漏れた Ref の使用 | grant を holder に紐づける（§3.4） |
| 偽った Ref による権限の取得 | 権限は grant 表だけで判断する（§3.4） |
| SSRF、解決の悪用 | 接続先のホストは `peers` の URL か `policy` の DID に限り、`service` は文書と同じオリジンに限る。`policy` にない DID は解決しない（§1.3、§1.5） |
| 許可していない相手への流出 | 送り先は `peers` と `policy` の DID に限る（`policy` の既定は空）。Ref は親からしか渡されない（§1.3、§3.2） |

**防がないもの**：機密性（輸送路に任せる。§1.6）、TLS を終端する中継機器・同じホストの中の平文の経路・`Authorization` を記録したログからトークンを得た者による有効期間の間のなりすまし（§1.4）、TLS を終端する中継機器による本文の改ざんと応答の偽造、秘密鍵の漏洩（did:key では古い ID を無効にできない。回復は、(1) 漏れた ID を holder とする grant を全 issuer で失効させ、(2) 漏れた ID が issuer である Ref を使っている側に使用をやめさせ、(3) 新しい鍵（新しい ID）で作り直して `peers` と grant を更新する）、設定ファイルの改ざん、正規の権限の範囲内での悪用、許可した送り先の範囲内での流出（言語の IFC で扱う）、covert channel、サービス妨害、時計の大きなずれ、トラフィック分析。

## 7. Katari Runtime への要求

- 言語に暗黙の権限を持たせない。外界とのやり取り（時刻・乱数を含む）は、すべて Ref を通して行う。
- Ref を偽造不能かつ不透明にする。Ref は引数と root grant からしか得られず、文字列に変換できない。Runtime は activation ごとに持つ Ref を管理し、それ以外への操作を拒否する。
- LLM のコンテキストに Ref そのものを入れない。
- activation ごとに計算資源の上限を課し、超えたら `panic` とする。
- 各 Ref について、issuer の DID と、受け取った経路を保持する（IFC のため）。
- `onFault` を受けた activation の計算は、ただちに止める。結果を待つ呼び出し（種別のメソッドなど）が型に現れないエラーで失敗した場合も、その activation の `panic` とする。
- init・revise の型引数と引数は、`onInit`・`onRevise` の中で、component のシグネチャに照らして検査する（§4.3）。
- Runtime の中の component の呼び出しも activation として扱う（内部と外部の component は同じ意味を持つ）。
- 自分が issuer である Ref への操作と、自分が提供する component の起動は、認証と通信を省いてローカルに処理してよい（意味は変えない）。

## 8. 外部プロトコルとの接続

Katari 以外のプロトコルとは、プロキシで接続する。外部のサービスとの境界は、できるだけ MCP に寄せる。プロキシは外部の資格情報を内部に保持し、Katari 側には絞った grant だけを公開する。`sink`・`blob` は `standard-kinds.md` の種別である。

| MCP | Katari |
|---|---|
| tool | component の起動。結果は引数の sink に `emit` する |
| resource の読み出し | `blob/fetch` |
| 購読 | component の起動（引数の sink に `emit`）。解除は dispose |
| task・キャンセル・状態 | activation・dispose・activation の状態 |

チャットサービスなどの外向きの操作は sink として、内向きのイベントは「見張る」component として公開する。外から届く webhook は、そのサービスの署名規約で検証しなければならない。外に webhook を送るときは、Standard Webhooks などの既存の署名規約に従う。

- **次に決めるもの**：derive の応答を待つ間の activation の状態と、derive が失敗したときの扱い（§4.10）。
- **慎重に決めるもの**：空の引数（`$pending`）。暗黙の capability（`context`）。内部の呼び出しも activation として扱う（§7）ので、言語が必要とするものはプロトコルに入れることになる。
- **保留**：init の応答で結果を直接返す最適化。自分が host する子に受け取った Ref を渡すときの derive の省略（実装で derive の回数と時間を測ってから判断する）。
- **外部とつなぐ段階**：鍵を更新でき漏洩から回復できる DID の方式（did:web、did:webvh、KERI 系）、did:web の解決器を加える時期と DID 文書の `service` の形式、`policy` の書き方（型を許すかなど）。
- **型と言語との境界**：IR の型と JSON Schema の対応表、Katari 以外のサーバーから component のシグネチャを取得する方法（呼ぶ側が知るための任意の情報。検査は component が行う）、型に現れるエラー（v0.1 の `throw[T]`。再起動で中断された外部呼び出しを含む）を handler の capability として標準ライブラリで提供する方法。
- **拡張**：プール（§4.8）の標準化、facet と caveat、署名の連鎖による委任（derive の往復を省く。revoke は省けない）、promise pipelining、root grant 単位の利用制限、WebSocket の binding。
- **運用**：`peers` の形式と鍵の生成の CLI、`katari:` スキームの IANA への暫定登録、エラーの説明の文書、MCP events への追従。

## 付録 C. `katari-protocol.md` で変えたことと根拠

`katari-protocol.md` は最終的なプロトコルだけを記述する。そこで変えた点と、その根拠をここに残す。

### 全体

- 状態の表（認証層の `self`・`resolved`、RPC 層の `outbox`・`seen_rpc`）を削り、守るべき性質だけを書いた。保存の形は相手から観測できない。また、表を「すべて永続化する」（§0.3）と結びつけると、次の `processing` のような誤りが生まれる。
- 「運用者に知らせる」の類を削った。運用の話であり、相手との取り決めではない。

### 認証層

- `peers` と `policy` は、運用者の設定（Peers、Policy）として残した。did:key の DID 文書は送り先を持たないので、did:key の送り先は設定でしか与えられない。
- 自衛の規則（接続先の制限、`serviceEndpoint` の同一オリジン、リダイレクトに従わない、Policy にない DID を解決しない）を「実装への要件」に分けた。相手からは観測できないが、Ref が URL を持たない設計（§3.2）は、どの実装もこれを守ることを前提にしている。
- **認証を、本文を包むエンベロープから、`Authorization: Bearer` のトークンに変えた**（本文の §1.4〜§1.6 も書き換えた）。本文と応答は普通の JSON-RPC になり、応答には署名しない。
  - 理由：エンベロープでは、リクエストのたびに署名が要り、本文も base64url になる。curl などで試せず、記録も読めず、他人が実装するときに JWS の検証と応答への署名が要る。MCP（OAuth の Bearer トークン）も AT Protocol も、本文は普通の JSON である。
  - 本文と応答への署名で防げる相手は、TLS を終端する中継機器だけである。署名鍵は応答するホストの上にあるので、ホストを乗っ取った攻撃者は鍵も得る。送り先の設定の誤りは、`aud` の不一致で見つかる。そのため、本文の完全性と応答の真正性は輸送路に任せ、ホストをまたぐ閉じたネットワークでも暗号化を MUST にした。以前この付録に書いた「応答の署名を残す」は、この点を見落としていた。
  - 手放したもの：トークンを写し取った者（TLS を終端する中継機器、`Authorization` を記録したログ）は、有効期間の間、送信者として別のリクエストを送れる。有効期間の上限と `aud` で範囲を狭める。AT Protocol と同じ線である。base64 による膨張（`blob/fetch` では二重）もなくなった。
  - 消えたもの：応答の署名と、応答の `iss` の確認。「署名付きの応答」と「署名のない拒否」の区別は、「JSON-RPC の応答」と「binding の層の拒否」の区別になった。
  - HTTP の認証の枠組みに乗るので、トークンの拒否は 401 と `WWW-Authenticate: Bearer`（RFC 6750）で返せる。以前の「`bad-signature` を 400 にする」は不要になった。
  - 本文が普通の JSON になったので、解釈できない JSON には JSON-RPC の -32700 を返す。
  - トークンを使い回せるようにし、`exp` を足して `jti` をやめた。ATP の `lxm` は採らない（§1.4 の根拠）。
- **DID をエンドポイントの ID とする理由は、本文の形とは独立しており、変わらない**。ID はリソースの URI・grant の holder・activation の親として長く残る状態に埋め込まれるので、場所（URL）から独立している必要がある。did:key なら、中央の登録所や CA なしに署名を確かめられ、相手ごとに秘密を配らずに済む（運用者が書くのは公開の情報だけで、各エンドポイントの秘密は自分の鍵一つである）。接続先は、持ち主か運用者が書いた場所からしか得ない（SSRF を防ぐ）。AT Protocol も、DID を ID にしたまま本文は普通の JSON である。
- `kid` の DID が `iss` と一致しないものは `malformed` とする。トークンだけで判定でき、どの受信者にとっても違反なので、`kid` の形式の誤りと同じ分類になる。鍵や署名の問題ではないので、`bad-signature` ではない。
- **RFC 9421（HTTP Message Signatures）＋ RFC 9530（`Content-Digest`）を採らない**。本文を JSON のまま、リクエストと応答に署名できるが、リクエストのたびに署名が要る点は変わらず、curl で試せないことは解決しない。加えて、(1) `@authority`・`@path` などの部品から署名の対象を組み立てるので、Host の付け替えやパスの接頭辞の除去を行う中継機器を挟むと検証に失敗する。(2) 署名の対象の組み立てと Structured Fields の解析を実装する必要があり、JWS ほど成熟したライブラリがない。

### RPC 層

- **「処理中」を永続化しない**。処理の途中で受信者が再起動したら、そのリクエストは処理していないものとして扱う。`processing` を永続化すると、落ちた後の再送に 1001 が返り続け、制御の経路では送信が終わらない。
- **1001 を受け取ったら、待ってから同じ `rpc.id` で再送する**。1001 は答えではなく、「答えがまだない」という知らせである。最初の処理が終わった後に結果を得る方法は、同じ `rpc.id` での再送だけである。設計記録 §2.2 の表の「送信者の対応」の列にあったが、本仕様にまとめるときに落ちていた。
- 終わりの応答を、応答の分類で定めた（1001・-32603・2001 は再送する。それ以外の JSON-RPC の応答で終わる）。§2.4 の「JSON-RPC の応答が返ったら送信をやめてよい」では、これらでも止まれてしまう。
- **リースを削った**。一つのエンドポイントは一つのプロセスで動かす（v0.1 の runtime も、`typescript/runtime/src/db/instance-lock.ts` の single-instance lock で同じ前提をとる）。複数のプロセスにする場合も、排他の取り方は実装が選ぶ。同じ `rpc.id` を同時に送っても、1001 と再送により結果は変わらないので、「同時に一本まで」は SHOULD に下げた。
- **チャネルを削った**。送信側の仕組みであり、受信側はそれに頼れない。必要な順序は、それを必要とする層が要件として書く。
  - Component：親は、init に終わりの応答を受け取るまで、同じ activation への revise・dispose を送らない。これで足りるのは、ほかの入れ替わりが受信側の規則で吸収されるためである。revise 同士の入れ替わりは、子が途中の revision を飛ばすこと（§0.2 の 3）と同じであり、親はすでにそれを扱う。dispose の後に届いた revise は、`disposing` 中なら無視され、終了後なら 1201 で終わる。
  - sink：同じ activation から同じ sink への `emit` を書いた順に届けることは、Runtime の約束として `standard-kinds.md` に書く。
- **経路（データ・制御）をやめた**。経路はメッセージに載らない送信者の再送の仕方であり、メソッドごとにも決まらない（`grant/revoke` は、寿命の規則で送るときだけ制御の経路だった）。経路には、相手に関わる性質が二つ混ざっていた。
  - 保持期間を過ぎても再送してよいか：受信者は保持期間を過ぎると処理済みの応答を忘れ、届いた再送を新しいリクエストとして処理する。害がないのは冪等なメソッドだけなので、RPC 層は「冪等でないメソッドは再送の期限でやめる」とし、冪等かどうかはメソッドを定める層が書く。
  - 送り続けるか：相手の進行がそれに頼る（親は子の報告を、子は親の dispose を待つ）。頼る層が求める。Component の章では、`activation/*` と寿命の規則による `grant/revoke` を、完了するまで送り続ける（再送しても変わらない拒否でもやめない）と書く。これらは冪等なので、RPC 層の規則と矛盾しない。
  - 二つは独立している。`blob/fetch` は冪等だが送り続ける必要はなく、`sink/emit`・`grant/derive` は冪等でない。
- 再送の間隔の上限を一つ（1 分）にした。経路ごとに分けていた値（データ 5 分、制御 1 分）は、経路をやめると根拠がなくなる。相手が回復した後に早く再開するほうを取った。
- エラーの `code` の表は、各層が自分の `code` を定める形にした。RPC 層は形式と範囲の割り当てだけを定める。

### capability 層

- **Ref から `cid`（内容のハッシュ）を削った**（本文の §3.2 と `standard-kinds-slop.md` の blob も書き換えた）。Ref は grant の URI だけを持つ。
  - `cid` で防げるのは、Ref を渡した者が見た内容と、issuer が後で返す内容が食い違う場合だけである。通信の途中の改ざんは輸送路で防ぐ。範囲を分けて取得する間の変化は、「blob の内容は変わらない」を issuer の義務にすれば起きない。
  - 残るのは、issuer が内容を差し替える場合である。内容を持つのは issuer なので、issuer を信頼しないなら、その blob はそもそも使えない。応答の署名をやめたときの「ホストの乗っ取りは防がない」と同じ線である。
  - `cid` は任意の欄だったので、受け取る側はあることを当てにできず、保証になっていなかった。
  - 手放したもの：内容を取得せずに同じ内容かを比べること、issuer をまたいだキャッシュと重複の排除。どちらも最適化であり、本仕様はこれらに頼らない。
  - Ref をオブジェクトのままにしたのは、後で欄を足せるようにするためである。
