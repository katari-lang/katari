## 0. 3 文で

```
1. component は React のコンポーネント。props と state から子（resource と子 component）を宣言し、消えた宣言は dispose される。
   dispose は React の unmount と違い、外部の resource を片付ける（terraform の destroy）
2. 各 component は 1 つの inbox と 1 本の loop（Kotlin の coroutine、actor）を持つ。loop だけが自分の state を書き、tool（async 関数）を await し、
   inbox から message を受ける。header の `<- Msg` が親から送れる inbox、`-> E` が自分の event。子の宣言末尾の `-> Tag` でその子の event を受ける
3. 宣言には住所（address）があり、terraform のように差分を plan / apply する。走っている loop の位置も住所を持ち、migration できる
```

通信の向きは 2 つだけ。**前向き（親 → 子）に state、後ろ向き（子 → 親）に event。** send できるのは自分が依存している（継続である）ノードへだけで、
inbox は run の後ろにあるので、run は「event を受けている相手」に send できない（相互参照は静的エラー）。

| 借りるもの | 出所 | ずれ |
|---|---|---|
| component、props、state、key、reconcile | React | state は `s <- v` で書く。unmount が destroy |
| loop、suspend 関数、構造化並行性、`finally` | Kotlin coroutines | scope の中で `launch` できない。並行するものは全て住所を持つ子 |
| 1 つの mailbox、loop だけが state を書く | actor（Erlang / Akka） | props も受ける。mailbox は durable |
| resource、address、plan / apply、moved | terraform | run（loop）がある |

## 1. component

### 1.1 宣言

```
component Name(params) [<- Msg] [-> E] {  <- Msg: 親から送れる inbox の型。-> E: 自分が出す event の型。どちらも省略可
  [inbox Msg]                            内部 inbox の型を明示する（省略時は配線の Tag から推論）
  [export] use x = M(args) [key k] [-> Tag]     子 / resource。x は M の出力。-> Tag で M の event を自分の inbox に Tag(e) として受ける
  [export] state s: T = init             書くのは §2 の run だけ
  when cond { … }                        cond が真の間だけ存在する宣言
  [export] use xs = for x in p key f(x) { … ; v }     要素ごとの宣言。式としては Map<Key, V>
  step name(args) { 逐次 }               run の手続き。state を書ける。値にならない
  run { … } [finally { … }]              1 つだけ。§2。`loop { … }` は `run { loop { … } }` の省略
}
tool T(params): R { 逐次 }               top-level の async 関数。§3
fn   f(params): R = 式                   純粋
```

- body は宣言の集合で順序を持たない。依存は自由変数で決まる。`x` を使う宣言は `x` が揃うまで保留される（terraform の依存と同じ）
- **出力は export の直積。** export が無ければ `Unit` で、`use d = Digest(…)` の継続は即座に現れる。無限に待つ出力（Void）は無い
- inbox は run と一緒に作られ、run の依存先が揃った後に生まれる。header に `<- Msg` を書けば親が `x <- m` で送れる。
  書かなければ内部用で、`-> Tag` で配線した子の event だけが入る（型は Tag から推論。`inbox Msg` で明示もできる）
- `-> Tag` で配線した宣言は inbox に依存する（inbox より後に作られる）。**run は `->` で配線した宣言を参照できない**（参照すると循環。静的エラー）。
  run が send できるのは矢印の無い宣言だけ
- 自分の event（header の `-> E`）は、親が `-> Tag` で受ける。`-> Tag` は親の inbox への入口（sink）を暗黙の引数として渡す配線で、値は動かない
- ある子と話す向きは 1 つ。send する子からは event を受けず、event を受ける子には send しない。反対向きの情報は state で渡す
  （send で下ろす子は結果を export state で上げ、run が `wait agent.reply` で読む。`->` で受ける子は入力を props で受ける）
- 宣言が消えると、その配下は依存の逆順に dispose される。これが cancel の唯一の形
- `use` の束縛名は address のために必ず付ける

### 1.2 address と key

```
address ::= (scope, key)* · label        scope = use の束縛名 / for の site。label = 束縛名
```

- address は同一性。reconcile の対応、state の引き継ぎ、外部に渡す id の元、冪等キー。引数は同一性に含まれない（`key` だけ）
- 依存（誰が誰を待つか、↑ の順序）は別の構造。`use a` を消しても `b` の address は変わらず keep
- `for x in p key f(x)` は要素ごとに別の住所。`use … key k` は同一性を上書きする。`key` の用途はそれだけ
- 改名は migration の `moved` で対応づける。label は body 内で一意。`_` は不可

### 1.3 環境

言語の中に可変値は無い。あるのは **環境の列** で、環境はある時点の全ての名前（props、state、宣言の出力）の値。全部 不変。

```
宣言        環境の関数（React の render）。環境が変われば宣言が再評価される
phase       run の中の 1 つの環境。開始時の props、state、resource の要素で完走する。await を跨いでも変わらない
tool call   body 全体が 1 つの phase。call 時の環境で完走する
束縛        phase の中では何でも名前を付けられる（`let c = ch` も可。同じ環境だから）
```

環境を越えられるものは 3 種類だけで、越境先で改めて名前が割り当てられる。

```
1. インスタンス（宣言と params）   identity で越え、次の phase では今の要素に解決される
2. state                          phase の中の書き込みは phase の終わりで次の環境に反映される（transaction）。phase の中で読む state は開始時の値
3. phase の出力                    `phase x = { …; return y }` の y。data だけ。resource は越えない
```

書かなければ sync 区間（await と await の間）が暗黙の phase。`phase` は複数の await を 1 つの環境に括る構文で、
tool は名前の付いた phase、`phase` は inline の tool。phase が握っている resource の古い要素は phase が終わるまで解放されない
（CI の runner が環境を離さないのと同じ。plan / trace に出る）。dangling は構造的に起きない。

- 0 / 1 の pool（state、props、宣言の出力）と、複数要素の pool（`for` の集合、外部の集合）。要素の差し替えは update（§1.5）、出入りは init / dispose
- `use x = M(args)` の継続は「`for x in M の出力の pool`」そのもので、要素が無ければ召喚されない
- props は pool のまま渡る。要素を子の同一性にしたければ `use conv = Conversation(ch, model) key ch.id` と書く
- 永続化（state、inbox、frame）は値か pool の address。address は直列化できるので、state や message に resource の参照が入ってもよい
- AI に見せる tool の引数は値である必要がある（schema）。`describe` の問題で、言語の規則ではない
- tool が resource を作る場合は、呼び出し側が置き場（drive、store）を渡し、tool はそこへ保存して id を返す。id は drive の同一性と組で有効

### 1.4 resource が使える場所

resource は値なのでどこにでも渡せる。違うのは export（時変の signal）をどこで読めるか。

```
宣言        resource を引数に渡す。export を読む（pool として反応する）
run         export を読む（区間ごとに今の値）。wait できる。tool を呼べる
tool        tool を呼ぶだけ。export は読めない（環境が固定なので意味が無い）。待ちたいなら葉（await gh.wait_merged(pr)）か run に出す
```

- 走行中の phase / tool call は開始時の環境で完走し、握っている要素はその間 解放されない。完走後、引数が変わっていれば新しい引数で呼び直される
- `atomic` は葉の宣言で、「dispose されても完走する」の意味だけ（決済）。update は次の phase、dispose は即時、が規則

run で pool を読むときの型: 無条件の宣言と props は `T`（要素が無い瞬間はその読みで区間が切れ、要素が来るまで待つ）、
`when` 配下の宣言は `Option<T>`、`for` と明示の pool は `Map<Key, T>`。`await pr.merged` は pr が Some になり field の条件を満たすまで待つ。

### 1.5 更新の伝播

0 / 1 の pool の要素には世代番号（gen）がある。要素が差し替わると `update` が依存の向きに流れ、各ノードは乗り換えてから
`updated(gen)` を返す。親は依存する全ノードが乗り換えるまで古い要素を解放しない。

```
親 → 子   update(id, args, gen) / 子 → 親   updated(id, gen) / failed(id, gen?, error)
```

| ノード | 乗り換え方 |
|---|---|
| Katari component | 宣言は再評価（依存先に update）。run は次の区間から新しい要素を読む。子の updated が揃ったら updated。Faulted な run は妨げない |
| `key` で要素を同一性にした子 | 旧要素の子を dispose、新要素の子を init、その後 updated |
| 外部 resource | `update` と宣言した引数なら、その場で乗り換える（新しい要素を作り、継続に update を流し、継続の updated を待って旧要素を閉じる）。それ以外の引数は作り直し |
| tool call（Katari / 外部） | 走行中の call は call 時の環境で完走し（phase）、握っている要素を解放しない。完走後、引数が変わっていれば新しい引数で呼び直される。tool は差し替えを観測しない |
| `atomic` な葉 | dispose されても完走する（決済）。それ以外は tool call と同じ |

- 連打: 要素列 `[(g₁, a), (g₂, b), (g₃, c)]`。消費者は最新の gen に跳んでよく、`updated(g)` はそれ以前を含意する。誰も見なかった要素は作られ次第 解放
- 失敗: 新しい要素の作成に失敗すれば旧要素のまま。ノードの `status` は `Faulted(UpdateFailed(e))`。drift を plan に出す。自動 retry しない
- plan / trace は pending な update（address、gen、待っている呼び出しと経過時間）を出す
- 継続（出力）を持つ外部 component が作り直されると、継続の宣言も召喚し直され、その state は消える（plan に出す）

例。`ch_id` が変わったとき:

```
component Bot(discord: Discord, model: Model, ch_id: Text) {
  use ch   = discord.channel(ch_id)                      ← ch_id の update。外部 component が新しい接続を作る（update）
  use msgs = discord.messages(ch) -> Received            ← ch の update。購読を張り直す（update）
  use conv = Conversation(ch, model)                     ← ch の update。配下に流す
  loop {
    let batch = receive all
    with typing = discord.typing(ch) {                   ← 走行中に差し替われば typing は作り直し
      await ch.send(await ai.infer_text(model, prompt(batch)))      ← send が atomic なら完走してから乗り換え
    }
  }
}
```

## 2. run

component につき 1 つの逐次コード。state を書く唯一の場所。宣言が消えれば cancel される（構造化並行性）。

### 2.1 文

```
run {
  let m  = receive                         inbox の次の 1 件
  let ms = receive all                     溜まっている全件（1 件以上になるまで待つ）
  let t  = receive Tick(t) if t > due      条件に合う最初の 1 件。合わないものは順序のまま残る（Erlang の selective receive）
  match receive A(x) | B(y) { … }          A か B だけを待つ（複数節）
  emit e                                   自分の event を出す（header の -> E。親の inbox へ）
  c <- m                                   依存している子 c の inbox へ送る。c は矢印の無い宣言で、`<- Msg` を持つこと
  let x = await T(a)                       tool を呼ぶ。Fault は伝播。`await try T(a)` は Outcome
  wait sig                                 pool を待つ。Option なら Some を待って T を返す、Bool なら真を待つ
  s <- v                                   state を書く
  phase x = { …; return y }                1 つの環境で完走するブロック。出力 y は data だけ。書かなければ sync 区間が暗黙の phase
  let x = 式                               今の環境の値に名前を付ける（resource も可）。phase を越えるのは phase の出力だけ
  var v = 式                               phase の中の局所可変。phase を越えて持ち回るなら return する。loop 全体で持つなら state
  with r = M(args) { … }                   ブロックの間だけ存在する resource
  let (a, b) = await par(T(a), U(b)) / await par(xs, key = f) { … } / await race(T(a), U(b))
  name: await T(a)                         束縛しない await に名前を付ける（migration と plan が参照する）
  loop { … } / for x in xs { … } / break / match / if / try catch throw
} finally { … }                            完走・Fault・cancel のどれでも走る。参照している宣言はまだ生きている
```

- `let x = await …` の label は x。名前の無い await は `name:` を前置する。付けなければ `tool名 · 出現番号`（plan が表示する）
- `wait sig` は `for await v in sig { if ready(v) { break v } }` の省略。state が条件を満たすまで待つためのもので、通知を待つ用途には使わない（それは event）。
  phase の境界で環境が進むので、`wait` は phase の外（暗黙 phase の境界）で待つ
- 並行は `par`（全部待つ）、`race`（tool どうし。負けは dispose し、その ↑ を待ってから戻る）。`launch` は無い。並列は子 component
- lambda は純粋な式の中だけ（await を含まず、state / inbox に保存しない）
- selective receive で残り続ける message は trace に mailbox 長として出る。溜めたくなければ `receive all` で引き取って自分で振り分ける

### 2.2 開始、commit、終了

```
開始     run が参照する無条件の宣言の出力が全て揃ってから。参照しない宣言は待たない（Unit の子は即座に揃う）
区間     resume から次の await までが 1 transition。区間内の書き込みは即座に自分から見え、await 境界でまとめて commit → render
順序     runtime は全 component の transition を直列化する。1 つの run は program order、1 つの inbox は FIFO
終了     run は参照している宣言より先に cancel される（finally の中で ch をまだ使える）
```

- 同じ区間で同じ state に 2 回書けば後勝ち。`s <- v; await …` は「v が見えてから await」
- `wait sig` の sig が自分の state だけに依存するなら静的エラー（永遠に待つ）

### 2.3 run の終わり

```
全 component に暗黙の export  status: Running | Done | Faulted(Fault)
```

- `break` や完走で run が終われば Done。宣言は残り、state はそのまま。再び走らせるには `key` を変える
- `state x: T = t` の `t` は init 時に 1 回だけ評価する。その後 `t` が変わっても x は変わらない
- 捕まえなかった Fault は run を終え、Faulted になる。黙って止まらない。親は `when child.status is Faulted(f)` や `wait child.status` で見る
- `finally` は cancel でも走る。親の ↑ は finally の完了を待つ。finally の中の await は plan / trace に出る

### 2.4 変化を待つ

```
for await v in sig { … }                 sig の現在値で body を走らせ、値が変わるたびに body を cancel して走らせ直す（collectLatest）
```

導出データはこれで書く。stdlib の `derived`:

```
component derived(f: Tool<A, R>, args: A) {
  export state value: Option<R> = None
  run { for await a in args { value <- Some(await f(a)) } }      args が変わるたびに前の call を cancel して呼び直す
}
use users = derived(fetchUsers, groupId)        users.value : Option<List<User>>。再起動後は呼び直さず value を復元
```

`use x = derive T(args)` はこの糖衣。

## 3. tool

tool は event を 1 回出す component で、`await` はその event を待つ糖衣。意味論の項目ではない。
tool の中に時変値は無い。引数は call 時の環境の値で、data も resource も不変。走行中の call は完走し、差し替えは次の call から（§1.3）。

```
tool T(params): R { body }
  ≡  component T(params) -> Done(Outcome<R>) { run { emit Done(try { Ok(body) } catch f { Fault(f) }) } }

let x = await T(a)
  ≡  frame の下に use t = T(a) -> Done を宣言し、Done(o) を待つ。o が Ok なら x、Fault なら伝播（`await try` は o をそのまま）
Outcome<R> = Ok(R) | Fault(Failed(Error) | Interrupted)
```

- 親の state を書けないこと、cancel が dispose であることは「宣言だから」。環境が call 時に固定されるのは phase の性質
- `atomic` は葉の宣言で、dispose されても完走する（決済）。Katari の tool には要らない
- 綴りは `tool T(args): R { … }`。結果は型注釈で書き、`->` は event に使う
- ワンショットの仕事（1 つの goal の遂行）は tool。常駐の仕事（goal が次々届く）は component で、goal は event
- `race` / `par` は複数の子を frame の下に宣言して event を待つ。負けは dispose
- frame の子（await で宣言）の event は frame に直接届き、run を resume する。body の子（`->` で宣言）の event は inbox に届く。区別はこれだけ
- 外部の tool（http、model、human.ask）も同じ。引数ごとの反応（§1.5）に従い、cancel は dispose
- tool 値 = 定義に引数を与えたもの（`Search(kb, _)`）。式。与えた pool と値を持ち、環境は捕捉しない。宣言の中では再評価される
- AI に渡す tool の schema は残りの params（名前付き、値）と結果型から導出する。`fn` も Tools に入れられる（即答）
- 外部が Katari の tool 値を呼ぶ（mcp.serve、AI の即答）とき、runtime は tool 値を宣言したノードの scope で走らせる。address は `srv·(call, id)`。宣言の dispose で cascade
- component の中の `step name(args) { … }` は別物で、run の手続き（呼んだ run の区間として inline に走り、state を書ける。値にはならない）

## 4. inbox と event

component の通信は inbox（受け口）と event（出し口）の 2 つだけ。

```
component X(…) <- Msg   親が x <- m で送れる inbox。無ければ内部用で、型は配線の Tag から推論（inbox Msg で明示もできる）
component X(…) -> E     自分が出す event の型。親が use x = … -> Tag で受け、inbox に Tag(e) として入る
```

- inbox は durable。未消費の message は Katari が永続化する。容量は既定で無制限、`inbox Msg capacity n` で制限（emit が suspend）。
  外部 event 源には ack の遅延で伝える（背圧）
- 入る経路は 2 つ: 自分の子の event（`-> Tag` で包まれる。Tag は自分が選ぶ）と、自分に依存する run からの `x <- m`（m は `<- Msg` の値）。
  どちらも書いた側が型を知っているので、偶然の型一致で混ざらない
- header に `<- Msg` の無い component への `x <- m` は型エラー
- 子 → 親は `-> Tag` の 1 辺ずつ。孫から祖父へは子が `emit` で転送する。inbox の send 側を値として下に配る形は無い
- 外部 event 源（`discord.messages(ch)`）は event を出す外部 component で、`-> Tag` で受ける。protocol の `event(id, value)` は runtime が inbox に積んで
  永続化してから ack し、host は ack を見て cursor を進める。dedup は外部 component が message id で行う
- 外部 component にも inbox（`<- Msg`）と tool（往復）がある。`ch.send(text)` は結果を返す tool

## 5. 外部 component と protocol

```
親 → 子   init(id, args, cont) / update(id, args, gen) / updated(cont, gen) / dispose(id)
子 → 親   init(cont, x) / update(cont, x', gen) / updated(id, gen) / failed(id, gen?, error) / event(id, value) / disposed(id)
```

- 外部 component も「出力を出して生き続ける」か「event を出し続ける」か「event を 1 回出して終わる（tool）」のどれか。protocol は同じ
- update は 2 段階（§1.5）。host が継続に update を流した場合、runtime は継続の配下が乗り換えた時点で `updated(cont, gen)` を返す。
  args の中の pool は、host には参照先の現在の要素（出力の値の部分と不透明な id）として届く
- id は runtime が振る不透明値。address ↔ id の対応を runtime が持つ。migration / reset / args 変化 / moved で id は変わらない。葉は id を冪等キーにする
- 全メッセージに id ごとの連番、ack まで再送（両方向）。同じ id では disposed を待ってから init。宣言がもう無い id からの到着は無視
- 静的宣言（`external pkg.name(a: T [update], …) [<- Msg] [-> E] [: R] { export …; atomic; on restart retry | interrupt; on dispose delete | detach }`）:
  `update` は in-place で乗り換えられる引数（resource のみ）、`atomic` は始まったら最後まで走る（作り直しも中断もされない）、
  `on restart` は開始済み未完了の呼び出しを復帰時にどうするか（どちらも結果を送る）。fake にも同じ宣言を要求する
- JS は隔離プロセス。永続化と復帰は id をキーに自分で行う。atomic 性は葉の 1 回の呼び出しの中だけ。Katari は at-least-once で、address が冪等キー
- Katari で書く末端 component は `run { 確保 } finally { 解放 }` の対（useEffect と cleanup）。要るのは `atomic` だけ

## 6. 永続化と再起動

```
SoT : Defs（版）
      address ↦ state
      address ↦ frame（run の位置 = label、locals、保持している子ノードの address 集合）
      address ↦ inbox の未消費 message と消費カーソル
      address ↦ 継続の入力（外部の出力 x）と要素列 [(gen, 要素)]
      依存辺 ↦ 消費者の gen
      id ↦ 送信ログ（連番、ack、failed）
導出 : 宣言木、依存 DAG
```

```
1  root から再 render。state と継続の入力をはめ込む
2  各 run の frame を復元。frame が保持する子（tool call、ブロックの resource）は宣言として再現される
3  宣言集合と送信ログを比べる: init 済み ack 済み → 何もしない。未 ack → 再送。宣言に無いのに init 済み → dispose
4  inbox を復元。receive で待っていた run は次の transition で resume
5  外部は自分で復帰し、未 ack を (id, 連番) で除去する
```

receive の pop と区間の実行と commit は 1 transition なので、途中で落ちれば pop ごと巻き戻る。Katari 内の配送は exactly-once。

## 7. patch

```
不変条件: 木全体は常に 1 つの版。apply は 1 transition として原子的
```

| ノード | 互換の判定 | 非互換のとき |
|---|---|---|
| state | 型が互換 | migration か reset（単位は body の state と run の位置を合わせた 1 塊） |
| run の frame | 新定義に同じ label があり locals の型が互換 | migration（`at label { … } => label { … }`。反復は `at got · n`）か最初から |
| inbox | message の型が互換 | migration（`inbox addr { old => new }` か `drop`）。無ければ BLOCKED |
| 完了した run（Done） | — | 再実行しない |

- 挿入した await は走行中の run では走らない（通過済みの位置）。plan が必ず出す
- reset 後の render で生じる init / dispose、`atomic` の作り直しのブロック、「以前 init された id」、pending な update、migration で dispose される子を plan が出す
- migration は apply に渡す一回限りのプログラム。実在する状態に対してだけ定義されていればよい。apply 時に再検査

```
migration {
  Checkout state { old => … }
  Checkout run at charge { … } => charge { … }
  Bot inbox { old => { old with thread: none } }
  moved Support.Triage[*] => Support.Ticket[*]
}
```

## 8. capability と動的 attach

- 「この node の下で何が許可されているか」= 渡された pool。record は幅の部分型で、子は宣言した型の field しか参照できない。
  ambient authority は無く、全ての外部 component は provider を要求する。減衰（`with_budget`、scoped channel）は外部 component が提供し、失効は宣言の消滅
- 動的 attach: `validate(src, env, I): Result`（tool）、`use d = link(src, env, I, migration = m)`（失敗しない）、`use app = d(args)`。
  名前は env の module、権限は args の pool。`I` は静的な型で AI には `describe(I)`。`reflect` / `plan` / `validate_migration` は tool
- AI が組み替える閉ループは run の中の逐次コードで書ける。label を変えれば plan に reset が出る
- v0.1 の effect / coeffect は持たない。失われるのは推論だけ

## 9. 指針

```
前向きは props、後ろ向きは event。state は状態の定義と伝播で、通知には使わない
親が逐次で結果を待つなら tool。親が宣言で寿命を決め結果に反応するなら子 component + event。外から見たい進捗は export state
親が子に命令するときだけ <- Msg。agent は middleware（下の event を貯め、上へ結果を投げる）で、命令は受けない
state の書き手は run だけ。遷移は run を上から読めば分かる
可変値は無い。環境の列があり、越えるのは instance・state・phase の出力（data）だけ。phase と tool は 1 つの環境で完走し、差し替えは次の phase から。dispose だけが即時
並列は子 component。run の中の並行は par / race だけ
複数の源は 1 つの inbox に -> Tag で集め、receive で分岐。loop は 1 つ
loop が await で塞がる間は inbox を受けられない。command を受けながら長い処理をするなら、長い処理を子に出す
人間を待つ処理は await human.ask。取り下げは宣言の消滅。待ちを外から見せたければ state に出す
履歴・監査ログは store（run の中で await store.append）。state には構造が依存する小さな値だけ
tool が作る resource（画像など）は drive に保存して id を返す
```

### B2. ユーザーごとに並列、掃除つき

```
component Desk(discord: Discord, model: Model, clock: Clock) {
  use ch    = discord.channel("help")
  use seen  = discord.messages(ch) -> Seen
  use ticks = time.every(clock, 1.day) -> Tick
  state users: Map<UserId, Timestamp> = {}
  use convs = for (u, _) in users key u { Conversation(u, ch, model) }
  loop {
    match receive {
      Seen(m) => users <- users.insert(m.author, m.at)
      Tick(t) => for (u, last) in users { if t - last > 30.days { users <- users.remove(u) } }
    }
  }
}

component Conversation(u: UserId, ch: Channel, model: Model) {
  use mine = discord.messages(ch, author = u) -> Received
  state history: List<Msg> = []
  loop {
    history <- history ++ receive all
    let answer = await ai.infer_text(model, prompt(history))
    history <- history ++ [assistant(answer)]
    await ch.send(answer)
  }
}
```

### B3. 承認と timeout、取り下げ時の後始末

```
component Request(req: Req, human: Human, exec: Executor, clock: Clock) {
  export state decision: Pending | Approved | Rejected | TimedOut = Pending
  run {
    match await race(human.ask(req, options = [Approve, Reject]), clock.after(3.days)) {
      Left(Approve) => { decision <- Approved; await exec.run(req) }
      Left(Reject)  => decision <- Rejected
      Right(_)      => decision <- TimedOut
    }
  } finally {
    if decision is Pending { await human.notify(req.author, "withdrawn") }
  }
}
```

### B5. 実装 → PR → レビュー → マージ → デプロイ

```
component Feature(spec: Spec, gh: GitHub, model: Model, deploy: Deployer) {
  use branch = gh.branch(spec.repo, name = spec.slug)
  state phase: Implementing | Reviewing | Merged | Deployed = Implementing
  state feedback: List<Change> = []
  when phase is Reviewing { use pr = gh.pr(branch, title = spec.title) }
  run {
    loop {
      impl: await Implement(model, spec, feedback, branch)
      phase <- Reviewing
      match await Review(model, wait pr) {
        Approve    => { wait pr.merged; phase <- Merged; break }
        Changes(c) => feedback <- feedback ++ [c]
      }
    }
    deployed: await deploy.run(branch.sha)
    phase <- Deployed
  }
}
```

### B6. agent と orchestrator

```
tool Turn(model: Model, history: List<Msg>, tools: Tools): Text {
  var h = history
  loop {
    match await ai.infer(model, h, tools) {
      Say(t)      => return t
      Call(calls) => h = h ++ [assistant(calls)] ++ tool_results(calls, await par(calls, key = c.id) { c => tools[c.name](c.args) })
    }
  }
}

component Worker(model: Model, tools: Tools, task: Task) -> Done(TaskId, Text) {
  run { emit Done(task.id, await Turn(model, [user(task.prompt)], tools)) }
}

component Orchestrator(model: Model, tools: Tools, goal: Text) {
  export state results: Map<TaskId, Text> = {}
  state tasks: List<Task> = []
  use workers = for t in tasks key t.id { Worker(model, tools, t) -> Done }
  run {
    tasks <- await ai.infer_json(model, planning_prompt(goal), schema = List<Task>)
    loop { let Done(id, r) = receive; results <- results.insert(id, r) }
  }
}
```

run は `workers`（`->` で配線）を参照していない。task は props で下り、結果は event で上がる。

### B7. 動的 attach と AI の組み替え

```
component Plastic(spec: Text, env: Env, model: Model, ops: Human, args: I) {
  state cur: Option<(Text, Text)> = None
  when cur is Some((src, m)) { use d = link(src, env, I, migration = m); use app = d(args) }
  loop {
    let current = if cur is None then None else Some(wait d)
    let p = await Propose(model, spec, describe(I), env, current)
    if await ops.ask("apply?", p.diff) == Approve { cur <- Some((p.src, p.migration)) }
    for await _ in spec { break }
  }
}
```

## 第 3 版からの変更

- component は 1 つの inbox（header の `<- Msg`、内部用なら推論）と 1 つの出し口（header の `-> E`）を持つ。`-> Tag` は子の event を自分の inbox に流す配線。
  `channel<T>()`、`export send`、`to:`、`select`、`close` を廃止。`emit` と `x.send`（依存先へだけ）を追加。
  inbox は run と一緒に作られ、run は `=>` で配線した宣言を参照できない（循環）。1 つの子と話す向きは 1 つ
- 出力は export の直積。export が無ければ `Unit`（Void は無い）
- 参照と値の区別を言語から消した。名前は全て pool。`phase`、handle の let の規則、`Data / handle` を廃止
- 外部 resource は in-place で乗り換えられる引数を `update` と宣言する。`atomic`（始まったら最後まで走る）が `replace: forbidden` / `interruptible` / `finish` を統合
- update は 2 段階（gen、updated、failed）。create-first は `update` の中にだけある
- run の開始は参照する宣言が揃ってから、終了は参照する宣言より先
- 「kind」という語を廃止し「外部 component」に
- tool は event を 1 回出す component、`await` はその event を待つ糖衣、と定義した。frame の子の event は frame に、body の子の event は inbox に届く
- 表層構文を `2026-10-03-syntax.md` で決め直した（header の矢印、`-> Tag`、`x <- m`、`receive` / `wait` / `await`、`with`、`step`、`name:` ラベル）
