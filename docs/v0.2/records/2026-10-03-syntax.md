`syntax-requirements.md` の要件に対して `syntax-proposals/` の 4 案を比較し、ここで 1 つに決める。意味論は `2026-10-02-spec.md`（第 4 版）のまま。

## 1. 判断

| 論点 | 採ったもの | 理由 |
|---|---|---|
| inbox の公開と event 型 | header の矢印 `component X(params) <- Msg -> E`（HCL 風・最小） | `export receives` が消える。`<-` = 親が送れる、`->` = 自分が出す、が 1 行で読める |
| 内部 inbox の型 | 配線の Tag から推論。明示したければ body に `inbox Msg`（最小） | 配線を足すたびに型を直さない |
| 子の event の配線 | 宣言末尾の `-> Tag`（HCL 風・Kotlin 風・最小） | header の `->` と同じ記号で「x が Tag として自分に出す」 |
| send | run の `child <- msg`（最小） | header の `<-` と同じ記号。「配線した子（`->` 付き）には `<-` できない」が矢印の向きで読める |
| state の書き込み | `s <- v` | send と同じ「流し込む」記号。body の `=` は束縛、run の `<-` は書き込み、で `=` の多義が消える |
| 子 / resource の宣言 | `use x = M(args)`（既存） | terraform の文字列ラベル（HCL 風）は Katari の密度では重い。`val`（Kotlin 風）は state との対で `var` を呼び込む |
| state | `state s: T = init`（既存） | React の語。`var` より役割が明確 |
| 待つもの | `await`（tool）、`receive` / `receive all` / `receive Pat if c`（inbox）、`wait expr`（pool）、`for await v in sig`（collectLatest）（保守的改良） | 各行が何を待つか keyword で分かる |
| run 内の資源 | `with r = M(args) { … }`（保守的改良） | body の `use`（宣言の寿命）と区別する |
| await 位置の名前 | `name: await …`（HCL 風。JS のラベル文） | `let x = await` は x が名前。束縛しない await に付ける |
| 条件付き宣言 / 集合 | `when cond { … }` / `use xs = for x in p key f(x) { …; v }`（既存） | run の `if` / `for` と字面を分ける |
| 手続き | component 内の `step name(args) { … }`（HCL 風） | top-level の `tool` と位置で意味が変わるのを避ける |
| tool / fn | `tool T(args): R { … }`、`fn f(args): R = e` | `->` を event に譲り、結果は型注釈 |
| tool 値 | `Search(kb, _)` | 名前付き引数の部分適用は省略可能引数と見分けがつかない |
| 外部 component | `external pkg.name(a: T [update], …) -> E { export …; atomic; … }`（保守的改良 + HCL 風） | in-place 可能な引数だけ `update`。`atomic` が作り直し禁止・中断禁止・完走を 1 語で |
| migration | `migration { X state { … }; X run at l { … } => l { … }; X inbox { … }; moved a => b }`（保守的改良） | 1 塊で読める |

退けたもの: 文字列ラベル（重い）、`val` / `var`（state の語を失う）、`async fn`（位置で意味が変わる）、`emits Tag`（矢印の方が header と揃う）、`parent <- e`（`emit` の方が明確）、`await { expr }`（型で意味が変わる）。

## 2. 3 文で

```
1. component は props と state から宣言（use / state / when / for）を組み立てる。React のように reconcile され、消えた宣言は dispose される
2. header の `<- Msg` が親から送れる inbox、`-> E` が自分の event。子の宣言末尾の `-> Tag` でその子の event を自分の inbox に流す（その子には送れない）。
   矢印の無い子には run から `child <- msg` で送れる
3. `run`（`loop`）だけが逐次。`await` は tool、`receive` は inbox、`wait` は pool を待ち、`s <- v` で state を書く
```

keyword: `component` `inbox` `use` `state` `when` `for` `key` `export` `run` `loop` `phase` `let` `var` `await` `receive` `wait` `emit` `with` `par` `race` `finally` `step` `tool` `fn` `external` `migration` `moved`。
記号: `<-`（流し込む: header の公開 inbox、send、state の書き込み）、`->`（出す: header の event、配線）、`name:`（await 位置の名前）、`_`（tool 値の空き引数）。

## 3. 文法

```
component Name(params) [<- Msg] [-> E] {
  [inbox Msg]                              内部 inbox の型を明示する（省略時は配線の Tag から推論）
  [export] use x = M(args) [key k] [-> Tag]
  [export] state s: T = init
  when cond { 宣言… }
  [export] use xs = for x in p key f(x) { 宣言…; v }
  step name(args) { 逐次 }                 run の手続き。state を書ける。値にならない
  run { 逐次 } [finally { 逐次 }]           1 つ。`loop { … }` は `run { loop { … } }`
}

tool T(args): R { 逐次 }                           1 つの環境で完走する phase。引数は call 時の値で不変。差し替えは次の call から
fn   f(args): R = 式

external pkg.name(a: T [update], …) [<- Msg] [-> E] [: R] {
  export x: T
  atomic                                   dispose されても完走する（決済）
  on restart retry | interrupt
  on dispose delete | detach
}
```

run の文:

```
let x = await T(a)                   tool。Fault は伝播。`await try T(a)` で Outcome
let m = receive                      inbox の次の 1 件
let ms = receive all                 溜まっている全件（1 件以上になるまで待つ）
let t = receive Tick(t) if t > due   条件に合う最初の 1 件。合わないものは残る
match receive A(x) | B(y) { … }      A か B だけを待つ（複数節）。合わないものは残る
wait pr / wait pr.merged             pool が揃う / 真になるまで
for await v in sig { … }             sig が変わるたびに body をやり直す
emit e                               自分の event（header の -> E）
child <- m                           矢印の無い子の inbox へ（子が <- Msg を持つこと）
s <- v                               state を書く
phase x = { …; return y }            1 つの環境で完走するブロック。出力 y は data だけ。書かなければ sync 区間が暗黙の phase
let x = 式                           今の環境の値に名前を付ける（resource も可）。phase を越えるのは phase の出力だけ
var v = 式                           phase の中の局所可変。越えて持ち回るなら return。loop 全体で持つなら state
with r = M(args) { … }               ブロックの間だけの resource
let (a, b) = await par(T(x), U(y)) / await par(xs, key = f) { … } / await race(T(x), U(y))
name: await T(a)                     束縛しない await に名前を付ける
loop / for x in xs / break / match / if / try catch throw
```

## 4. 例

### 1. echo

```
component Echo(discord: Discord) {
  use ch   = discord.channel("general")
  use msgs = discord.messages(ch) -> Received
  loop { let Received(m) = receive; await ch.send("echo: " ++ m.text) }
}
```

### 2. ターン制

```
component Bot(discord: Discord, model: Model) {
  use ch   = discord.channel("general")
  use msgs = discord.messages(ch) -> Received
  loop {
    let batch = receive all
    phase _ = {                                                  1 ターンは 1 つの環境（model、ch が途中で変わらない）
      with typing = discord.typing(ch) { await ch.send(await ai.infer_text(model, prompt(batch))) }
    }
  }
}
```

### 3. ユーザーごとの常駐、30 日で掃除

```
component Desk(discord: Discord, model: Model, clock: Clock) {
  use ch    = discord.channel("help")
  use seen  = discord.messages(ch) -> Seen
  use ticks = time.every(clock, 1.day) -> Tick
  state users: Map<UserId, Timestamp> = {}
  use convs = for (u, _) in users key u { Conversation(u, ch, model) }
  loop {
    match receive {
      Seen(m) => users <- users.insert(m.author, m.at)
      Tick(t) => for (u, last) in users { if t - last > 30.days { users <- users.remove(u) } }
    }
  }
}

component Conversation(u: UserId, ch: Channel, model: Model) {
  use mine = discord.messages(ch, author = u) -> Received
  state history: List<Msg> = []
  loop {
    history <- history ++ receive all
    let answer = await ai.infer_text(model, prompt(history))
    history <- history ++ [assistant(answer)]
    await ch.send(answer)
  }
}
```

### 4. 承認、timeout、取り下げ

```
component Request(req: Req, human: Human, exec: Executor, clock: Clock) {
  export state decision: Pending | Approved | Rejected | TimedOut = Pending
  run {
    match await race(human.ask(req, options = [Approve, Reject]), clock.after(3.days)) {
      Left(Approve) => { decision <- Approved; await exec.run(req) }
      Left(Reject)  => decision <- Rejected
      Right(_)      => decision <- TimedOut
    }
  } finally {
    if decision is Pending { await human.notify(req.author, "withdrawn") }
  }
}
```

### 5. PR パイプライン

```
component Feature(spec: Spec, gh: GitHub, model: Model, deploy: Deployer) {
  use branch = gh.branch(spec.repo, name = spec.slug)
  state phase: Implementing | Reviewing | Merged | Deployed = Implementing
  state feedback: List<Change> = []
  when phase is Reviewing { use pr = gh.pr(branch, title = spec.title) }
  run {
    loop {
      impl: await Implement(model, spec, feedback, branch)
      phase <- Reviewing
      match await Review(model, wait pr) {
        Approve    => { wait pr.merged; phase <- Merged; break }
        Changes(c) => feedback <- feedback ++ [c]
      }
    }
    deployed: await deploy.run(branch.sha)
    phase <- Deployed
  }
}
```

### 6. orchestrator

```
tool Turn(model: Model, history: List<Msg>, tools: Tools): Text {
  var h = history                      引数は call 時の値。ターンの間は自分のもの
  loop {
    match await ai.infer(model, h, tools) {
      Say(t)      => return t
      Call(calls) => h = h ++ [assistant(calls)] ++ tool_results(calls, await par(calls, key = c.id) { c => tools[c.name](c.args) })
    }
  }
}

component Worker(model: Model, tools: Tools, task: Task) -> Done(TaskId, Text) {
  run { emit Done(task.id, await Turn(model, [user(task.prompt)], tools)) }
}

component Orchestrator(model: Model, tools: Tools, goal: Text) {
  export state results: Map<TaskId, Text> = {}
  state tasks: List<Task> = []
  use workers = for t in tasks key t.id { Worker(model, tools, t) -> Done }
  run {
    tasks <- await ai.infer_json(model, planning_prompt(goal), schema = List<Task>)
    loop { let Done(id, r) = receive; results <- results.insert(id, r) }
  }
}
```

`for` の中の配線は `Done(key, event)` の形で届く。

### 7. agent は middleware（下から event を貯め、上へ結果を投げる）

```
component Agent(model: Model, tools: Tools, discord: Discord, channels: List<Channel>) -> Reply(ChannelId, Text) {
  use subs = for c in channels key c.id { discord.messages(c) -> Received(c.id) }
  state history: Map<ChannelId, List<Msg>> = {}
  loop {
    let Received(c, m) = receive
    history <- history.push(c, user(m.text))
    let t = await Turn(model, history[c], tools)
    history <- history.push(c, assistant(t))
    emit Reply(c, t)
  }
}

component Desk(discord: Discord, model: Model, kb: Knowledge) {
  use chs   = for n in ["help", "general"] key n { discord.channel(n) }
  use agent = Agent(model, { search = Search(kb, _) }, discord, values(chs)) -> Reply
  loop { let Reply(c, t) = receive; await chs[c].send(t) }
}
```

親は agent に send しない。agent は props で渡された channel を自分で購読し、結果を event で上げる。
`<- Msg` を使うのは親が子に命令する場面だけ。

## 5. 書き方の慣習

```
親が逐次で結果を待って次に進む        tool を await する。cancel は親の run の cancel
親が宣言で寿命を決め、結果に反応する    子 component。結果は -> Event で上げる
子が読む設定・データ・handle           props
外から見たい進捗・状態                 export state。通知には使わない（state は状態の定義と伝播、event は出来事）
親が子に命令する                      <- Msg。agent のような middleware には要らない
複数の源                              1 つの inbox に -> Tag で集め、receive で分岐。loop は 1 つ。並列は子 component
```

- 可変値は無い。環境の列があり、越えるのは instance（宣言名。今の要素に解決）・state・phase の出力（data）だけ。`state x: T = t` の `t` は init 時に 1 回だけ評価する
- phase と tool は 1 つの環境で完走する。親の再設定は次の phase から。即時に止めたければ dispose（宣言の消滅）
- 複数の await を 1 つの環境で扱いたい区間（1 ターン）は `phase` で括る。括らなければ await ごとに環境が進む
- ワンショットの仕事は tool、常駐の仕事は component
- tool の `return v` は `emit Done(v); break` と同じ意味。tool body に `emit` は無く、run に `return` は無い

## 6. 残した曖昧さ

- `->` が header（自分の event）と宣言末尾（配線）の 2 か所に出る。どちらも「出す」で一貫
- `<-` が header（公開 inbox）、send、state の書き込みの 3 か所。どれも「流し込む」で一貫
- `wait` は「state が条件を満たすまで」にだけ使う。変化の通知を待つ用途には使わない（それは event）
