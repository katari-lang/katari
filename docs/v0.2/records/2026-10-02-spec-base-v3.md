> この文書は第 3 版の評価の入力として凍結した。現行は `2026-10-02-spec.md`。

第 2 版（`2026-10-01-spec.md`）までの議論で、tool を component に統一する試み（Ready / 継続 / `=> Tag` / method）は
初見で説明できないと判断した。本版は **発明を component system（寿命・address・reconcile・patch）だけに限り、
それ以外は既存のパラダイムを名前ごと借りる**。これは usage 評価（`usage-v3/`）の入力で、評価後に改訂する。

| 借りるもの | 出所 | Katari での姿 |
|---|---|---|
| component、props、state、key、reconcile | React | 宣言は state と props の純粋関数。state の書き込みは render の外 |
| actor | Erlang / Akka | component は 1 つの loop と mailbox（channel）を持ち、loop だけが自分の state を書く |
| 構造化並行性、Channel、suspend 関数 | Kotlin coroutines | `run` は component の scope の coroutine。tool は suspend 関数。channel は send / receive が suspend |
| resource、address、plan / apply | terraform | 宣言の同一性と動的更新 |

## 0. 位置づけ

```
body    : (params, state) → { address ↦ declaration }       純粋。render
run     : component につき 1 つの逐次 loop。state を書く唯一の場所。tool を await し、channel から受ける
channel : event の唯一の経路。外部 event 源は ReceiveChannel を export する。他の component への影響は channel に send することだけ
patch   : 定義を差し替えて同じ state と run の位置で続ける。reconcile と同じ操作
```

Katari の内部は純粋か逐次のどちらかで、作用・時間・失敗は外部 component（葉）にある。

## 1. 核

### 1.1 Component と use

```
Component(B)  ≅  (B ⇒ Void) ⇒ Void       継続を受け取る middleware（引数適用済み）
M : Args → Component(B)

use x = M(args)      x : B（M の export の record）。x を参照する宣言が M の継続。参照しない宣言は M と並列
```

- B = Void なら `use d = Digest(…)` は許され、d を参照すると型エラー
- x が揃うまで、x を参照する宣言は存在しない。render に未知値は現れない
- tool は `use` できない（tool は値ではなく suspend 関数。§3）

### 1.2 body は宣言の集合

順序なし。依存は自由変数で決まり、DAG は静的。`when` の枝の選択だけが動的。

### 1.3 protocol（概念）

```
init d(args) → i / ↓i / ↑i（依存ノードが全て ↑ してから）
```

完了シグナルは無い。dispose 命令は言語に無い。init / dispose は宣言の変化の cascade。

### 1.4 address と DAG

```
address ::= (scope, key)* · label        scope = use の束縛名 / for の site。label = 束縛名。全宣言が名前を持つ。`_` 不可
```

- component はノードではなく接頭辞。address = 同一性、依存 DAG = 寿命。別の構造
- `when` は接頭辞を作らない。`for x in p key f(x)` は scope を作る。`key` は同一性のためだけ
- 改名は migration の `moved`

### 1.5 kind（Data / Type）

```
Data ⊑ Type。Data はコピー可能で handle を含まない。Type は handle（use の出力、channel、Definition、tool 値）を含みうる
state は Data。channel に流せるのは Data。Pool の要素は Type でよい
handle が body に入る経路は params、use の出力、for の束縛。上に戻るのは export と member だけ
```

### 1.6 signal と読み取り

```
宣言の中     params と state は signal。変化は依存する宣言の再評価（render）だけを起こす
run の中     params と state は「読んだ時点の値」（Kotlin の StateFlow.value）。固定したければ let に写す
tool の引数  call 時の値
```

## 2. 宣言

```
component Name(params) {
  [export] use x = M(args) [key k]      resource / 子
  [export] state s: T = init            T : Data。書けるのは同じ body の run だけ
  pool p: Pool<B> / member admit x       上向きの handle
  when cond { … } / for x in p key f(x) { … }
  run { 逐次 }                          1 つだけ。`loop { … }` は `run { loop { … } }` の糖衣
}
tool T(params) ~> R { 逐次 }            top-level。suspend 関数
fn   f(params): R = 式                  純粋
```

### 2.1 state

- `s <- v` は同じ body の `run` の中にしか書けない。他の component からは channel に送ることでしか影響できない
- 書き込みは await 境界でまとめて commit され、その後 render（await と await の間 = 1 transition）
- 同じ sync 区間で同じ state に 2 回書けば後勝ち

### 2.2 export と self

- export の record が出力 B。`self` は全 export の record で、`self` を使う宣言は全 export の後
- export できるのは use の出力、state（読み取り専用の signal）、channel の send 側 / receive 側、tool 値

### 2.3 Pool と member

第 2 版と同じ（層化の規則を含む）。

## 3. run と tool

### 3.1 run

```
run {
  let x = await T(a)                 tool を呼ぶ。Fault は伝播。`await try T(a)` は Outcome
  let m = await ch.receive()         channel から受ける（suspend）
  await sig                          signal が定義される / 真になるまで待つ
  s <- v                             state を書く
  with r = kind(args) { … }          区間の resource
  await par(T(a), U(b)) / race(…)    構造化された待ち合わせ。fire-and-forget の launch は無い
  loop { … } / for x in xs { … }
}
```

- run の寿命 = component の宣言。宣言が消えれば cancel（構造化並行性）。await 中の tool と resource も cascade
- 並列は構造で作る: 単位ごとに子 component（自分の run と state を持つ）。親は channel で配る
- run の位置と locals は永続化される（§5）。再起動後は await 境界から続く

### 3.2 tool

```
tool T(params) ~> R { 逐次 }       suspend 関数。state を持たない。await で tool と channel を使う
外部の tool（http、model）も同じ型。葉として呼ばれる
Outcome<R> = Ok(R) | Fault(Failed(Error) | Interrupted)    await は Ok を返し Fault を伝播。try / catch / throw
```

tool 値 = 定義に引数を与えたもの（`Reply(ch, persona, _)`）。式。評価時の handle と Data のコピーを持つ。環境は捕捉しない。
AI に渡す tool の schema は残りの params（Data）と結果型から導出する。

## 4. channel

stdlib の component。buffer は Katari が永続化する。

```
use c = channel<T>()                 export send: SendChannel<T>, receive: ReceiveChannel<T>
c.send(x)      : T ~> Unit           suspend（容量があれば即時）
c.receive()    : () ~> T             suspend
c.receive_all(): () ~> List<T>       1 件以上来るまで suspend、全部取る
use m = channels<K, T>()             key ごとの channel。m.send(k, x)、m.for(k) : ReceiveChannel<T>
```

- 外部の event 源は `ReceiveChannel` を export する（`discord.messages(ch)`）。protocol の `event(id, value)` が buffer に積まれる
- 複数種類の event は直和 1 つの channel（順序が保たれる）
- 誰が send できるかは handle の受け渡し（capability）

## 5. 外部 component、永続化、再起動

protocol は第 2 版と同じ: `init(id, args, cont) / update / dispose`、`init(cont, x) / update(cont, x') / event(id, value) / disposed`。
tool の葉は `init` → `event(id, Outcome)` 1 回。id は runtime が振る不透明値。kind の静的宣言（updatable / replace: forbidden / interruptible / on_restart）も同じ。

```
SoT : Defs、address ↦ state、address ↦ run の位置と locals、channel の buffer、継続の入力、送信ログ
再起動: 再 render → state と run を復元 → 送信ログと宣言集合の差分だけ init / dispose
```

## 6. patch

- 木全体は常に 1 つの版。apply は 1 遷移として原子的
- state: 互換なら keep、migration があれば migrate、無ければ reset（単位は body の state 全体）
- run: 位置 `(label, locals)` が新定義と互換なら続行。非互換なら migration（`at label { … } => label { … }`）か最初から
- plan は render を commit なしで行い、reset 後の render で生じる init / dispose、`replace: forbidden` のブロック、「以前 init された id」を表示
- `moved` で改名を対応づける

## 7. 動的 attach、capability

第 2 版の §7 と同じ（validate / link、reflect / plan / validate_migration、handle = capability、env = 名前）。

## 8. 指針

```
state の書き手は run だけ。run は一本道で、state の遷移は上から読めば分かる
並列は子 component。run の中の並列は par / race だけ
固定したい値は let に写す。追従させたい値は読み直す
event は channel。callback は無い
人間を待つ処理は run の中で await human.ask(…)。取り下げは宣言の消滅
```

## 9. 正典例（評価の起点）

### A. ターン制の bot

```
component Bot(discord: Discord, model: Model) {
  use ch   = discord.channel("general")
  use msgs = discord.messages(ch)
  state status: Idle | Answering(Int) = Idle

  loop {
    let batch = await msgs.receive_all()
    status <- Answering(length(batch))
    with typing = discord.typing(ch) {
      let answer = await ai.infer_text(model, prompt(batch))
      await ch.send(answer)
    }
    status <- Idle
  }
  when status is Answering(n) { use banner = ui.banner("answering " ++ n) }
}
```

### B. ユーザーごとに並列

```
component Bot(discord: Discord, model: Model) {
  use ch      = discord.channel("general")
  use msgs    = discord.messages(ch)
  use inboxes = channels<UserId, Message>()
  state users: Set<UserId> = {}

  loop {
    let m = await msgs.receive()
    users <- users ∪ {m.author}
    await inboxes.send(m.author, m)
  }
  for u in users key u { use conv = Conversation(u, inboxes.for(u), ch, model) }
}

component Conversation(u: UserId, inbox: ReceiveChannel<Message>, ch: Channel, model: Model) {
  state history: List<Turn> = []
  loop {
    let batch = await inbox.receive_all()
    let answer = await ai.infer_text(model, prompt(history, batch))
    await ch.send(answer)
    history <- history ++ [(batch, answer)]
  }
}
```

### C. 承認と timeout

```
component Request(req: Req, human: Human, exec: Executor, clock: Clock) {
  state decision: Pending | Approved | Rejected | TimedOut = Pending
  run {
    match await race(human.ask(req, options = [Approve, Reject]), clock.after(3.days)) {
      Left(Approve) => { decision <- Approved; await exec.run(req) }
      Left(Reject)  => decision <- Rejected
      Right(_)      => decision <- TimedOut
    }
  }
}
```

### D. agent

```
component Agent(model: Model, goal: Text, tools: Tools, out: SendChannel<Text>) {
  state messages: List<Msg> = [system(goal)]
  loop {
    let step = await ai.infer(model, messages, tools)
    match step {
      Say(t)      => { messages <- messages ++ [assistant(t)]; await out.send(t); break }
      Call(calls) => {
        let results = await par(calls.map(c => tools[c.name](c.args)))
        messages <- messages ++ [assistant(calls)] ++ tool_results(calls, results)
      }
    }
  }
}
```

### E. 動的 attach

```
component Plastic(spec: Text, env: Env, model: Model, args: I) {
  state src: Option<Text> = None
  run {
    var errors = []
    loop {
      let t = await ai.infer_text(model, prompt(spec, describe(I), errors))
      match await validate(t, env, I) { Ok(()) => { src <- Some(t); break }, Err(es) => errors = es }
    }
  }
  when src is Some(t) { use d = link(t, env, I) ; use app = d(args) }
}
```

## 10. 評価で確かめたいこと

- props / state を run の中で読む規則（読んだ時点の値）が、長い loop で意図せぬ追従を生まないか。固定の `let` が自然か
- state の書き手が run だけ、で書けない形は無いか（子から親の state を変えたい場面は channel で足りるか）
- channel が第一級であることで、v0.1 の Sink と同じ問題（寿命を越えて情報が逃げる、古い結果が届く）が戻っていないか
- run が 1 つ、の制約。複数の loop が欲しい場面は子 component で自然か
- run の位置の patch と migration が、逐次コードの読者に説明できるか
- tool と component の境界（tool は suspend 関数、component は宣言 + run）が初見で読めるか
