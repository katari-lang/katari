## 0. 位置づけ

Katari v0.2 は動的な terraform である。静的なリソース宣言に、状態・配線・instance の動的な更新を加える。
React が DOM として解釈しているものを組織構造として解釈する DSL。

```
body       : Inputs → { address ↦ declaration }
signal     : 時変値。変化は render を起こす
transition : 子からの到着（Ready か Event）で起きる。State を書く唯一の機会
runtime    : transition のたびに body を再評価し、宣言集合の差分を init / update / dispose に変換する（reconcile）
patch      : 定義を差し替えて同じ State で再評価する。reconcile と同じ操作
```

Katari の内部は純粋で一瞬で終わる。作用・時間・失敗は全て外部 component（葉）にある。

## 1. 核

### 1.1 Component と use

```
Component(B)  ≅  (B ⇒ Void) ⇒ Void        継続を受け取る middleware（引数適用済み）
M : Args → Component(B)

use x = M(args)      x : B。x を参照する宣言が M の継続（M の子）。参照しない宣言は M と並列
```

- 出力が無ければ B = Void。`use d = Digest(…)` は許され、d を参照すると型エラー
- 継続に渡すのは M の `self`（export の record、§2.6）。self は export にしか依存しないので、Void の子は self を遅らせない
- 継続が現れるのは出力 `x` が揃ったとき。それまで x を参照する宣言は存在しない。render に未知値は現れない
- component と tool の区別は kind の性質（§1.7）だけで、宣言の形は同じ

### 1.2 body は宣言の集合

順序なし。依存は自由変数で決まり、DAG はコンパイル時に静的に構築される。`when` の枝の選択だけが動的。

```
宣言 d は、d の式に自由に現れる名前を束縛した宣言に依存する
```

### 1.3 protocol（概念）

```
init d(args) → i     instance を作る。親を教える必要はない（親が子を覚える）
↓i                   dispose 命令
↑i                   dispose 完了通知。i に依存するノードが全て ↑ してから
```

instance に完了シグナルは無い。dispose 命令は言語のプリミティブに無い。init / dispose はすべて宣言の変化の cascade として起きる。

### 1.4 同一性（address）と寿命（DAG）は別の構造

```
address ::= (scope, key)* · label
scope   ::= component 呼び出し site の label（use の束縛名、for の site）
label   ::= body 内の束縛名。全ての宣言が束縛名を持つ
```

- component は **ノードではなく address の接頭辞**。「C の instance」= 接頭辞 `…·C` を持つノードの集合
- address が同一性（reconcile の対応、State の引き継ぎ）。依存 DAG が寿命（↑ の順序）。別の構造
- `use a` を抜いても `b` の address は変わらず keep。DAG の辺だけ更新（init / ↓ を伴わない）
- label は 1 つの body 内で一意。排他でない 2 つの `when` に同じ label があれば静的エラー。`_` は label にできない
- `when` は接頭辞を作らない。`for x in p key f(x)` は scope `(site, f(x))` を作る。`key` は同一性のためだけにある
- 改名は migration の `moved` で対応づける（§6.2）

### 1.5 kind（Data と Type）

```
Data ⊑ Type
Data : コピー可能。handle を含まない（数、文字列、レコード、直和、source text）
Type : handle（use の出力、Pool、Definition、tool 値）を含みうる
```

- State は Data。event の payload は Data。Pool の要素は Type でよい（読み手が要素より短命）
- handle が body に入る経路は params、use の出力、`for` の束縛の 3 つ。上に戻るのは export と member だけで、受け手が型で宣言する

### 1.6 出力: 到着の列と signal

子から親への到着は 1 本の列。

```
Ready(B)    ノードの最初の出力。1 回。`use x = M(args)` の x はこの値。継続はこれを構造として読む
Event(E)*   0 回以上。繰り返す離散通知（watch の message、channel の API エラー、streaming の断片）
```

Ready の後の出力の変化は update（signal）で、transition を起こさない。古い値は新しい値が届くまで残る。
同じ address は同じノードなので、引数が変わっても Ready は再び届かない。呼び出しごとに別にしたければ `key` で別のノードにする。

到着ごとに、`=> Tag` があれば transition が走り、その後 render する。継続の宣言は transition 後の宣言に従う。
1 つの到着を状態（`=> Tag`）で消費するか構造（継続）で消費するかは caller が選び、通知は 1 回。

これとは別に export（signal）がある。時変値で、継続が読む。変化は依存する宣言の再評価（render）を起こすだけ。

```
tool        Ready(Outcome<R>) だけ。streaming なら Event(Partial) が先に並ぶ
resource    Ready(self) の後、Event が続きうる（channel の ApiError）
event 源    Ready(()) の後、Event が続く（watch の Message）
```

component mode では型 `T` の式は signal。literal は定数 signal。DAG が静的なので、signal の変化で再評価されるのは依存する宣言だけ。
transition と tool body では値。

### 1.7 component kind と tool kind

宣言はどちらも `use x = M(args)`。違いは kind の性質だけ。

```
component  引数の変化は update（kind が updatable と宣言した引数）または作り直し（dispose → init。継続も消えて新しい Ready）。
           Ready の後も signal と Event を出す。片付けがある
tool       解放の要らない middleware。引数の変化は同じノードの再計算（走行中は中断）。結果は Ready か update。Event は無い。片付けは中断だけ
```

- `use x = T(args)` の x : Outcome<R>。再起動しても再実行しない。引数が変われば再計算し、x が update される
- 出力後のノードは何も握っていないので、継続がその下にあってもコストは無い
- Katari で書いた tool body（§3）は component に展開される

### 1.8 追従の規則

```
宣言の引数            signal。変われば update か作り直し。下流だけが影響を受ける（dataflow）
完了した tool         宣言が消えていれば何も起きない。残っていれば引数の変化で再計算（update）
到着（Ready / Event）  transition が 1 回だけ消費する。再実行は無い
定義（patch）         単一版の規則（§6）
```

値を固定する手段は 1 つ: transition で State に写す。宣言の側で凍結する機構は無い。
「引数を後から変える」は「変えたい」と同じ意味なので、固定したければ変わらない引数（不変の payload）で宣言する。
呼び出しごとに transition が欲しければ `key` で呼び出しごとに別のノードにする（同じノードの再計算は update で、Ready ではない）。

## 2. 宣言

```
component Name(params) {
  event E                                                 繰り返す離散出力の型。1 つの直和。無ければ省略
  [export] use pat = M(args) [key k] [=> Tag[(payload)]]  resource / 子 / tool 呼び出し。pat は束縛パターン
  [export] state s: T = init                              T : Data
  pool p: Pool<B>                                         p.admit : Admit<B>
  member admit x                                          x : B を pool に入れる。この宣言が有効な間だけ
  when cond { ... }
  for x in p key f(x) { ... }
  on Tag(payload, e) = transition
}
component Name(params) ~> R { …; return e }               出力 Outcome<R> を持つ component。e : Option<Outcome<R>> が Some になったとき継続を召喚
tool T(params) ~> R { 逐次 }                               top-level のみ。出力は Outcome<R>
fn   f(params): R = 式                                     純粋
```

component は 2 種のどちらか。resource（出力 = self、export を持つ）か、`~> R`（出力 = Outcome<R>、export を持たない。event は持てる）。

### 2.1 `=> Tag`、on、emit

```
use pat = M(args) => Tag(payload)      M からの到着ごとに transition。on Tag(payload, arrival)、arrival : Ready(B) | Event(E)
```

- Ready はノードにつき 1 回（dispose → init で作り直されれば再び）。`update(cont, x')`（signal の変化）では発火しない。
  tool の再計算（引数の変化）は update なので、完了ごとに transition が欲しければ `key` で別のノードにする
- 到着ごとに transition → render の順。継続の宣言は transition 後の宣言に従う（transition が宣言を消せば継続は現れない）
- `pat` はパターン。`use Ok(x) = T(args)` なら継続は Ok のときだけ現れる
- tool の `on Tag(p, Ready(o))` は省略して `on Tag(p, o)` と書ける（Event が無いため）

```
on Tag(payload, arrival) = s₁ <- e₁, s₂ <- e₂, …, emit e'      純粋。body の state と payload と到着を読み、次の値と自分の event を出す。全域
```

- transition は瞬間。ノードにならない。走行中という状態が無い。1 transition = 1 遷移として原子的に commit、その後に render
- 同じ state への 2 回の書き込みは型エラー。`emit` は transition の中でだけ書ける（component の event 型 E の値）
- `for` / `when` の束縛は payload に明示的に載せる（`=> Done(n)`）。scope の規則は無い
- Tag は component ごとの直和で、`on` の節の集まりが update 関数
- transition 以外に State を書く手段は無い。callback を値として渡す形（Sink、port）も無い
- event は子ごとに順序を保ち、1 発 = 1 transition。宣言が消えた子からの event は捨てる
- Katari 内の emit は、その transition の直後に親の transition として順に処理される（外部メッセージより先）

### 2.2 event の源と入力

- `event` は Ready の後に続く離散通知のためにある。1 回の出力（完了、結果）は Ready で表す
- 外部 kind は protocol の `event` で出す（watch は message ごとに 1 発）。複数種類の event は直和 1 つ（順序が保たれる）
- Katari component は transition の中で `emit`。子の event を親に渡すのは、受けて emit し直す（明示の転送）
- resource への入力は引数。書きたい値を State に持ち、引数に渡す（`mcp.serve(listen, tools, answers = answers)`）。1 回の送信は tool（`ch.send(text)`）
- 動的に生える子へ event を直接届けることはできない。親の State に溜めて props で下ろすか、kind が filter 付きの watch を提供する

### 2.3 失敗: Outcome

tool の出力は `Outcome<R>`。

```
Outcome<R> = Ok(R) | Fault(Fault)
Fault      = Failed(Error) | Interrupted        Error : Data。Interrupted は葉の再起動契約（§4.4）から
```

| 形 | 受け取るもの |
|---|---|
| `use x = T(a)` | `x : Outcome<R>`（Ready の値） |
| `use Ok(x) = T(a)` | `x : R`。Fault なら継続は現れず、ノードが faulted として trace / plan に出る |
| `use t = T(a) => Tag` | `on Tag(_, o)` の o : `Outcome<R>`。全域なので両方を扱う。t を参照しなければ結果は遷移にだけ使われる |
| tool body の `await T(a)` | `R`。Fault は呼び出し元の Outcome に伝播。`try { … } catch f { … }`、`throw e` |

呼び出し元が分岐する失敗（却下、見つからない）は tool が `~> Result<R, E>` を値として返す。Fault は想定外の失敗と中断のため。

### 2.4 Pool と member

```
p : Pool<B>                       所有者が宣言。p.admit : Admit<B> は handle として下に渡す
member p.admit x                  x : B は宣言者の body の use の出力。pool に居る間 = 宣言が有効な間
for x in p key f(x) { body }      x を束縛。body は x のノードに依存（DAG は木でない）
```

Pool の中身は保存しない。宣言から毎回導出する。

層化: pool を頂点、「p を読む宣言（`for … in p`、p に依存する `when` の条件）の配下に `member q.admit` がある」を辺 p → q とする
render 依存グラフは非巡回でなければならない（静的エラー）。Admit の由来は静的に辿り、辿れなければ同じ要素型の Admit を同じ pool とみなす。
body の top-level の `member admit self` と同じ body の `for p in pool` は通る。巡回的な成長は transition を挟んで State に写す。

### 2.5 tool 値

tool の定義は top-level。component が持てるのは **値** で、定義に引数を与えたもの。

```
export reply = Reply(channel, persona, _)        tool 値。評価時の channel（handle）と persona（Data のコピー）を持つ
```

- 式なので、`persona` が変われば再評価され、それを引数に取る宣言が update / 作り直しされる
- 環境を捕捉していない。定義への参照（名前）と引数だけ。State には入らない（Type）

### 2.6 export と self

component の signal 出力は `export` 付き宣言の record。無ければ `Component(Void)`。

- `self ≡ { e₁ = e₁, …, eₙ = eₙ }`。自由変数は全 export なので、self を使う宣言は全 export の後
- 実際に待つのは `export use` だけ。`export state` は初期値で即座に揃う
- export は body の top-level のみ。export が self に依存すると静的エラー
- `~> R` の component は export を持たない。途中で見せたいものは event で出す（Ready の前に Event が並ぶ）
- resource kind の interface = 出力の型（継続）、export 集合、event 型

### 2.7 `{}` のモード

```
component / when / for   →  宣言の集合。順序なし
tool                     →  逐次
on                       →  式（braces なし）
```

### 2.8 時刻

transition は純粋なので現在時刻を読めない。時刻は resource が出す。

```
use clock = time.clock(resolution = 1.min)        export now: Timestamp
use t = time.at(clock, when) => Fired             event
use e = time.every(clock, d) => Tick
```

## 3. tool body

top-level にのみ書ける逐次記法。引数以外の環境を持たない。component body への展開で意味が定まる。

```
tool T(a: A, cfg: Cfg) ~> R {         component T(a, cfg) {              a, cfg は signal
  let x = await U(a)                    use x = U(a)                     a が変われば U だけ再実行
  let y = await V(x, cfg)               use y = V(x, cfg)                x か cfg が変われば V だけ再実行
  let g = f(x)                          式。使う場所で評価
  with c = kind(args) { … }             use c = kind(args) …             寿命 = 宣言
  return h(x, y, g)                     出力 Ok(h(x, y, g))。継続の召喚
}                                     }
```

- `await` = `use Ok(…)`。`let` = 式（今の値）。`return` = 出力 `Ok`。`throw` = 出力 `Fault`。`await try` は Outcome を束縛
- 追従は dataflow。変わった入力の下流だけ再実行する。完了した tool は通常、結果の transition で宣言が消える
- 並列: `par(U(a), V(b))`、`await for c in cs { F(c) }`（動的な個数。結果は List）、`race(U(a), V(b))`（先に揃った方。残りは dispose）
- ループ: `loop { … }` / `for x in xs { … }` は `state i` と持ち回り変数の `state`、反復 key 付きの use、末尾の `on` に展開される。
  持ち回り変数（`var` への代入）だけが transition で固定される。`let` は反復の中でも生きた導出
- 途中状態 = 埋まっている `let` の集合。address は `let` の名前（反復の中では `· 反復 key`）。migration は component と同じノード単位
- 実装は逐次 body を直接実行してよい。展開と観測的に同値であればよい
- at-least-once。sub-call の address が冪等キー。atomic 性は葉（JS）の 1 回の呼び出しの中だけ

使い分け:

```
tool body    : 途中を誰も見ない・変えない。逐次に読める処理
component    : 途中を見る・変える（人間が待っている、取り下げる、引数が変わる）。状態機械
```

どちらも同じ component に落ちる。人間を待つ処理は component の `when` に出す方が、取り下げと patch が読みやすい。

## 4. 外部 component と境界プロトコル

外部 component（JS 等）も middleware。継続を受け取る。tool も同じ protocol で、継続を 1 回召喚する。

### 4.1 メッセージ

```
親 → 子   init(id, args, cont)        cont = 子が召喚する継続の id
          update(id, args)
          dispose(id)
子 → 親   init(cont, x)                        Ready
          update(cont, x')                     signal の更新
          event(id, value)                     Event
          disposed(id)
```

- 親子の向きは場所で入れ替わる。`use x = M(args); rest` では Katari→M が `init(M, args, rest)`、M→Katari が `init(rest, x)`。
  M は自分の継続を先に片付けてから `disposed(M)` を返す
- tool は `init(cont, Outcome)` を 1 回送る。引数の変化は `update(id, args)` で、再計算の結果は `update(cont, Outcome')`。dispose は中断
- 全メッセージに id ごとの連番を付け、ack が返るまで再送する（両方向）。受け手は (id, 連番) で重複を除く
- 同じ id では `disposed` を待ってから次の `init` を送る
- 宣言がもう無い id からの event / 出力は無視する

### 4.2 id

外部に渡す id は runtime が振る不透明な値で、runtime が address ↔ id の対応を持つ。

- migration / reset / args 変化 / `moved` で id は変わらない。key 変更・宣言の削除追加で変わる
- 葉は id を冪等キーとして使う。同じ id への再 init は同じものの再取得（`when` の反転で dispose → init されたとき）
- at-most-once / at-least-once は葉（と外部サービス）の責任。Katari に作用の分類は無い
- plan は「以前 init されたことのある id への init」を注記する

### 4.3 kind の静的宣言

kind の interface は export 集合と event 型と次の宣言。fake にも同じ宣言を要求する。

```
updatable: [args…]          in-place で更新できる引数。他の引数の変化は作り直し。tool は全引数（再計算）
replace: forbidden          作り直しを plan がブロックする
interruptible: false        完了まで dispose を送らない。親の ↑ も待つ。同じ address への再 init も待つ
on_restart: retry | interrupt   §4.4
```

### 4.4 葉の再起動契約

葉の呼び出しは外部実行で、runtime 再起動を跨いだ exactly-once は Katari では保証できない。

- 葉は開始を記録してから実行する。復帰時に開始済み未完了の呼び出しがあれば、`on_restart` に従って再実行するか、
  `init(cont, Fault(Interrupted))` を送る。どちらの場合も出力を送る（caller が永遠に待たない）

### 4.5 外部の責務

- JS は隔離プロセス。自分の永続化と復帰は id をキーに自分で行う
- 外部 component の種類は使い方の違いだけ: resource（継続を召喚し signal を出し続ける）、event 源（event を出し続ける）、tool（継続を 1 回召喚して終わる）
- resource kind は外部で定義される。component body に unmount hook は無い。dispose 時の作用は、終わりを決めた側が次の枝で宣言する

## 5. 永続化と再起動

```
SoT  : Defs（現在の版）
       address ↦ State（state、tool の結果の memo、loop の state）
       address ↦ 継続の入力（外部の signal 出力 x）
       id ↦ 送信ログ（連番、ack）
導出 : 宣言木、依存 DAG、Pool の中身
```

```
1  root から再 render。各 address の State と継続の入力をはめ込む
2  宣言集合と送信ログを比べる: init 済み ack 済み → 何もしない。未 ack → 再送。宣言に無いのに init 済み → dispose
3  走行中の tool body は埋まっている let から続行。待っている sub-call は宣言として再現され、2 の判定に乗る
4  外部は自分で復帰し、未 ack を (id, 連番) で除去する
```

## 6. patch（動的更新）

```
不変条件: 木全体は常に 1 つの版で動く。apply は木全体で 1 遷移として原子的
```

### 6.1 ノードごとの扱い

| ノードの状態 | plan | 扱い |
|---|---|---|
| 互換、args 不変 | `≡` keep | そのまま |
| 互換、args 変化 | `~` update / `-/+` replace | kind の updatable に従う |
| 非互換、migration あり | `→` migrate | 関数で変換して続行 |
| 非互換、migration なし | `!` reset | 初期値に。単位は同じ body の state 全体 |

- tool body のノード（`let` の memo、loop の state）も同じ規則。完了済みの tool は出力の型が互換なら keep。deploy のたびに推論をやり直すことはない
- reset 後の render が新たに宣言する init / dispose も plan に出る
- `replace: forbidden` の kind に作り直しが及ぶなら plan がブロックする。migration を書くか、明示の `--force-replace`
- 定義 m を差し替えると依存する定義は再 link。影響範囲は DAG を辿る

### 6.2 migration

apply に渡す一回限りのプログラム。実在する状態に対してのみ定義されていればよい。apply 時に再検査し、未定義なら何も変えず中止。

```
migration {
  component Triage { state old => { step: if old.closed then Closed else Open } }     左辺は body の state 全体
  tool Onboard   { let answer: OldAnswer => NewAnswer(…) }                            let の memo の型変換
  moved Support·(Triage,*) => Support·(Ticket,*)
}
```

plan が雛形を生成し、埋めるべき穴と、migration によって dispose される葉を示す。

### 6.3 plan

render は純粋なので、plan は同じ計算を commit なしで行う。新しく init されるノードの継続配下は「apply 後に確定」として出る。

```
≡ Support·(Triage,t42)·closed          keep
! Support·(Triage,t42)·{step}          reset to init (Open)            no migration for Triage
  + Support·(Triage,t42)·h             init                            when not closed becomes true (id seen before)
-/+ Checkout·(Order,"o-7")·charge      dispose + init                  BLOCKED: kind forbids replace
```

### 6.4 指針

- 不変条件を共有する state は 1 つの state（record / 直和）にまとめる
- 再実行は同じ address のまま宣言し直す。`key` は同一性を変えるので、作用を伴う葉の retry には使わない

## 7. 動的 attach

```
Text            : Data      source。snapshot
Definition<I>   : Type      link 済みの定義。use の出力。下にしか渡せない

validate : (src: Text, env: Env, I) ~> Result<Unit, Errors>     tool
use d = link(src, env = { m }, I, migration = m?)                resource。失敗しない。updatable: [src, migration]
use app = d(args)
```

- 名前（型・関数・他の定義・kind）は env の handle に束縛。権限は args の handle。同じ機構
- `I` は静的な型。AI には `describe(I): Text` で渡す
- AI 生成が返すのは Text（validate を含む tool の中でループする）。link するのは host
- root の env は runtime が与える builtin module。deploy は root の `link` の src 差し替え + migration

### 7.1 AI が組み替える

```
reflect(d)                      ~> Structure       address 木、State の型と値の要約、依存 DAG、走行中 tool の位置
plan(d, src', m)                ~> Diff
validate_migration(d, src', m)  ~> Result<Unit, Errors>
```

AI は reflect → 生成 → validate → validate_migration → plan → (人間の承認) → State に書く、の閉ループを tool と transition で書く
（`usage/self-reorganizing.md` §1）。label を変えれば plan に reset が出るので、人間のデプロイと同じ規律が AI にも課される。

### 7.2 capability

「この node の下で何が許可されているか」は handle の有無で表す。それ以外の表現を持たない。

```
ambient authority は無い     全ての kind は provider handle を要求する。root は runtime の設定から provider を受け取る
handle は下にしか流れない     params、use の出力、for の束縛。上に戻るのは export と member だけで、受け手が型で宣言している
record は幅の部分型           { discord, model, http } は { model } の所で使える。子は宣言した型の field しか参照できない
動的な定義は I で検査される    触れる handle は args の型 I に列挙されたものだけ。名前は env
減衰は kind が提供する        with_budget、scoped channel。元の handle を包む resource
失効は宣言の消滅              cascade で dispose
```

- 静的: component の params の型が subtree の capability の上界（v0.1 の coeffect row に相当。宣言であって推論ではない）
- 動的: 依存 DAG と address 木。plan は差し替えで増減する capability を示す
- v0.1 の effect / coeffect の機構は持たない。失われるのは推論だけ。`caps` の record を 1 つの param で渡す

## 8. 標準ライブラリの形

```
ai.infer        : (model, messages, tools) ~> Step          葉。model を 1 回呼ぶ
ai.infer_text   : (model, prompt) ~> Text
ai.stream       : (model, prompt) ~> Text  with event Partial(Text)     完了は継続、断片は event
Agent           : component（付録 E）。出力は Outcome<Text>。tools は引数。会話の途中で tools が変われば次の step から反映
human.ask       : (who, question, options?) ~> A                          UI に出る。取り下げは dispose
store.workspace(name)         export get / put / list（tool 値）、watch(key)（signal）
model.with_budget(m, tokens)  export model、remaining
mcp.serve(listen, tools, answers) / mcp.client(url, auth)      client は tools を export
reflect / plan / validate_migration                            §7.1
```

- 記憶は store、構造を決める Data は State
- 外部が親になる場合（mcp.serve）の address は `srv·(call, id)` を Katari が振る。同じ id が 2 回来れば連番を足す

## 9. 未決

- transition の全域性と tool body の停止性（loop の展開）の検査方法
- `for` の iteration の export を Pool として受ける糖衣
- 遷移のたびに外部へ追記したい State（履歴・監査ログ）の置き場
- Katari で kind を定義する `kind` カテゴリ
- 受信箱 Pool で ack されない要素（dead-letter）の定型
- event と signal 更新の頻度の上限（streaming。runtime 設計）
- implicit parameter（`using caps`）

### A. サポート組織

```
component Support(slack: Slack, model: Model, teams: List<TeamSpec>) {
  use inbox = slack.channel("support")
  use w     = slack.watch(inbox) => Incoming
  state tickets: List<Ticket> = []
  on Incoming(Event(m)) = tickets <- tickets ++ [ticket_of(m)]
  on Incoming(Ready(_)) = skip

  pool members: Pool<TeamHandle>
  for spec in teams key spec.name { use team   = Team(slack, spec, members.admit) }
  for t in tickets key t.id       { use triage = Triage(model, t, members) }
}

component Team(slack: Slack, spec: TeamSpec, admit: Admit<TeamHandle>) {
  export use channel = slack.channel(spec.name)
  export use memory  = store.workspace(spec.name)
  export state spec  = spec
  export reply       = Reply(channel, spec.persona, _)
  export search      = Search(memory, _)
  member admit self
  use digest = Digest(channel, every = 1.day)
}

component Triage(model: Model, ticket: Ticket, teams: Pool<TeamHandle>) ~> Summary {
  use Ok(name) = Classify(model, ticket, names(teams))
  state result: Option<Outcome<Summary>> = None
  on Done(o) = result <- Some(o)

  when result is None {
    for t in teams key t.spec.name when t.spec.name == name {
      use agent = Agent(t.spec.model, ticket.body, { reply = t.reply, search = t.search }) => Done
    }
  }
  return result
}

tool Classify(model: Model, ticket: Ticket, teams: List<Text>) ~> Text {
  return await ai.infer_text(model, prompt(ticket, teams))
}
```

### B. ターン制の bot

```
component Bot(discord: Discord, model: Model) {
  use ch = discord.channel("general")
  use w  = discord.watch(ch) => Received          on Received(Event(m)) = …。Ready(()) は無視
  state turn:    Option<(Int, List<Message>)> = None
  state pending: List<Message> = []

  on Received(Ready(_)) = skip
  on Received(Event(m)) = match turn {
    None    => turn <- Some((0, [m]))
    Some(_) => pending <- pending ++ [m]
  }
  on TurnDone(n, _) = match pending {
    []  => turn <- None
    ms  => turn <- Some((n + 1, ms)), pending <- []
  }

  when turn is Some((n, batch)) {
    use typing = discord.typing(ch)
    use t = Turn(ch, model, batch) key n => TurnDone(n)      ターンごとに別ノード。完了ごとに Ready
  }
}

tool Turn(ch: Channel, model: Model, batch: List<Message>) ~> Unit {
  let answer = await ai.infer_text(model, prompt(batch))
  await ch.send(answer)
}
```

`key n` が無ければ 2 ターン目の完了は同じノードの update になり、`TurnDone` は起きない。
`batch` は transition で state に写した値なので、応答中に届いたメッセージで `Turn` が再計算されることはない。

### C. 承認と timeout

```
component Request(req: Req, human: Human, exec: Executor, clock: Clock) {
  state decision: Pending | Approved | Rejected | TimedOut = Pending
  on Decided(Ok(Approve)) = decision <- Approved
  on Decided(Ok(Reject))  = decision <- Rejected
  on Decided(Fault(_))    = decision <- TimedOut
  on Expired(_)           = decision <- TimedOut

  when decision is Pending {
    use ask = human.ask(req, options = [Approve, Reject]) => Decided
    use ttl = clock.after(3.days)                         => Expired
  }
  when decision is Approved { use Ok(done) = exec.run(req) }
}
```

取り下げは親が `Request` の宣言を消すこと。`ask` と `ttl` は cascade で dispose され、以後の出力は捨てられる。

### D. 決済（at-most-once）

```
component Checkout(order: Order, pay: Payments) {
  state phase: Cart | Paying | Paid(Receipt) | Failed(Error) = Cart
  on Submit(_)          = phase <- Paying
  on Paid(Ok(r))        = phase <- Paid(r)
  on Paid(Fault(f))     = phase <- Failed(error_of(f))
  when phase is Paying { use charge = pay.charge(order) => Paid }
}
kind pay.charge   replace: forbidden   interruptible: false   on_restart: interrupt
```

### E. agent（component）

```
component Agent(model: Model, goal: Text, tools: Tools) ~> Text {
  state messages: List<Msg>  = [system(goal)]
  state calls:    List<Call> = []
  state answer:   Option<Outcome<Text>> = None

  when isEmpty(calls) && answer is None {
    use step = ai.infer(model, messages, tools) key length(messages) => Step     step ごとに別ノード
  }
  for c in calls key c.id { use call = tools[c.name](c.args) => Result(c) }

  on Step(Ok(Say(t)))    = messages <- messages ++ [assistant(t)], answer <- Some(Ok(t))
  on Step(Ok(Call(cs)))  = messages <- messages ++ [assistant(cs)], calls <- cs
  on Step(Fault(f))      = answer <- Some(Fault(f))
  on Result(c, o)        = messages <- messages ++ [tool_result(c, o)], calls <- calls.remove(c.id)

  return answer                                     answer が Some になったとき、継続を召喚する出力
}
```

`return answer` は `answer` が Some になったときに継続を召喚する。tool body の `return v` はこの `Some(Ok(v))` への糖衣。

`key length(messages)` で step ごとに別ノードにする。無ければ 2 回目以降の完了は同じノードの update になり `Step` が起きない。
`tools` が会話の途中で変われば、走行中の step は同じノードのまま新しい集合で再計算される。

### F. 動的 attach

```
component Plastic(spec: Text, env: Env, model: Model, args: I) {
  state src: Option<Text> = None
  on Generated(Ok(t))    = src <- Some(t)
  on Generated(Fault(_)) = skip
  when src is None    { use gen = Generate(model, spec, describe(I), env) => Generated }
  when src is Some(t) { use d = link(t, env, I) ; use app = d(args) }
}

tool Generate(model: Model, spec: Text, iface: Text, env: Env) ~> Text {
  var errors = []
  loop {
    let t = await ai.infer_text(model, prompt(spec, iface, errors))
    match await validate(t, env, I) { Ok(()) => return t, Err(es) => errors = es }
  }
}
```

## 第 1 版からの変更

- 宣言を `use` に統一。bare 宣言、`instant`、`name: T(a) => h` の label 記法を廃止
- 子→親の到着を 1 本の列 `Ready(B)` `Event(E)*` にし、`=> Tag` は到着ごとに transition を起こす。signal（export）は別で render だけ
- tool は解放の要らない middleware。出力は Ready(Outcome) 1 回、引数の変化は同じノードの再計算（update）。`event` が要るのは watch / timer のような繰り返す出力だけ
- Sink / port を廃止。event は値として持ち回れず、届く先は `use` した親の `=> Tag` だけ。転送は明示
- tool の等級（pure / sync / async）を廃止。transition は `on`、計算は `tool`（逐次記法）と `fn`（純粋）
- body 内の tool 定義を廃止。tool は top-level。component が持つのは tool 値（定義 + 引数）
- `State<T>` / `&s` / `bind` / `key` による凍結を廃止。値の固定は transition で State に写すこと
- tool body は component body の逐次記法（await = use Ok、let = 式、return = 出力、loop = state + on）。追従は dataflow。
  `(label, locals)` の正準形は不要になり、migration は component と同じノード単位
- component と tool を同じ kind 系に置き、protocol を 1 組にした（子→親に `event` を追加）
- 「送信元が dispose 済みなら捨てる」は「宣言がもう無い id からの出力 / event は捨てる」に単純化
- callback の捕捉循環の規則を削除（捕捉が無い）
- streaming は component（`ai.stream`）。agent のループは component で書く（付録 E）
