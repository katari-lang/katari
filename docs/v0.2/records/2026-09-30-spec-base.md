## 0. 位置づけ

Katari v0.2 は動的な terraform である。静的なリソース宣言に、状態・配線・instance の動的な更新を加える。
React が DOM として解釈しているものを組織構造として解釈する DSL。

```
body     : Inputs → { address ↦ declaration }
runtime  : 入力（外部イベント・State）が変わるたびに body を再評価し、宣言集合の差分を init / dispose に変換する（reconcile）
patch    : 定義を差し替えて同じ State で再評価する。reconcile と同じ操作
```

Katari の内部は純粋で一瞬で終わる。作用・時間・失敗は全て外部 component（葉）にある。

## 1. 核

### 1.1 Component と use

```
Component(B)  ≅  (B ⇒ Void) ⇒ Void        継続を受け取る middleware（引数適用済み）
M : Args → Component(B)

use x = c ; rest     ≡  c (λx. rest)        bind。rest は c の子。c は rest の親
c ; rest             ≡  par(c, rest)        bare は葉。rest と並列
```

- `Component(Void)` に `use` するのは静的エラー（継続は到達不能）
- 互いに独立な `use` は自動で並列
- 継続が呼ばれるのは出力 `x` が揃ったとき。それまで `rest` の宣言は存在しない（render に未知値は現れない）

### 1.2 body は宣言の集合

順序なし。依存は自由変数で決まり、DAG はコンパイル時に静的に構築される。`when` の枝の選択だけが動的。

```
宣言 d は、d の式に自由に現れる名前を束縛した宣言に依存する
```

### 1.3 protocol（概念）

```
init d(args) → i     instance を作る。親を教える必要はない（親が子を覚える）
↓i                   dispose 命令
↑i                   dispose 完了通知。i に依存するノードが全て ↑ してから
```

instance に完了シグナルは無い。dispose 命令は言語のプリミティブに無い。init / dispose はすべて宣言の変化か
外部イベントの cascade として起きる。

### 1.4 同一性（address）と寿命（DAG）は別の構造

```
address ::= (scope, key)* · label
scope   ::= component 呼び出し site の label（Child、for の site）
label   ::= body 内の構文上の名前（use / state / instant の束縛変数、Child 名、await の束縛変数）
```

- component は **ノードではなく address の接頭辞**。「C の instance」= 接頭辞 `…·C` を持つノードの集合
- address が同一性（reconcile の対応、State の引き継ぎ）。依存 DAG が寿命（↑ の順序）。別の構造
- `use a` を抜いても `b` の address は変わらず keep。DAG の辺だけ更新（init / ↓ を伴わない）
- scope の label 改名は `moved` で対応づける。既定は同 label
- label は定義の body 内で一意。排他でない 2 つの `when` に同じ label があれば静的エラー
- `when` は接頭辞を作らない。`for` は `(site, key)` を作る

### 1.5 kind

```
Data ⊑ Type
Data : コピー可能。handle を含まない（数、文字列、レコード、直和、source text）
Type : handle（use の出力、Sink、Pool、Definition）を含みうる
```

強制点は 1 つ: `Sink<X>` は `X : Data`。ここから

- tool の結果は Data（結果は Sink で運ぶ）
- State は Data（State は Sink 経由でしか書けない）
- Pool の要素は Type でよい（読み手が要素より短命）

handle が body に入る経路は params、use の出力、`for` の束縛の 3 つ。

### 1.6 signal

component mode では型 `T` の式は時変値。literal は定数 signal。tool mode では値（snapshot）。
component から tool call への引数は宣言時の snapshot。DAG が静的なので、signal の変化で再評価されるのは
依存する宣言だけ。

## 2. 宣言の種類

```
component Name(params) {
  [export] use r = M(args)               resource / 子。r : B
  [export] state s: T = init             T : Data。signal s と setter
  [export] instant x = T(args)           tool を呼び、結果を値として受ける。x : R
  T(args) => k                           tool を呼び、結果をイベントとして sync tool k に渡す
  [export] tool t(params): R = e         body 内の tool。sync ならこの body の State を書ける
  pool p: Pool<B>                        p.admit : Admit<B>
  member admit x                         x : B を pool に入れる。この宣言が有効な間だけ
  Child(args)                            子。出力 ⊥
  when cond { ... }
  for x in p key f(x) { ... }
}
```

### 2.1 state

`state s: T = init` は signal `s` と setter `set_s : Sink<T>` の対。`s <- v` は setter への送信。
書けるのは **同じ body の sync tool の中だけ**。async tool は State を書けない。

遷移は外部イベントか tool の完了でのみ起きる。State を書く sync tool は callback（`=> k`、`on_message = k`）
としてしか呼べない。`instant` の右辺には置けない（render をきっかけに遷移を起こさない）。

### 2.2 tool と等級

```
tool T(args): R { body }
  pure  ⊂  sync  ⊂  async
  pure  : 送信も await も無い    式の中で呼べる
  sync  : await が無い           1 遷移。port で Sink にできる。定義された body の State を書ける
  async : await がある           宣言でしか起動できない。State を書けない。dispose できる
型: Args → R（sync 以下）、Args ~> R（async）
```

- sync tool の body は 1 遷移として原子的に commit。同じ state への 2 回書きは型エラー。全域（構造的再帰）
- async tool は await で区切られた sync 区間の列。区間内は全域
- body 内 sync tool は scope の signal（発火時 snapshot）と Sink を捕捉する。捕捉は address と snapshot だけ

**tool は糖衣**。async tool は状態機械に展開される。

```
tool T(a: A) ~> R {
  let x = await U(a)          label ux
  let y = await V(x, cfg)     label vy    cfg は捕捉変数（component DAG のノード。tool の状態には入らない）
  return f(x, y)
}
State = ux {} | vy { x: X }            label ごとの直和。各 variant の変数は必ず値を持つ
```

tool call の順序は source 順 = label 順で逐次。並列は `let (x, y) = await par(U(a), V(b))` と明示。
`with c = kind(args) { … }` は label 区間の resource。

### 2.3 instant と after

```
instant x = T(args)     T のノードは結果を出したら終わる。x は address に Data として保持される
```

- 再起動後は address の値を使い再実行しない。args が変われば作り直して埋め直す
- 宣言が消えれば、走行中なら dispose、埋まっていれば値を捨てる
- `instant` は derivation（入力で key された計算結果の存在）。call が外部に作ったものが call より長生きし
  片付けが要るなら `use`（resource）。call の価値が出力そのものなら `instant`
- データ依存で表せない順序は `after`（自由変数に足すだけ）

### 2.4 Sink と port

```
port : (X → Unit) → Component(Sink<X>)      sync tool を Sink にする
k <- x                                       送信
```

- Sink への送信は 1 遷移。受け手の sync tool の書き込みと送信は commit 後に配送。自分の port への再入は無い
- イベント源は tool を受け取る。sync なら所有者の遷移、async ならイベントごとにノード（address = 源 · event key）
- **callback は、それを受け取る resource を捕捉してはならない**（静的循環）。返事先と購読は別 resource（channel / watch の分離）
- 処理が終わるまで要素を保持したい場合は、kind が受信箱の Pool（要素に ack の Sink）を export する形もある

### 2.5 Pool と member

```
p : Pool<B>                       所有者が宣言。p.admit : Admit<B> は handle として下に渡す
member p.admit x                  x : B は宣言者の body の use の出力。pool に居る間 = 宣言が有効な間
for x in p key f(x) { body }      x を束縛。body は x のノードに依存（DAG は木でない）
```

Pool の中身は保存しない。宣言から毎回導出する。

### 2.6 export と self

component の出力は `export` 付き宣言の record。無ければ `Component(Void)`。

- `self ≡ { e₁ = e₁, …, eₙ = eₙ }`。自由変数は全 export なので、self を使う宣言は全 export の後
- 実際に待つのは `export use` だけ
- export は body の top-level のみ。export が self に依存すると静的エラー
- resource kind の interface = component の export 集合

### 2.7 `{}` のモード

```
component / when / for / agent / with (component 内)  →  宣言の集合。順序なし
tool / with (tool 内)                                  →  逐次
```

sync tool は `=` の右に式 1 つでも書ける。

## 3. 外部 component と境界プロトコル

外部 component（JS 等）も middleware。継続を受け取る。tool はそれに結果の Sink を足したもの。

```
親 → 子   init(id, args, cont)     cont = 子が召喚する継続
          update(id, args)
          dispose(id)
子 → 親   disposed(id)
任意      send(sink, value)        value : Data
```

- 親子の向きは場所で入れ替わる。`use x = M(args); rest` では Katari→M が init(M, args, rest)、
  M→Katari が init(rest, x)。M は自分の継続を先に片付けてから disposed(M) を返す
- id = address。migration / reset / args 変化で変わらない。key 変更・宣言の削除追加・moved 無しの改名で変わる
- 同じ id へのメッセージは順序どおり、連番付きで、少なくとも 1 回届ける。受け手は (id, 連番) で重複除去
- 葉は id を冪等キーとして使う。at-most-once / at-least-once は葉（と外部サービス）の責任。Katari に作用の分類は無い
- kind は静的に宣言する: 引数ごとに update 可能か、`replace: forbidden`（plan がブロック）
- JS は隔離プロセス。自分の永続化と復帰は id をキーに自分で行う
- 外部 component の種類は使い方の違いだけ:
  resource（継続を出力で召喚し生き続ける）、イベント源（Sink を受ける）、tool（継続なし、結果 Sink）

resource kind は外部で定義される。component body に unmount hook は無い。dispose 時の作用は、
終わりを決めた側が次の枝で宣言する。

## 4. 永続化と再起動

```
SoT  : Defs（現在の版）, { address ↦ State }, 各 id へ送ったメッセージの連番
導出 : 宣言木、依存 DAG、Pool の中身
```

再起動 = 同じ定義で再 render し、address に State をはめ込む。外部側は自分で復帰する。

## 5. patch（動的更新）

```
不変条件: 木全体は常に 1 つの版で動く。apply は木全体で 1 遷移として原子的
```

ノードごとの扱い（plan が表示）:

| ノードの状態 | 扱い |
|---|---|
| 互換 | keep / update（args が変われば update） |
| migration がある | migrate |
| 非互換で migration が無い | reset: そのノードを初期値に。**単位は同じ body の state 全体** |
| 捕捉先が消えた走行中 tool | cancel |

- tool の状態 `(label, locals)` も同じ規則。互換 = 新定義に同 label があり locals の型が互換。label 改名は moved
- reset 後の render が新たに宣言する init / dispose も plan に表示される（`when` の反転による作用の再実行が見える）
- migration は apply に渡す一回限りのプログラム。実在する状態に対してのみ定義されていればよい。apply 時に再検査し、
  未定義なら何も変えず中止

```
migration {
  component Triage { state old => { old with quota: 0 } }
  tool Handle { at review { draft, paid } => publish { draft, receipt = paid } }
}
```

- 不変条件を共有する state は 1 つの state（record / 直和）にまとめるのが推奨
- 「別の定義か」は判定できないので常に reconcile。State を捨てたければ key を変える
- 定義 m を差し替えると依存する定義は再 check。影響範囲は DAG を辿る

## 6. 動的 attach

```
Text            : Data      source。snapshot
Definition<I>   : Type      check 済みで linked な定義。use の出力。下にしか渡せない
use d = check(src, env = { m }, i)     env は module handle の record。d → m の依存辺
when d.status is Ok { d(args) }
```

- 名前（型・関数・他の定義・kind）は env の handle に束縛。権限は args の handle。同じ機構
- tool は Data しか返せないので、AI 生成が返すのは Text。定義にするのは host
- root の env は runtime が与える builtin module。deploy は root の定義差し替え
