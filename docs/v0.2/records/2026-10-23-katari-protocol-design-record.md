# Katari Protocol 設計記録

> この文書は、Katari Protocol の設計の過程（検討した選択肢、判断の理由、比較した既存のプロトコル）を残すための記録である。規範となる仕様は `../spec/katari-protocol.md` にまとめる。両者が食い違う場合は、仕様を正とする。


## 0. 概要

本仕様は、Katari のエンドポイント間でリソースを共有・再配布・解放し、component を起動・更新・停止するためのプロトコルを定める。

### 設計方針

Katari Protocol は、既存の標準の**プロファイル**（組み合わせ方と制約の定義）として構成する。既存の標準・ライブラリをそのまま流用できる部分はすべて流用し、Katari 独自に定義するのは次の二つに限る。

1. **永続する参照**：object-capability の参照を、did:key と grant 表によって再起動に耐えるようにしたもの（§3）
2. **ライフサイクル**：activation と revision による寿命管理（§4）

Katari 以外のプロトコル（MCP、各種 webhook など）とは、プロキシで接続する（§6）。Katari Protocol 自体が他のプロトコルとワイヤ互換である必要はない。

### 前提

- エンドポイントは互いに HTTPS で通信する。
- どのエンドポイントも任意のタイミングで再起動しうる。
- 常時接続のセッションは仮定しない。二者間の関係は、鍵と永続化された表によって表す。
- 本仕様が定める状態はすべて durable に保持する。

### 層構成

Katari Protocol は次の層からなる。各層は下の層だけに依存し、独立したコードベース（パッケージ）として実装できるように定める。

| # | 層 | 内容 | 節 | パッケージの例 |
|---|---|---|---|---|
| 1 | 認証 | DID とその解決、JWT のエンベロープ、署名と検証、HTTP binding | §1 | `envelope` |
| 2 | RPC | JSON-RPC、冪等性、outbox と再送、エラーオブジェクト | §2 | `rpc` |
| 3 | capability | リソースの URI、grant と Ref、derive・revoke、値と型の形式、組み込みの種別 | §3 | `capability` |
| 4 | ライフサイクル | activation、revision、panic、寿命の規則 | §4 | `lifecycle` |
| 5 | Katari Language | IR、Compiler、インタプリタ（activation のフックとして動く） | 別の仕様（§5 は本仕様からの要求） | `ir`・`compiler`・`runtime` |

依存は一方向である（5 → 4 → 3 → 2 → 1）。Katari 以外のサーバーは、必要な層までを使えばよい。

| サーバーの例 | 使う層 |
|---|---|
| 自分のリソースを提供するだけのサーバー（投稿用の sink を提供するプロキシ、blob の置き場など） | 1〜3 |
| 他人の Ref を受け取って持ち続けるサーバー（イベントを届けるプロキシ、Timer など）。他人の Ref は activation の引数でしか受け取れないので、component を提供する | 1〜4 |
| Katari Runtime | 1〜5 |

**層をまたぐトランザクション**

各層は自分の表を持つが、一つの処理の中で複数の層の表を同じトランザクションで確定させる場面がある（RPC の応答の記録と grant の作成（§3.4 R3）、activation と引数の grant の対応づけ（§4.4）など）。そのため、各層は永続ストアを直接持たず、下の層から渡される**トランザクションの単位**（Unit of Work）を通じて自分の表を読み書きする。

## 1. 認証層

### 1.1 エンドポイント ID

**原則**

- **エンドポイント ID は DID（W3C Decentralized Identifier）とする。**
- エンドポイントの署名用の公開鍵と、メッセージを送る先の URL は、**DID の持ち主（または運用者）だけが書ける場所**から得る。DID 文書（DID を解決して得られる文書）の `verificationMethod` と `service`、または運用者の設定ファイルである。
- **第三者から渡された値（Ref など）から、接続先の URL を得てはならない。** 第三者が書いた URL に接続すると、内部ネットワークのアドレスなど任意の宛先にリクエストを送らされる（SSRF）おそれがあるためである。

この原則は、AT Protocol（DID 文書から鍵とサービスの URL を得る）、OCapN（自己証明的な designator で相手を指す）、WireGuard（認証できた相手のアドレスだけを記録する）と同じものである。

**受け付ける DID の方式**

どの DID の方式を受け付けるかは実装の設定とする。本版では次を定める。

| 方式 | 位置づけ | 鍵の得方 | 送り先の URL の得方 |
|---|---|---|---|
| did:key | 必須。自前で運用するエンドポイント | DID から DID 文書を組み立てる（通信しない） | 運用者の設定ファイル（§1.2） |
| did:web | 将来の拡張（外部のエンドポイントとつなぐ段階） | DID 文書の `verificationMethod` | DID 文書の `service` |

did:key は次の形をとる。

```
did:key:z<base58btc(0xed 0x01 ‖ 公開鍵 32 バイト)>
例: did:key:z6MkhaXgBZDvotDkL5257faiztiGiC2QtKLGpbnnEGta2doK
```

- did:key は multiformats に基づく、自己記述的な識別子である。ID は鍵そのものを含むので、追加の問い合わせなしに署名を検証できる。また、ID 自体がアルゴリズムを決める（multicodec の `0xed01` が Ed25519 を示す）ので、メッセージ側の指定に依存しない。
- did:key は鍵そのものが ID なので、鍵を更新すると ID も変わる。Katari では ID がリソースの URI、grant の `holder`、activation の親として長く生きる状態に埋め込まれるため、ID が変わると、そのエンドポイントが関わる grant・Ref・activation をすべて作り直すことになる。
- **did:key では、鍵が漏れたときに古い ID を無効にする手段がない。** DID 文書を持つ方式なら文書から古い鍵を外せば全員が受け付けなくなるが、did:key では、攻撃者は古い ID に紐づく grant を、各 issuer が失効させるまで使い続けられる。自前で運用する段階では、運用者が全 issuer で失効させて作り直すことで対処する（§1.7）。外部とつなぐ段階では、ID を変えずに鍵を更新でき、漏洩から回復できる方式が必要である（§9）。

**実装の要件：did:key を前提にしない**

ライブラリと実装は、DID の方式を差し替えられるように作る。

- DID は不透明な文字列として扱う。URI、grant 表、activation の表、設定は、DID の中身を解釈しない。
- 公開鍵は、DID から直接取り出さず、常に解決器（`resolve(did) → DID 文書`）を通して得る。DID 文書は、`id` を持つ検証用の鍵の一覧（`verificationMethod`）と、サービスの URL（`service`）を含む。解決器は、得た文書の `id` が解決した DID と一致することを確かめる。did:key の解決器は、DID から文書を組み立てるだけの実装になる。
- 署名の検証では、送信者の DID（`iss`）を解決した文書の中から、ヘッダの `kid` の鍵を探して用いる（§1.4）。検証に使う鍵は、常にこの解決から得たものだけとする。
- 自分の鍵と ID も、ID ＝ 鍵という前提を置かず、「現在の署名鍵」と「自分の DID」を別々に持つ。

### 1.2 送り先の解決

メッセージを送るときは、送り先の DID から URL を次の順で決める。

1. **運用者の設定ファイル**（`peers`）に DID があれば、その URL を用いる。
2. （拡張）受け付ける DID の方式に解決器があれば、DID を解決し、DID 文書の `service` の URL を用いる。
3. どちらでも決まらなければ、送信できない。上の層に「送り先を解決できない」として知らせる。

```toml
# peers.toml：運用者が書く、did → URL の表（/etc/hosts の DID 版）
"did:key:z6MkRuntime..." = "http://runtime:8080/katari"
"did:key:z6MkTimer..."   = "http://timer:8080/katari"
"did:key:z6MkDiscord..." = "http://discord-proxy:8080/katari"
```

- 表を引くのは送るときだけである。受け取るときは、`iss` を解決して鍵を得る（did:key では通信しない）ので、表は要らない。
- 自前で運用する構成では、全エンドポイントで同じ表を共有するのが簡単である。表を書くには各エンドポイントの DID が先に要るので、鍵は CLI などで事前に作る。
- **設定ファイルに書かれた URL は、運用者が許可したものとして扱う。** プライベートなアドレス（`http://timer:8080` など）でも接続してよい。
- 表にない DID のリソースを指す Ref を受け取っても、その Ref は使えない（送り先を解決できない）。閉じた構成では、これにより外部へ勝手に接続させられることもない。
- 応答のエンベロープの署名が送り先の DID で検証できない場合（§1.6）、その URL の設定の誤りか中間者を疑い、運用者に知らせる。

**拡張（DID の解決器）を加えるときの規則**

did:web などの解決器を加えると、第三者が指定した DID を解決することになり、解決のための取得と、DID 文書に書かれたサービスの URL への接続が、第三者の影響を受けうる。そのため、解決器を加えるときは次を守る。

- 解決のための取得と、DID 文書から得た URL への接続には、**プライベートなアドレス・ループバック・リンクローカルへの接続を拒否する HTTP クライアント**を用いる。名前解決の後でアドレスを確かめ、確かめた IP に接続する（DNS rebinding を防ぐため）。設定ファイルに書かれた URL だけは、この制限の対象外とする。
- **受け取る側でも解決が起きる。** 知らない DID からメッセージが届くと、署名の検証のために DID を解決する。攻撃者は DID を自由に選べるので、受け取る側の解決にも同じ HTTP クライアントを用い、DID ごと・送信元ごとの解決の回数を制限し、結果（失敗を含む）をキャッシュする。
- **送り先の方針**：送ってよい DID の方針（DID やドメインのパターンの許可リスト）を設定に持ち、方針から外れる DID には送らない。**既定は拒否**とする（`peers` にある DID だけに送る、今の閉じた構成と同じ性質を保つ）。運用者が明示的に開けた範囲にだけ送る。Ref の URI の issuer の DID は、その Ref への操作でデータが実際に送られる先そのもの（その DID を解決した先に送り、その DID の鍵で応答を検証する）なので、DID に基づく方針で流出先を確実に絞れる（§1.7）。
- DID 文書はキャッシュしてよい。署名の検証に失敗したときは、一度だけキャッシュを捨てて解決し直す（鍵の更新の直後に対応するため）。
- 解決できない場合は、一時的な障害として扱い、再送の対象にする。

```
self  : 鍵ペア
peers : did → url（運用者の設定。解決器を加えた場合は、その解決結果のキャッシュも持つ）
```

### 1.3 エンベロープ

すべてのメッセージ（リクエスト・応答）は、送信者の鍵で署名した JWT とし、JWS Compact Serialization（`header.payload.signature`）で表す。本節から §1.5 までの規則は輸送路に依存しない。輸送路への載せ方（binding）は §1.6 で定める。

**保護ヘッダ**

```json
{
  "alg": "Ed25519",
  "typ": "katari+jwt",
  "kid": "did:key:z6Mk...#z6Mk..."
}
```

- `kid` は、署名に用いた鍵を、送信者の DID 文書の中の鍵の `id`（DID URL）で指す。DID 文書は複数の鍵を持ちうる（鍵の交換の途中など）ので、どの鍵で署名したかを示す。
- 鍵そのもの（`jwk`）はヘッダに入れない。ヘッダに埋め込まれた鍵で検証すると、その鍵が `iss` の本人のものかを別に照合しなければならず、照合を忘れるとなりすましが成立する（埋め込み鍵を信じてしまう、JWT のよく知られた脆弱性の型）。`kid` は鍵の名前にすぎないので、鍵は `iss` を解決した文書から取り出すしかなく、照合が手順に組み込まれる。
- この形は、OIDC の ID トークン（発行者の JWKS から `kid` で鍵を引く）や、ACME（アカウントを作った後は `jwk` ではなく `kid` を用いる）と同じである。鍵そのものを埋め込む DPoP は、鍵のほかに ID を持たない場合のための形である。

**クレーム**

```json
{
  "iss": "did:key:z6Mk...",
  "aud": "did:key:z6Mk...",
  "jti": "0192f3a4-...",
  "iat": 1729150000,
  "kv": 1,
  "rpc": { ... }
}
```

| クレーム | 意味 |
|---|---|
| `iss` | 送信者の ID（DID）。ヘッダの `kid` は、この DID の文書の中の鍵でなければならない |
| `aud` | 受信者の ID。他のエンドポイント宛てのメッセージの使い回しを防ぐ |
| `jti` | このエンベロープ自身の ID（UUIDv7）。署名するたびに新しく付ける。ログと追跡に用いる |
| `iat` | 署名した時刻（Unix 秒） |
| `kv` | Katari Protocol のバージョン |
| `rpc` | 上の層（§2）の中身。本層はこの中身を解釈しない |

- `jti` は RFC 7519 の定義どおり、JWT 一枚ごとに一意な値とする。受信者は `jti` の表を持たない（リプレイへの対策は §1.5）。
- リクエストと応答は同じ形のエンベロープを用いる。応答では `iss` と `aud` が入れ替わる。

この構造は、AT Protocol のサービス間認証（DID を `iss`・`aud` に入れた JWT）や Restate の request identity（Ed25519 の JWT による送信者の証明）と同系統である。これらとの違いは、本文と応答も署名の対象に含める点にあり、理由は次の二つである。

- **応答の真正性**：エンドポイントの ID は did:key であり、TLS が保証するドメインとは結びついていない（URL は運用者の設定から得るもので、ID の持ち主を保証しない）。応答が ID の持ち主から来たことを示すには、応答への署名が必要である。
- **本文と署名の結びつけ**：送信者の証明だけに署名する方式では、TLS を終端する中継機器が署名を抜き取り、有効期間内に別の本文と組み合わせて使える。本文を署名に含めることでこれを防ぐ。リクエスト本文への署名は、AWS SigV4、各種 webhook、ActivityPub でも一般的である。

### 1.4 検証手順

受信者は、次の順に検証する。

1. `alg` が `Ed25519`、`typ` が `katari+jwt` であることを確認する。ヘッダの値に従ってアルゴリズムを選ぶことはしない。
2. ペイロードの `iss` を（まだ検証していない値として）読み、その DID を解決して DID 文書を得る（§1.1）。受け付けない方式の DID、解決できない DID は拒否する。ここで読んだ `iss` は、鍵を探す場所を決めるためだけに使う。
3. その文書の `verificationMethod` から、`id` がヘッダの `kid` と等しい鍵を探す。なければ拒否する。
4. その鍵で署名を検証する。検証に通れば、`iss` を含むペイロード全体が、その鍵の持ち主の署名によって確かめられたことになる。
5. `aud` が自分の ID と一致することを確認する。
6. `iat` が許容範囲内（既定値は付録 A）にあることを確認する。
7. 検証済みの送信者の ID（`iss`）と `rpc` を上の層（§2）に渡す。

`iss` の文書の中で `kid` を探す順にしているので、他人の文書から鍵を引いてくる経路はない。偽の `kid` を書いても、鍵が見つからずに失敗する側に倒れる。

検証に失敗したエンベロープは、次のいずれかの理由で拒否する。理由の識別子は Problem Details（RFC 9457）の `type` に用いる。輸送路ごとの返し方は binding が定める（HTTP は §1.6）。

| 理由 | `type` | 状況 | 送信者の対応 |
|---|---|---|---|
| malformed | `tag:katari-lang.dev,2026:error:malformed` | JWT として解釈できない | 再送しない（送信側のバグ） |
| unsupported | `tag:katari-lang.dev,2026:error:unsupported` | `alg` または `typ` が規定と異なる。`iss` が受け付けない方式の DID | 再送しない |
| bad-signature | `tag:katari-lang.dev,2026:error:bad-signature` | 署名が検証できない、`kid` の鍵が `iss` の文書にない | 再送しない |
| misdirected | `tag:katari-lang.dev,2026:error:misdirected` | `aud` が受信者の ID と一致しない | 宛先（URL と ID の対応）を確認する |
| stale | `tag:katari-lang.dev,2026:error:stale` | `iat` が許容範囲外 | 新しい `jti` と `iat` で署名し直して再送する |
| unavailable | `tag:katari-lang.dev,2026:error:unavailable` | 受信者側の一時的な障害（ストアに書けないなど） | 待ってから、同じ `rpc.id` で再送する |

拒否の応答は署名しない。内容は信用できないので、送信者は再送の判断にのみ用いる。

ヘッダに埋め込まれた鍵で検証が通ることは、「この鍵の持ち主が署名した」ことだけを意味する。何を許可されているかは、上の層（§3・§4）が判断する。

### 1.5 リプレイへの対策

本節の**リプレイ**は、第三者が途中で写し取ったエンベロープを、そのままもう一度送ることを指す。正規の送信者による**再送**（§2.4）とは別のものである。

| | 誰が | 署名 | `iat` |
|---|---|---|---|
| 再送 | 正規の送信者 | 送るたびに署名し直す（新しい `jti`） | 送るたびに現在時刻にする |
| リプレイ | 第三者（鍵を持たない） | 署名し直せないので、写し取ったものをそのまま送る | 元のまま古くなっていく |

本層は時間枠だけを受け持つ。

- `iat` が許容範囲外のエンベロープは拒否される。リプレイできるのは署名から数分以内に限られる。正規の再送は毎回署名し直すので、この時間枠に引っかからない。
- 時間枠内のリプレイは、§2 の冪等性によって無害になる（同じ `(iss, rpc.id)` には保存した応答が返るだけで、副作用は起きない）。

### 1.6 HTTP binding

一つのメッセージを、一つの HTTP リクエストと応答で運ぶ。リクエストのエンベロープは POST の本文に、応答のエンベロープは HTTP の応答の本文に入れる。

```
POST <url>
Content-Type: application/jwt

<JWS Compact: header.payload.signature>
```

`<url>` は §1.2 の手順で決めた送り先である。

| # | 状況 | HTTP | 本文 |
|---|---|---|---|
| 1 | malformed（Content-Type が `application/jwt` でない場合を含む） | 400 | Problem Details |
| 2 | unsupported | 400 | Problem Details |
| 3 | bad-signature | 401 | Problem Details |
| 4 | misdirected | 421 | Problem Details |
| 5 | stale | 400 | Problem Details |
| 6 | unavailable | 503（`Retry-After` を付けてよい） | Problem Details |
| — | エンベロープの検証に通った | 200 | 署名付きの応答エンベロープ（`Content-Type: application/jwt`） |

- #1〜#6 の本文は `application/problem+json` とする（§1.4 の拒否の理由）。`Retry-After` がある場合、送信者はそれに従う。
- すべての応答に `Cache-Control: no-store`（RFC 9111）を付け、HTTP の中継機器（CDN、API ゲートウェイなど）に応答をキャッシュさせない。中継機器が古い応答を返すと、`iat` の範囲外や `rpc.id` の不一致で送信者の検証が失敗し続けるためである。

```http
HTTP/1.1 401 Unauthorized
Content-Type: application/problem+json
Cache-Control: no-store

{ "type": "tag:katari-lang.dev,2026:error:bad-signature", "title": "Signature verification failed", "status": 401 }
```

応答を受け取った側も §1.4 の 1〜6 を行い、加えて応答の `iss` が送り先の DID と一致することを確かめる。満たさない応答は破棄し、§2 の再送の規則に従う。応答の検証に繰り返し失敗する場合（特に署名が検証できない場合）は、黙って再送を続けず、記録して運用者や上の層に知らせる。相手の設定の誤り（鍵の取り違えなど）、時計のずれ、中継機器によるキャッシュ、または中間者の存在が考えられるためである。

**輸送路の暗号化**

エンベロープの署名は、送信者の真正性と内容の完全性を守るが、内容を隠さない（§1.7）。機密性は輸送路と運用に任せ、経路に応じて次のとおりとする。

| 経路 | 要件 | 例 |
|---|---|---|
| 同じホストの中（ループバック、コンテナ間の仮想ネットワーク） | 平文の `http` を用いてよい（MAY） | docker compose のネットワーク |
| ホストをまたぐ、閉じたネットワーク | TLS か、下の層での暗号化を用いるべきである（SHOULD） | WireGuard（Tailscale など）、サービスメッシュの mTLS、CNI の暗号化、クラウドの VPC 内の暗号化 |
| インターネット | `https` を用いなければならない（MUST） | — |

- 同じホストの中の経路を盗聴できる攻撃者は、すでにそのホストを制御しているので、TLS を加えても守れるものがほとんどない。
- 暗号化は、エンドポイントが自分で TLS を張るよりも、下の層に任せることを勧める。エンドポイントの ID（DID）は TLS の証明書とは結びついていないので、自前の TLS では、証明書と DID の対応という別の問題を管理することになるためである。認証は常にエンベロープの署名で行う。
- 経路の判断は運用者が行う。`peers` に書く URL のスキームが、その判断を表す。

エンベロープの規則（§1.3〜§1.5）は輸送路から独立している。将来、一本の接続で多数のエンベロープを流す binding（WebSocket など）を追加できる。

### 1.7 脅威モデル

本層と、その上の層が何を防ぎ、何を防がないかを定める。

**想定する攻撃者**

| 攻撃者 | できること |
|---|---|
| ネットワーク上の攻撃者 | ホストをまたぐ経路での、通信の盗聴、改ざん、再送、遅延、破棄。TLS を用いない内部ネットワークも含む。同じホストの中の経路は、ホストを制御された場合と同じとみなし、対象外とする |
| 悪意のあるエンドポイント | 自分の正規の鍵で署名できる。自分が持つ grant の範囲で任意の操作を行い、偽った Ref を渡し、受け取った Ref を第三者に漏らす |
| 漏れた Ref を手にした第三者 | Ref のすべてのフィールドを読み、自分の鍵で使おうとする |
| 不正な Ref を流し込む相手 | 自分が issuer であるリソース（sink など）の正規の Ref をプログラムに渡し、秘密の情報をそこへ送らせようとする。Ref も grant も本物なので、署名や grant の検証では区別できない。Ref は activation の引数でしか流れない（§3.4）ので、Ref を渡せるのは親（と、root grant を設定する運用者）だけであり、呼び出しの結果やツールの出力、sink のイベントから Ref が入り込むことはない |
| 解決を悪用する相手（DID の解決器を加えた場合） | 自分で選んだ DID を送り込み、受け取る側・送る側に解決のための通信を起こさせる |

**防ぐもの**

| 脅威 | 対策 | 節 |
|---|---|---|
| なりすまし、本文の改ざん | エンベロープへの Ed25519 署名（本文を含む） | §1.3・§1.4 |
| 別の宛先への流用 | `aud` の確認 | §1.4 |
| リプレイ | `iat` の時間枠と `(iss, rpc.id)` による冪等性 | §1.5・§2 |
| 応答の偽造 | 応答への署名 | §1.6 |
| 漏れた Ref の使用 | grant を holder に紐づける | §3 |
| 偽った Ref による権限の取得 | 権限は issuer が grant 表だけで判断する | §3.3 |
| 内部ネットワークへの接続の誘導（SSRF） | 送り先は運用者の設定（と、将来は制限付きの DID の解決）からだけ得る | §1.2 |
| 埋め込まれた鍵によるなりすまし | 鍵はヘッダから取らず、`iss` を解決した文書の中から `kid` で探す | §1.3・§1.4 |
| 解決の悪用（大量の解決、内部への接続） | 受け取る側・送る側の解決に、SSRF 対策済みのクライアント、回数の制限、キャッシュを用いる | §1.2 |
| 不正な Ref による、許可していない相手への流出 | 送り先の方針（既定は拒否）。データが送られる先は Ref の URI の issuer の DID そのものなので、DID に基づいて流出先を絞れる | §1.2 |

**防がないもの（範囲外）**

- **機密性**：署名は内容を隠さない。暗号化しない経路では、本文（リソースの内容を含む）は盗聴されうる。経路ごとの要件は §1.6 の「輸送路の暗号化」に定める。
- **秘密鍵の漏洩**：漏れた鍵で、その ID になりすませる。鍵の保護は実装と運用が受け持つ。did:key では古い ID を無効にできないので（§1.1）、漏洩したら次の手順で回復する。
  1. 漏れた ID を holder とする grant を、各 issuer で失効させる（自前の運用では、全 issuer が運用者の管理下にある）。
  2. 漏れた ID が issuer であるリソースを使っている側に、それらの Ref を使わないよう知らせる（漏れた鍵を持つ攻撃者が、そのリソースの issuer になりすませるため）。
  3. 新しい鍵（新しい ID）でエンドポイントを作り直し、`peers` を更新し、grant を発行し直す。
- **運用者の設定の改ざん**：`peers` の URL を差し替えられると、応答の署名の検証に失敗するので偽の応答は受け入れないが、リクエストの内容は漏れ、通信は止まる。設定ファイルは秘密鍵と同様に保護する。
- **正規のエンドポイントによる、権限の範囲内での悪用**：capability は渡した権限の範囲に被害を限るだけである。渡す権限を最小にする（facet を用いる）のは、プログラムの責任である。
- **方針の範囲内での流出**：送り先の方針で許可した相手の sink に、送るべきでない情報を送ってしまうこと。capability は「誰がアクセスできるか」を制御するが、「データがどこへ流れるか」は制御しない（confinement problem）。これは言語の層の情報流制御（IFC）で扱う（§5）。
- **隠れた経路（covert channel）**：タイミングや量などを使った情報の流出。IFC の一般的な限界であり、扱わない。
- **サービス妨害**：大量のリクエストや、署名の検証のコストを狙った攻撃。流量の制限は実装に任せる。
- **時計のずれ**：大きくずれたエンドポイントのエンベロープは拒否される（安全側に倒れ、可用性が損なわれる）。
- **通信の有無や相手、量から推測される情報**（トラフィック分析）。

## 2. RPC 層

### 2.1 メッセージ

エンベロープの `rpc` クレームには、JSON-RPC 2.0 のリクエストオブジェクトまたは応答オブジェクトを入れる。

```json
// リクエスト
"rpc": { "jsonrpc": "2.0", "id": "0192f3b0-...", "method": "sink/emit", "params": { ... } }

// 応答
"rpc": { "jsonrpc": "2.0", "id": "0192f3b0-...", "result": { ... } }
```

- `rpc.id` は必須の文字列（UUIDv7）とし、リクエストの送信者が付ける。応答はその値をそのまま返す（JSON-RPC 2.0 の規定）。JSON-RPC の通知（`id` のないリクエスト）は用いない。
- `method` の名前空間は上の層ごとに分ける（`grant/*` は §3、`activation/*` は §4）。本層はメソッドの意味を解釈せず、登録された上の層の処理に渡す。

**ID の役割**

| ID | 役割 | 再送時 | 見たことのある値が届いたとき | 層 |
|---|---|---|---|---|
| `jti` | エンベロープの識別（ログ・追跡） | 毎回新しくする | 判定に用いない | 1 |
| `(iss, rpc.id)` | リクエストの冪等性と、応答との対応づけ | 変えない | 保存した応答を返す | 2 |

- `rpc.id` は再送をまたいで同じ値を使うので、論理的なリクエストの識別子として IETF httpapi WG の `Idempotency-Key` と同じ役割を担う。`rpc.id` は送信者ごとに付けるので、判定は `iss` と組にして行う。
- `rpc.id` は署名の内側にあるので改ざんできない。リクエストごとに異なる値を用いるので、過去の正規の応答を別のリクエストへの応答として使い回すことはできない。
- エンベロープ自身の ID と、やり取りを結びつける ID を分ける考え方は、DIDComm v2 がメッセージの `id` と返信先を示す `thid` を分けているのと同じである。
- `Idempotency-Key` ヘッダ自体は使わない。HTTP のヘッダは署名の対象外であり、また HTTP の中継機器が独自に応答をキャッシュして返すと、`iat` の古い応答が返って受信側で拒否されるためである。

### 2.2 処理手順

受信者は、§1 の検証に通ったリクエストを次の順に判定し、最初に該当した行の応答を返す。応答は署名付きのエンベロープで返す（HTTP binding では 200）。

| # | 状況 | JSON-RPC の応答 | `seen_rpc` への記録 | 送信者の対応 |
|---|---|---|---|---|
| 7 | `rpc` が JSON-RPC のリクエストとして不正 | error -32600 | しない | 再送しない |
| 8 | `(iss, rpc.id)` が処理中 | error 1001 | — | しばらく待って、同じ `rpc.id` で再送する |
| 9 | `(iss, rpc.id)` が処理済みで、フィンガープリントが異なる（照合する場合のみ） | error 1002 | — | 再送しない（ID の再利用は送信側のバグ） |
| 10 | `(iss, rpc.id)` が処理済み | 保存した応答（`result` または `error`） | — | 応答を受け取る |
| 11 | 新しいリクエストで、上の層の処理がエラーになった | 上の層のエラー | する | 再送しない。エラー内容に応じて対処する |
| 12 | 新しいリクエストで、処理中に予期しない内部エラーが起きた | error -32603 | しない（処理はロールバックする） | 同じ `rpc.id` で再送してよい |
| 13 | 新しいリクエストで、上の層の処理が成功した | `result` | する | 応答を受け取る |

- 処理済みのリクエストに応答を返し直すときは、保存しておいた JSON-RPC の応答オブジェクトを、新しいエンベロープ（新しい `jti` と `iat`）で包んで返す。保存するのは署名済みのエンベロープではない。エンベロープごと保存すると、後から返したときに `iat` が古くなって受け取り側で拒否されるためである。
- #12 は記録を残さない。同じ `rpc.id` で再送されたときに、最初から処理し直せるようにするためである。処理による状態の変更もロールバックする。§1.4 の unavailable も同様である。
- #11 のエラーも応答として記録する。同じ `rpc.id` の再送には、状態がその後変わっていても同じエラーを返す。
- **フィンガープリントの照合は任意**である。照合する場合は、JSON-RPC のリクエストオブジェクトを RFC 8785 で正規化し、SHA-256 を取った値を `seen_rpc` に記録する。照合は攻撃への対策ではなく、送信側のバグ（ID の再利用）を検出するためのものである。
- #8・#9・#10 の処理は、Idempotency-Key のドラフトが定める規則（処理中は 409、内容の不一致は 422、処理済みは保存した応答）と同じである。Katari では HTTP のステータスではなく、署名付きの JSON-RPC エラーとして返す。

**応答を受け取る側の判定**

| 状況 | 対応 |
|---|---|
| 応答のエンベロープが §1.4 の 1〜6 を満たさない、または `iss` が送り先の DID と異なる | 応答を破棄し、同じ `rpc.id` で再送する（§2.4 の再送の規則に従う） |
| 応答の `rpc.id` が、送ったリクエストの `rpc.id` と一致しない | 応答を破棄し、同じ `rpc.id` で再送する（同上） |
| outbox のエントリがすでに完了している（通常は起きない） | 応答を破棄する（二重適用を防ぐ） |
| 上記以外 | 応答を受け取り、outbox のエントリを完了にする |

HTTP binding では、応答は常に同じ HTTP リクエストへの応答として返るので、応答待ちの表は持たない（一本の接続に多数のメッセージを流す binding では、`rpc.id` で応答を対応づける）。リプレイされた応答（同じ相手が過去に返した正規の応答を、中継機器などが別のリクエストへの応答として差し込んだもの）は、`rpc.id` が一致しないので破棄される。

### 2.3 エラー

**エラーの二つの種類**

| 種類 | 形式 | 例 |
|---|---|---|
| 型に現れるエラー | op や component が宣言した型に従う。プロトコルは関与しない | `compile` の型エラー（`result` の中で返す）、標準ライブラリが提供する型付きのエラー |
| 型に現れないエラー | **本節が定める Katari のエラーオブジェクト**に従う | 署名が不正、grant が失効、引数が不正、`panic` |

型に現れないエラーは、どこから届いても同じ形をとる。

| 経路 | 形式 |
|---|---|
| エンベロープの段階の失敗（§1.4） | 署名なしの Problem Details |
| リクエストの失敗 | JSON-RPC の `error` オブジェクト |
| activation の失敗（§4.3） | `activation/report` の `panic` イベントの `error`。JSON-RPC の `error` オブジェクトと同じ形 |

JSON-RPC の `error` オブジェクトの形（`code`・`message`・Problem Details の `data`）を、**Katari のエラーオブジェクト**と呼ぶ。

```json
{
  "code": 1103,
  "message": "Grant has been revoked",
  "data": { "type": "tag:katari-lang.dev,2026:error:revoked", "title": "Grant has been revoked" }
}
```

**エラーの識別**

- エラーの種類は、URI（Problem Details の `type`）で識別する。エンベロープの段階では Problem Details の `type` に、それ以外では `error.data.type` に置く。
- 本仕様が定めるエラーの `type` は、tag URI（RFC 4151）の `tag:katari-lang.dev,2026:error:<名前>` とする。tag URI は「そのドメインを、その日付の時点で持っていた者が作った名前」を表すので、登録が要らず、将来ドメインの持ち主が変わっても意味が変わらない。Problem Details（RFC 9457）は、たどれない `type` の例として tag URI を挙げている。説明の文書は katari-lang.dev に置くが、`type` 自体はたどる対象ではない。
- **拡張（本仕様の外）が定めるエラーは、自分が持つドメインに基づく URI**（tag URI、または https の URI）を `type` に用いる。他人のドメインや、本仕様の `tag:katari-lang.dev,...` の名前空間を用いてはならない。中央の登録なしに名前の衝突を避けるためであり、Google の `ErrorInfo`（ドメインと理由の組）、Matrix の逆ドメイン形式の `errcode`、AT Protocol の NSID と同じ考え方である。
- JSON-RPC 2.0 は -32768〜-32000 を予約している。JSON-RPC 標準の意味を持つエラーには標準のコードを用い、Katari 独自のエラーには予約範囲の外を用いる。予約範囲の外を用いるのは、JSON-RPC の仕様に沿うためと、MCP など他のプロトコルのコード（MCP は -32002 を「リソースが見つからない」に用いる）との衝突を避けるためである。
- **`code` は扱い方の分類だけを表し、エラーの種類の識別は `data.type` で行う。** 受け取った側は `code` を見て、再送するか、どの層の問題かを機械的に判断する。`code` の値は本仕様だけが定める。拡張は新しい `code` を作らず、下の 2000・2001 のどちらかを用いる（独立に作られた実装が同じ番号を選んで衝突するのを防ぐため）。
- 本仕様の中では、コードの範囲を層ごとに割り当てる。

| 範囲 | 層 |
|---|---|
| -32600〜-32603 | JSON-RPC 標準 |
| 1000〜1099 | RPC 層（本節） |
| 1100〜1199 | capability 層（§3） |
| 1200〜1299 | ライフサイクル層（§4） |
| 2000 | 拡張が定めるエラー。再送しない |
| 2001 | 拡張が定めるエラーのうち、一時的なもの。同じ `rpc.id` で再送してよい |
| 上記以外 | 将来の版のために予約。知らないコードを受け取った側は、2000 と同じに扱う |

本層のエラー：

| `code` | `data.type` | 意味 |
|---|---|---|
| -32600 | `tag:katari-lang.dev,2026:error:invalid` | リクエストの形式が不正（JSON-RPC 標準） |
| -32601 | `tag:katari-lang.dev,2026:error:no-method` | メソッドが存在しない（JSON-RPC 標準） |
| -32602 | `tag:katari-lang.dev,2026:error:invalid-params` | 引数が不正（JSON-RPC 標準） |
| -32603 | `tag:katari-lang.dev,2026:error:internal` | 内部エラー（JSON-RPC 標準） |
| 1001 | `tag:katari-lang.dev,2026:error:in-progress` | 同じ `rpc.id` のリクエストが処理中である |
| 1002 | `tag:katari-lang.dev,2026:error:id-reused` | 同じ `rpc.id` で、内容の異なるリクエストが処理済みである（フィンガープリントを照合する場合のみ） |

JSON-RPC 標準の -32700（Parse error）は用いない。`rpc` は JWT のペイロードの一部としてすでに JSON として解釈されており、解釈できない場合はエンベロープの段階（§1.4 の malformed）で処理を打ち切るためである。

### 2.4 配送

- 配送は at-least-once とする。未送達のリクエストは outbox に永続化し、再起動後に再送する。
- outbox には、JSON-RPC のリクエストオブジェクト（`rpc.id` を含む）を保存する。`rpc.id` は積んだ時点で決め、再送しても変えない。応答を受け取ったエントリは完了とする。
- 再送のたびに、新しい `jti` と現在時刻の `iat` でエンベロープを作り直して署名する。
- 一つの outbox エントリについて、同時に送るリクエストは一本までとする。タイムアウト後に再送する場合は、先に前のリクエストを中断する。
- 複数のプロセスが一つの outbox を共有する場合は、エントリを取り出すときに排他（期限付きのリース）をかける。リースの期限が切れるまで、他のプロセスはそのエントリを送らない。
- 再送の間隔は、ジッター付きの指数バックオフとする。unavailable の拒否に待ち時間の指定（HTTP では `Retry-After`）があれば、それに従う。
- 再送の上限は、メッセージの経路によって分ける。

  | 経路 | メッセージ | 再送の上限 | 上限に達したら |
  |---|---|---|---|
  | データの経路 | 制御の経路以外のすべて（`sink/emit`、`blob/fetch`、`grant/derive` など） | あり（回数または期限） | `failed` とし、上の層に知らせる |
  | 制御の経路 | `activation/*`（§4）と、寿命の規則による `grant/revoke` | なし（再送の間隔の上限だけを持つ） | 上限はない。受信者から署名付きの応答が返るまで送り続ける |

  制御の経路の再送は、送り先ごとにまとめることを勧める。止まっている送り先には、送り先ごとに一本だけ様子を見る送信を続け、応答が返ったら溜まっているメッセージを送る。

  制御の経路を諦めないのは、失敗の報告（`panic`）や寿命の後始末が途中で消えると、相手が永遠に待ち続けるためである。制御の経路のメッセージは意味上の冪等キー（`aid`、`(aid, rev)`）を持つので、`seen_rpc` の保持期間を超えて再送され、二度処理されても害はない。
- 送信を中止してよいのは、上限に達した場合のほかは、受信者から**署名付きの**応答（エラーを含む）が返った場合だけである。署名のない拒否（§1.4）は内容を信用できないので、再送するかどうかの判断にだけ用いる。ただし malformed・unsupported・bad-signature・misdirected のように再送しても変わらない拒否は、データの経路ではただちに `failed` としてよい。制御の経路では、設定が直るまで再送を続け、運用者に知らせる。
- `failed` になったエントリの `rpc.id` は再利用しない。改めて送る場合は、新しい `rpc.id` で outbox に積み直す。受信側ではすでに処理済みの可能性があるので、操作そのものの重複は上の層の意味上の冪等キー（§4 の `(aid, rev)` など）で防ぐ。
- 受信者は、`seen_rpc` を送信者が再送しうる期間よりも長く、かつ `iat` の許容範囲より十分長く保持する。
- `seen_rpc` への登録は原子的に行い（一意制約付きの挿入など）、処理中と処理済みを区別する。処理結果の記録は、上の層の処理による状態の変更と同じトランザクションで確定させる。
- 送り先の URL を決められない（§1.2）エントリは、送らずに再送の規則に従って待つ。設定が直れば送られ、上限に達すれば `failed` になる。
- メッセージの順序は保証しない。順序が必要な場合は、次のチャネルを用いるか、上の層で通し番号を用いる。
- **チャネル**：outbox のエントリには、任意でチャネルのキーを付けられる。同じチャネルのエントリは積んだ順に一つずつ送り、前のエントリが完了するまで次を送らない。チャネルのエントリが `failed` になったら、そのチャネルの後続のエントリは送らずに止め、上の層に知らせる（順序を守るため、失敗したものを飛ばして先に進まない）。
- **応答の受け取り**：outbox のエントリを完了にすることと、応答の結果を上の層に渡して上の層が状態を確定させることは、同じ Unit of Work で行う。途中で落ちた場合は、同じ `rpc.id` で再送すれば保存済みの応答が返る（§2.2 の #10）。これにより、結果を永続化するための別の仕組みは要らない。

```
outbox   : 送信するリクエスト → { status: pending | done | failed, path: data | control, channel（任意）, attempts, next_attempt_at, lease（複数プロセスの場合） }
seen_rpc : (iss, rpc.id) → { status: processing | done, fingerprint（任意）, JSON-RPC の応答オブジェクト }
```

重複とリプレイの排除は層ごとに行う。それぞれ意味論的に異なる層の性質なので、それぞれで検証する。

| 仕組み | 防ぐもの | 層 |
|---|---|---|
| `iat` の時間枠 | 古いエンベロープのリプレイ | 1 |
| `(iss, rpc.id)` | 再送や時間枠内のリプレイによる二重処理 | 2 |
| `(aid, rev)` | 同じ操作の重複 | 4 |

## 3. capability 層

### 3.1 概念と Cap'n Web との対応

参照の意味論は Cap'n Web / CapTP の object-capability モデルに従う。名前を知っているだけでは何もできず、操作には必ず権限が要る。

Katari の参照（Ref）は、二つのものの組として捉える。

| 要素 | 役割 | 属する先 |
|---|---|---|
| **リソースの URI** | 何を指すか | リソース |
| **grant** | それを使ってよい根拠。holder に紐づく認可 | holder とリソースの組 |

これは AWS の ARN と IAM、REST の URL とアクセストークン、OAuth のリソース指示子（RFC 8707）とトークンと同じ分け方である。Ref は言語の中では不透明な一つの値として受け渡され（§5）、grant が holder に紐づき、権限の判断は必ず grant で行うので、object-capability の性質は保たれる。

Cap'n Web の参照はセッション内の整数 ID であり、セッションが終わると無効になる。Katari はこれを、エンドポイント ID（did:key）に紐づく grant として永続化する。

| Cap'n Web / CapTP | Katari | 違い |
|---|---|---|
| `RpcTarget` を継承したオブジェクト | resource（URI で識別される） | — |
| スタブ（stub） | Ref | Katari の Ref はセッションに依存せず、再起動に耐える |
| export テーブル（セッション内） | grants 表（issuer 側、永続） | holder の did に紐づく |
| import テーブル（セッション内） | なし | Ref は自己完結した値なので、holder 側は表を持たない |
| メソッド呼び出し | `sink/emit`・`blob/fetch`（データだけを運ぶ）、結果を返す呼び出しは component の起動（§4） | 汎用のメソッド呼び出しは持たない。結果と寿命を持つものはライフサイクル層が扱う |
| `release` | なし | Ref の寿命は、それを引数として受け取った activation の寿命で決まる（§4）。holder が「もう使わない」と伝える必要がない |
| （該当なし） | `grant/derive`、`grant/revoke` | 第三者への再配布と、発行元による失効 |

本層は「何を使えるか」を定め、「いつまで使えるか」は定めない。grant の寿命は、上の層（§4 のライフサイクル）が本層の操作を使って決める。

**Ref は木を下にだけ流れる。** 他人の Ref を受け渡せるのは activation の引数（§4）だけであり、`sink/emit` のイベントと `blob/fetch` の結果はデータだけを運ぶ（§3.4）。Ref は親から子へ下に流れ、データは子から親へ上に流れる。これは React の「props は下へ、コールバックは上へ（値だけ）」と同じ形であり、Ref の寿命が常にいずれかの activation のスコープに収まることを保証する（§7.2）。

### 3.2 リソースの URI

```
リソースの URI : katari:<issuer の DID>/<種別>/<ローカル ID>
grant の URI   : <リソースの URI>/grant/<grant の ID>

例: katari:did:key:z6MkhaXgBZDvotDkL5257faiztiGiC2QtKLGpbnnEGta2doK/sink/7f3a
    katari:did:key:z6MkhaXgBZDvotDkL5257faiztiGiC2QtKLGpbnnEGta2doK/sink/7f3a/grant/g12
```

- 構成は AT Protocol の AT URI（`at://<DID>/<コレクション>/<レコードキー>`）と同じで、種類と ID を交互に並べる形は Google の resource name（AIP-122）と同じである。
- `katari:` の後ろに `//` を置かない。`//` を置くと、URI の一般的な規則（RFC 3986）では DID の部分が「ホスト名:ポート番号」として解釈され、一般的な URI のパーサー（WHATWG URL など）で扱えなくなるためである。`//` を置かない形は、`did:`・`urn:`・`mailto:` と同じく、一般的な URI として正しい。
- DID は `/` を含まないので、`katari:` の後ろの最初の `/` までが DID である。種別・ローカル ID・grant の ID も `/` を含まない一つの区切りとする。

**名前の原則**

Katari の名前は、すべて `katari:<名前を作った DID>/<種類>/<ID>` の形で表す。URI の権威（DID の部分）は、その名前を作り、一意性に責任を持つエンドポイントである。

- **通信の中で URI を使うのは、第三者に渡る名前（Ref）だけ**とする。第三者に渡る名前は、受け取った人が名前だけから送り先を知る必要があるので、権威を含む URI で表す。Ref の場合、権威（issuer）は送り先でもある。
- 二者の間でしか使わない名前は、通信では短い形のまま扱い、URI はログ・ダッシュボード・エラーの表示などのための表記として定める。

| 名前 | URI の表記 | 通信での形 | 権威 |
|---|---|---|---|
| リソース | `katari:<issuer>/<種別>/<ID>` | grant の URI から得る | issuer（送り先でもある） |
| grant | `katari:<issuer>/<種別>/<ID>/grant/<ID>` | Ref として、この URI のまま | issuer（送り先でもある） |
| activation | `katari:<親>/activation/<aid>` | `aid`（親の DID はエンベロープから分かる） | 親（名前の作り手。activation が動く場所ではない） |
| リクエスト | `katari:<iss>/rpc/<rpc.id>` | `rpc.id`（`iss` はエンベロープにある） | 送信者 |

activation の URI の権威は親だが、activation が動いているのは子である。この URI を見て親に制御のメッセージを送ってはならない（送り先は親の activation の表に記録した子である）。

| 部分 | 意味 |
|---|---|
| issuer の DID | リソースを保持し、grant を発行するエンドポイント |
| 種別 | リソースの種類。組み込みは短い名前（§3.9、§4.2）、利用者が定義する種別は逆ドメイン形式の名前（`com.example.counter` など） |
| ローカル ID | issuer の中で、その種別のリソースを一意に識別する文字列 |

- URI は大域的に一意であり、リソースの同一性を表す。同じリソースを指す Ref の判定、ログ・監査、失効後に再発行した grant との対応づけに用いる。
- **種別は変わらない。** 種別はリソースの作成時に決まり、リソースが存在する間は変わらない。詳しい型（型引数など）は種別に含めない。型引数は呼び出しのときに指定する（§4.3）。
- **URI は権限ではない。** issuer は操作を受け付けるとき、必ず grant で判断し、URI を根拠に許可してはならない（confused deputy を防ぐため）。URI を分解した結果（種別など）で処理を分けるのは構わないが、権限の判断には用いない。
- **URI は公開されうる識別子として扱う。** ローカル ID に秘密の情報を含めてはならない。

**権限の絞り込み**

同じリソースに対して、grant ごとに異なる権限を持たせることはしない。権限を絞った版が必要な場合は、issuer が元のリソースへの操作の一部だけを転送する別のリソース（facet）を作り、その Ref を渡す。facet は別の URI を持ち、元のリソースとは独立に失効させられる。これは object-capability における facet / forwarder の定石と同じである。

### 3.3 Ref の表現

```json
{
  "grant": "katari:did:key:z6Mk.../sink/7f3a/grant/g12",
  "cid":   "bafkrei..."
}
```

| フィールド | 必須 | 意味 | 信頼できるか |
|---|---|---|---|
| `grant` | ○ | grant の URI（§3.2）。指しているリソースの URI と issuer は、この URI から得る | 権限の検証は issuer が grant 表で行うので、偽っても権限は得られない |
| `cid` | 任意 | 不変データの内容の識別子 | 取得した内容と照合して検証できる |

- grant の ID は秘密ではない。grant は holder に紐づくので、grant の URI を知っていても、holder でなければ使えない。OCapN の sturdyref のように URI そのものが合鍵になる方式とは異なり、grant の URI はログに書いても、他人に見せてもよい。
- 同じリソースへの別々の grant は、リソースの URI が同じで、grant の ID だけが異なる。derive した sub-grant も、同じリソースの下の別の grant になる。派生の関係は URI に含めず、issuer の grant 表（`derived_from`）で持つ。
- Ref は issuer の URL を持たない。issuer への送り先は、grant の URI に含まれる issuer の DID から §1.2 の手順で決める。Ref に URL を含めると、Ref を渡した第三者が接続先を指定できてしまう（SSRF）ためである。
- grant は holder に紐づくので、Ref が第三者に漏れても、その第三者は使えない。OAuth の用語でいう sender-constrained な参照である。
- Ref のフィールドは issuer の署名で守られていない（Ref は第三者を経由して渡される）。そのため、grant 表以外を根拠に権限を判断してはならない。偽ったフィールドによって起きうるのは、操作の失敗だけである。
- `cid` は、内容が変わらないリソース（画像、component の定義など）について、内容のハッシュから作った CID（multiformats に基づく）である。CID を持つ Ref から取得したデータは、取得経路（CDN、キャッシュ、第三者）によらず、CID と照合して検証する。

`cid` は内容の識別子、リソースの URI はリソースの識別子、grant の URI は権限の識別子であり、それぞれ役割が異なる。

**型について**

Ref が表す型の情報は、URI の種別だけである。種別は粗い分類（sink か、component か）であり、受け取った側は、宣言された型の種別と URI の種別を照合して早期に誤りを検出できる。型引数（`Sink<Event>` の `Event` など）は Ref には含めない。リソースの中身の型の検査は、そのリソースの issuer が行い、通信の層では行わない。

### 3.4 値

JSON-RPC の `params` と `result`（および上の層が運ぶ値）は、次の文法の値（Value）とする。

```
Value  := null | bool | number | string
        | [ Value, ... ]
        | { key: Value, ... }        -- key が "$" で始まる単一キーのものを除く
        | { "$ref": Ref }            -- 参照
        | { "$lit": Value }          -- "$" で始まるキーを持つオブジェクトのエスケープ
```

- `$ref` は値の任意の位置に、任意の個数置ける。Cap'n Web の参照が値の任意の位置に現れるのと同じである。ただし、`$ref` を含めてよいのは下の R1 が定める場所だけである。`$ref` を含まない値を**データ**と呼ぶ。
- キーが `$` で始まる単一キーのオブジェクトは予約する。値として `$` で始まるキーを持つオブジェクトを渡すときは `{ "$lit": <値> }` で包む。この規則は値の深い位置にも再帰的に適用する。

**値に Ref を埋め込むときの規則**

- **R1（Ref が流れる場所）**：Ref を含めてよいのは、activation の引数（§4 の `activation/init` と `activation/revise` の `args`）だけである。`sink/emit` のイベントと `blob/fetch` の結果はデータとする。データであるべき場所に `$ref` を含む値を受け取った場合は、-32602 を返す。例外は、本層の `grant/derive` と `grant/redeem` の結果である（作った grant をその要求者に返すためのもので、値の受け渡しではない）。
- **R2（holder）**：activation の引数に含める Ref は、そのメッセージの受信者（`aud`）を holder とする grant でなければならない。自分が issuer の Ref なら、受信者を holder とする grant を自分で作る。自分以外が issuer の Ref なら、事前に `grant/derive` で受信者向けの sub-grant を作らせる（§3.8、§4.5 の L2）。
- **R3（応答で返す grant）**：`grant/derive` と `grant/redeem` で grant を作る場合、その作成は `seen_rpc` への応答の記録（§2.4）と同じトランザクションで確定させる。同じ `rpc.id` の再送には保存済みの応答が返るので、再送のたびに新しい grant が作られることはない。

R1 の理由：sink のイベントや呼び出しの結果で Ref を上に流すと、その Ref は受け取った側のどの activation のスコープにも属さなくなり、「activation が終われば、それに渡したリソースは（他に渡していなければ）解放してよい」という寿命の規則が成り立たなくなる。呼び出しより長く残す結果は、呼び出した側が用意した置き場（プール）に書き込ませる（§4.7）。

受け取った側は、Ref を独立した表に登録しない。Ref は自己完結した値なので、受け取った値の一部としてそのまま保持すればよい。

### 3.5 状態

issuer 側だけが状態を持つ。holder 側は、本層に関する表を持たない。

```
resources : リソースの URI → リソースとその内部状態
grants    : grant の ID → { holder, target, derived_from, revoked }
              holder       : この grant を使えるエンドポイント（did）
              target       : 対象のリソースの URI
              derived_from : 派生元の grant（derive で作られた場合）。なければ根
tokens    : 招待トークン → { target, redeemed }
```

上の層が grant と自分の概念（activation など）との対応を記録する場合は、本層の表に列を足さず、上の層の表として持つ。

### 3.6 メソッド

holder から issuer に送る。各メソッドの `grant` は grant の URI（§3.2）である。メソッドの名前空間は、リソースへの操作は種別の名前（`sink/`・`blob/`）、grant の管理は `grant/` とする。

| メソッド | params | 意味 | result |
|---|---|---|---|
| `sink/emit` | `{ grant, event }` | sink にイベント（データ）を送る（§3.9） | `null`（受理した） |
| `blob/fetch` | `{ grant, offset?, length? }` | blob の指定した範囲のバイト列を読む（§3.9） | `{ data, size }` |
| `grant/derive` | `{ items: [ { grant, holder } ] }` | 再配布のための sub-grant を、まとめて作る。各 sub-grant の `derived_from` は元の grant、`target` は元と同じリソース | `{ refs: [ { "$ref": ... } ] }`（`items` と同じ順） |
| `grant/revoke` | `{ grant }` | 自分の祖先の grant から derive させた sub-grant を失効させる（寿命の規則 L3・L4 による） | なし |
| `grant/redeem` | `{ token }` | 招待トークンを root grant に引き換える（§3.8） | `{ "$ref": ... }` |

- `grant/derive` は、同じ issuer の grant をまとめて扱うことで、issuer ごとに一回の往復で済むようにする。異なる issuer への derive は並行して送ってよい。
- `grant/derive` の `items` の一部だけが検証に失敗した場合は、全体をエラーとし、sub-grant を一つも作らない。

**リソースへの操作は二つだけ**

- capability 層のリソースへの操作は、データを送り込む `sink/emit` と、バイト列を引き出す `blob/fetch` だけである。どちらもデータだけを運ぶ短い操作であり、Ref を運ばない（§3.4 の R1）。issuer は、受け取ってから一定時間（付録 A の既定値）以内に応答する。
- **結果を返す処理は、すべて component として起動する**（§4）。結果は引数で渡した sink への `emit`（データ）で受け取り、キャンセルと後片付けは dispose で行う。外部のツールの呼び出し（MCP の tool など）も、長い処理（long-running operation、MCP の tasks）も、同じ形で表す。往復の数は増えるが、オーケストレーターでは外部の処理の時間が支配的なので、最適化より一つの抽象にそろえることを優先する（§9）。
- 1001（処理中）は二重処理を防ぐためのものであり、結果を待つポーリングには用いない。
- **結果の永続化**：`blob/fetch` の結果は issuer 側の `seen_rpc` に保存され、holder 側では §2.4 の「応答の受け取り」の規則で確定する。
- **大きなデータ**：エンベロープの大きさには上限（付録 A の既定値）がある。大きなバイト列は、`blob/fetch` で範囲を分けて取得する。sink のイベントにバイト列を入れず、バイト列は常に blob として渡す。書き込みも、相手に blob の Ref を渡して取りに行かせる形で表す（§4.7）。
- **issuer が返す URL**：結果に外部の URL（外部ストレージの署名付き URL など）を含める方式を用いる場合、holder はその URL を第三者が書いた URL として扱い、SSRF 対策済みのクライアント（§1.2）で取得する。issuer は認証済みであっても、悪意を持ちうるためである。

### 3.7 検証規則と上の層への API

送信者の ID（`iss`）を `s`、params の grant の URI を `g` とする。`g` を受け取るすべてのメソッドで、まず次を確かめる。

- `g` の issuer の DID が自分であり、`g` のリソースの部分が `grants[g].target` と一致する。満たさなければ 1101 を返す。grant がどのリソースのものかは URI の構造で決まるので、別のリソースの grant を使うことはできない。

そのうえで、メソッドごとに次を確かめる。

| メソッド | 条件 |
|---|---|
| `sink/emit` / `blob/fetch` / `grant/derive` | `grants[g].holder = s` であり、かつ `derived_from` をたどった祖先がすべて失効していない |
| `grant/revoke` | 自分が issuer であるか、`s` が `derived_from` をたどった**真の**祖先のいずれかの holder である（holder は自分の grant を `revoke` できない。grant の寿命は、それを渡した側が決める） |
| `grant/redeem` | トークンが存在し、まだ引き換えられていない |

メソッドがリソースの種別に合わない場合（sink の grant に `blob/fetch` を送った、など）は -32601、`sink/emit` のイベントが sink の型に合わない場合は -32602 を返す。

本層のエラー：

| `code` | `data.type` | 意味 |
|---|---|---|
| 1101 | `tag:katari-lang.dev,2026:error:unknown-grant` | 該当する grant が存在しない |
| 1102 | `tag:katari-lang.dev,2026:error:unauthorized` | holder が送信者と一致しない |
| 1103 | `tag:katari-lang.dev,2026:error:revoked` | grant またはその祖先が失効している |

**上の層への API**

本層は、上の層が自分のメソッドの中で権限を確かめ、grant を作り・失効させるための API を提供する。上の層は、grant 表を直接読み書きしない。

| API | 意味 |
|---|---|
| `check(grant, sender)` | 上の検証規則（grant と対象の一致、holder、祖先の失効）を行い、通れば対象のリソースを返す |
| `issue(resource, holder)` | 自分のリソースへの grant を作り、その URI を返す |
| `revoke(grant)` | grant を失効させる（`derived_from` をたどる sub-grant も失効する） |
| `encode(value)` / `decode(value)` | 値を §3.4 の形式に変換する。データであるべき場所では Ref を拒否し（R1）、activation の引数では R2 に従って必要な grant の作成と derive を行う |

### 3.8 再配布とブートストラップ

**再配布**

- 受け取った参照を第三者に渡せるのは、自分が起動する activation の引数としてだけである（R1）。そのとき、issuer に `grant/derive` を送って sub-grant を作らせる（R2）。受け取った側は issuer と直接通信する（proxy しない）。
- issuer が grant を失効させると、`derived_from` をたどるすべての sub-grant も失効する。
- 多数の Ref は、activation の引数にそのまま並べて渡せばよい。同じ issuer への derive は一回の `grant/derive` にまとめられる。

**ブートストラップ**

最初の grant（root grant）は、次のいずれかの方法で得る。

- **設定による発行**：自前で運用する場合、issuer の設定で特定の did を holder とする root grant を発行し、その Ref を holder 側の設定に書く。
- **招待トークンの引き換え**：issuer は、一度だけ使える推測不能なトークン（128 ビット以上の乱数）を発行し、Katari の外の手段（アカウント登録など）で配る。holder は `grant/redeem` でトークンを提示し、自分の did を holder とする root grant を得る。引き換えたトークンは失効する。

root grant 以降の grant は、すべて activation の引数として受け取る（親が自分のリソースについて作ったものか、親が derive させたもの）。

### 3.9 組み込みの種別

| 種別 | メソッド | 備考 |
|---|---|---|
| `blob` | `blob/fetch({ offset?, length? })` → `{ data, size }` | 画像などのデータ。`data` は指定した範囲のバイト列の base64、`size` は全体の大きさ。大きなデータは範囲を分けて取得する。不変なら Ref に `cid` を付け、取得した全体を照合する |
| `sink` | `sink/emit(event)` | 一方向のイベントの受け口。`event` はデータ（Ref を含まない）。受け付けるイベントの型は sink の issuer が知っており、`emit` のときに検査する |

`component` 種別はライフサイクル層が定める（§4.2）。

**sink の `emit` の意味**

- `emit` の成功（`result` が `null`）は「issuer がイベントを受理した」ことを意味し、「処理を終えた」ことは意味しない。受理した後の処理（Discord への投稿など）の失敗は、`emit` の応答には現れない。受理した後の失敗を送り手に知らせたい issuer は、そのための仕組み（別の sink など）を自分で用意する。
- `emit` にエラーが返るのは、次の場合だけである。

  | 分類 | エラー | 送り手の対応 |
  |---|---|---|
  | 一時的な障害 | 届かない、unavailable、stale、1001、-32603、2001 | 再送する（§2.4）。上限に達したら上の層に知らせる |
  | バグ・設定の誤り | malformed、unsupported、bad-signature、misdirected、-32600、1002、-32601、1101、1102、2000 | 再送せず、ただちに上の層に知らせる |
  | 権限を失った | 1103 | ただちに上の層に知らせる。通常の経路（L3・L4）では起きず、強制終了か issuer による失効でだけ起きる |
  | 型が合わない | -32602（イベントが sink の型に合わない） | ただちに上の層に知らせる |

- sink の issuer は、上の表以外の理由で `emit` を拒否しない。流量の制限は unavailable（待ち時間の指定付き）で表す。
- 送り手は、`emit` の結果を待たずに先に進む（一方向の通知）。そのため、`emit` の失敗は呼び出し元に返すことができず、ライフサイクル層では activation の `panic` として扱う（§4.3）。
- 順序は保証しない。同じ送り手から同じ sink への順序が必要な場合は、§2.4 のチャネルを用いる。

### 3.10 型と値の形式

| 対象 | 形式 |
|---|---|
| 値 | JSON。Ref は `{ "$ref": ... }`、エスケープは `{ "$lit": ... }`（§3.4） |
| 型 | JSON Schema 2020-12 ＋ Katari の語彙（`katariRef` キーワード） |
| スキーマの適用先 | 復号した後の値（`$ref` を Ref に、`$lit` を元の値に戻したもの） |

**単相の型だけを流す**

Katari は総称型を IR に保持し、reflection の時点では型引数がすべて埋まっている。そのため、プロトコルの上を流れる型はすべて単相であり、型引数を持たない JSON Schema で表せる。

**`katariRef` キーワード**

```json
{
  "type": "object",
  "properties": {
    "out":   { "katariRef": { "kind": "sink", "targs": [ { "$ref": "#/$defs/Event" } ] } },
    "label": { "type": "string" }
  },
  "$defs": { "Event": { "type": "object", "properties": { "text": { "type": "string" } } } }
}
```

| 項目 | 意味 | 検証するか |
|---|---|---|
| `kind` | Ref の URI の種別（§3.2） | する。値が Ref であり、URI の種別が一致することを確かめる |
| `targs` | その Ref の型引数（任意） | しない。説明のためのものである（Ref は型引数を持ち運ばず、中身は issuer が検査するため） |

- スキーマは、ワイヤ上の形ではなく、復号した後の値に対して書く。これにより、`$lit` のエスケープとスキーマがずれることも、データの `$ref` と JSON Schema 自身の `$ref` キーワードが混ざることもない。
- `katariRef` を知らない検証器は、JSON Schema 2020-12 の規則により未知のキーワードを無視するので、Ref 以外の部分の検証はそのまま行える。`katariRef` の検証は、各言語の検証器の独自キーワードの仕組み（TS の `ajv` の `addKeyword` など）で実装する。
- MCP の tool の引数も JSON Schema で表されるので、プロキシ（§6.1）は `katariRef` を含まない部分をそのまま受け渡せる。

これは AT Protocol の Lexicon が、JSON Schema に近い形式に `blob` や `cid-link` といったプロトコル固有の型を少しだけ足しているのと同じ方針である。

現時点では、型を CID で識別する必要はない。将来、大きな型を多くのメッセージで共有したい場合などに、スキーマを RFC 8785 で正規化してから CID を取り、値の代わりに CID で参照する方式を追加できる。

## 4. ライフサイクル層

### 4.1 概念

- **component**：起動できる定義。`component` 種別のリソースであり、その Ref を持つことが「起動してよい」権限になる。
- **activation**：component の起動一回分。activation を開始した側（親）が所有し、キャンセルの単位となる。引数として渡した grant の寿命を束ねる。
- **revision**：activation の中で引数全体を差し替える一回分。通し番号 `rev` を持つ。

設計上の対応物として、activation / revision / dispose は React の mount / update / unmount に、`rev` と `revised` は Kubernetes の `generation` と `observedGeneration` に、activation の木は structured concurrency のスコープに相当する。

**capability 層との関係**

capability 層は「何を使えるか」を、本層は「いつまで使えるか」を定める。本層が capability 層を使うのは次の三か所だけである。

| 使う場所 | 内容 |
|---|---|
| 起動の権限 | `activation/init` で、component の grant を `check` する |
| 引数の受け渡し | 引数の値を `encode` / `decode` し、引数に含める Ref の grant を作る・derive させる |
| 引数の寿命 | 寿命の規則（L1〜L4）に従い、引数の grant を `revoke` する |

activation の制御そのもの（revise・dispose・完了の通知）は grant を使わず、本層のメソッドと本層の表で認可する。activation の制御と完了の通知の届け先は、木の構造（所有者）で決まるものであり、移譲したり絞り込んだりする必要がないためである。

### 4.2 component 種別

| 種別 | 用途 |
|---|---|
| `component` | 起動できる定義。`activation/init` の対象になる。capability 層のメソッドの対象にはならない |

- component のシグネチャ（型引数・引数の型）は定義の一部である。
- Ref に定義の CID を付けると、activation が用いるコードのバージョンが固定され、再起動後の再生でも同じ定義が使われる。
- component の grant を失効させても、すでに起動した activation には影響しない。component の grant は「新しく起動する権限」であり、起動した activation の寿命は親が持つ。

### 4.3 メソッド

| メソッド | 送信者 → 受信者 | params | 意味 |
|---|---|---|---|
| `activation/init` | 親 → component の issuer | `{ component, aid, targs, args }`（`component` は component の grant の URI） | activation を開始する（revision 0） |
| `activation/revise` | 親 → 子 | `{ aid, rev, targs?, args }` | 引数（と型引数）を差し替える |
| `activation/dispose` | 親 → 子 | `{ aid }` | activation を終了する |
| `activation/report` | 子 → 親 | `{ aid, event }` | 子の状態の変化を知らせる |

`activation/report` の `event` は次のいずれかである。

| `event` | 意味 |
|---|---|
| `{ "kind": "revised", "rev": n }` | revision `n` の適用を完了した |
| `{ "kind": "disposed" }` | dispose を完了した |
| `{ "kind": "panic", "error": <Katari のエラーオブジェクト> }` | 回復できない失敗が起きた |

- `activation/report` は、プロトコルがイベントの型を定めた sink と同じ性質を持つ。一方向の通知だけを受け付け、結果の値を返さない。
- いずれのメソッドも、result は受理の確認（`null`）だけである。完了は `activation/report` で非同期に知らせる。

**識別と冪等性**

- activation の名前は `katari:<親の DID>/activation/<aid>` である（§3.2）。通信では `aid` だけを送り、子は送信者の DID と組み合わせてこの名前を得る。子の側では `(親の DID, aid)`、親の側では `aid` で識別する。
- `aid` は親が決め、親の中で一意な文字列とする。activation が終わった後も、同じ `aid` を再利用しない（ログの中で、終わった activation と新しい activation が同じ名前にならないようにするため）。
- `aid` は init の意味上の冪等キーを兼ねる。同じ `(親, aid)` による init は、二度目以降は何もせず受理を返す。
- revise と `revised` の意味上の冪等キーは `(aid, rev)` とする。§2 の `(iss, rpc.id)` は同じリクエストの再送を、これらのキーは同じ操作の重複を防ぐ。
- 子は受け取った revise のうち最大の `rev` だけを適用する。古い revise は捨ててよいが、`revised` は適用した `rev` を返す。

**revise をいつ・どう反映するか**

revise の決まりは「子は、適用し終えたら `revised` を返す」だけであり、いつ・どう適用するかは子が決める。親は `revised` を待てるので、反映が遅くてもよい。代表的な方針を挙げる。

| 方針 | revise が届いたときの子の動き | 向いている場面 |
|---|---|---|
| 区切りで反映する | 処理を区切り（フェーズ）ごとに進め、区切りに来たら最新の revise を適用して `revised` を返し、次の区切りを新しい引数で続ける | 一連の作業をフェーズに分けて進めるもの。動的なソフトウェア更新の update point と同じ考え方 |
| 完了してから最新を実行 | 今の実行を最後まで終え、最新の引数でもう一度実行し、`revised` を返す | 外部への作用を持つもの、キャンセルできないもの。Kubernetes のコントローラーの reconcile と同じ |
| キャンセルして最新を実行 | 今の実行を止め、最新の引数で始め、`revised` を返す | LLM の生成や検索など、止めても害がないもの（RxJS の `switchMap` と同じ） |
| メモ化 | 引数が前と同じなら、何もせずに `revised` を返す | 上のどれとも組み合わせられる |

- どの方針でも L3 は成り立つ。外される Ref は、`revised` を返すまでは使い続けてよいので、区切りや完了まで前の引数で進めてよい。
- dispose も「何も引き継がない revision」なので、同じく子の区切りまで待たされうる。すぐに止めたい処理は、途中で中断できるように作る（Katari では言語の側で、中断してよい区切りを書けるようにする）。応答が遅いときは §4.6 の `onStuck` で知らされる。
- 古い引数で計算した結果と新しい結果を区別したい場合は、親が revision ごとに別の sink を渡せばよい。古い sink は L3 によって解放されるので、新しい revision の sink には新しい結果だけが届く。

**認可**

| メソッド | 受信者が確かめること |
|---|---|
| `activation/init` | capability 層の `check(component, iss)` が通ること |
| `activation/revise` / `activation/dispose` | `hosted` の表に `(iss, aid)` の activation があること（activation の名前の権威が送信者であること） |
| `activation/report` | `started` の表に `aid` の activation があり、その `child` が `iss` であること |

該当する activation がない場合は、存在するかどうかを区別せず 1201 を返す。

**型引数と境界での検査**

- `targs` は、component のシグネチャの型引数に与える型を、単相の JSON Schema（§3.10）として並べたものである。Katari は総称型を IR に保持するので、型引数は呼び出しのたびに明示的に与える。
- 型引数は、revise で変えてよい（`activation/revise` の `targs` を省略した場合は変えない）。activation の同一性は `aid` だけで決まり、中身（型引数と値の引数）は revise で差し替えられる。型引数の変更をどう反映するか（型に依存する内部の状態を捨てるか、移行するか、子孫を作り直すか）は component が決める（Katari の component では言語の仕様が定める。動的なプログラムの更新と同じ仕組みを用いることを想定する）。
- 型引数が変わると、引数の型も変わる。`Sink<T>` のように型引数に依存する Ref は、親が新しい型の Ref を作り、revise の引数で渡す。古い Ref は L3 によって解放されるので、型の食い違いは起きない。
- 子は、component のシグネチャを `targs` で具体化し、その型で `args` を検査する（init と revise のそれぞれで）。Ref については URI の種別を照合する。合わなければ、引数を永続化する前に -32602 を返す。init の時点で失敗した場合、activation は作られない。durable execution では型の合わない値が永続化されると、後の再生のときに初めて誤りが表面化するため、受け取った時点で弾く。
- 検査するのは activation 自身の引数だけである。引数に含まれる Ref の中身の型（`Sink<E>` の `E` など）は検査しない（§3.3）。
- 境界での検査は早期発見のためのものである。親が型引数を偽った場合、検査は通りうるが、その後の操作で各リソースの issuer が中身を検査して弾く。権限には影響しない。

**失敗（panic）**

- 子の中で回復できない失敗が起きたとき（言語の中で処理されなかった失敗、Runtime の再起動で中断された外部呼び出し、資源の上限の超過など）、子は `panic` を報告する。
- **`panic` を起こした activation は、自分の計算を止め、自分が起動した activation（`spawned(X)`）にすべて dispose を送る**（キャンセルを木の下へ伝える）。そのうえで `panic` を親に報告し、`faulted` の状態で親の `dispose` を待つ。
  - 自分自身は終了しない。activation を終わらせられるのは所有者である親だけ、という原則に従う。引数として受け取った Ref は、親の `dispose` まで保持する（使わない）。片付けの経路は通常の dispose（L4）だけになる。
  - 子孫を止めるのは、`faulted` の activation の下で外部への作用（投稿、タイマーなど）が続かないようにするためである。これは structured concurrency（Kotlin のコルーチン、Trio）で、子の失敗がスコープの中の他の処理をキャンセルしてから外に伝わるのと同じであり、Erlang の link とも同じ考え方である。
  - `panic` の報告は、子孫の `disposed` を待たずに送ってよい。親の `dispose` に対する `disposed` は、L4 により子孫の `disposed` を待ってから返るので、寿命の規則は崩れない。
  - `faulted` の activation が issuer であるリソース（子孫に渡した sink など）への操作は、受理して捨ててよい。子孫は dispose の途中であり、エラーを返すと子孫の側で余計な `panic` を起こすためである。
- `faulted` の子が受け付けるのは `dispose` だけである。`revise` には 1202 を返す。
- **本層の中で起きる失敗**：activation の代わりに送った、結果を待たないメッセージ（`emit` など）が失敗した場合（§3.9）、本層はその activation を `faulted` にし、`panic` を報告する。`faulted` への遷移と `panic` の報告を outbox に積むことは、同じ Unit of Work で確定させる。そのうえで、ライブラリの利用者に知らせる（フック `onFault(aid, error)`）。利用者はこれを受けて、その activation の計算を止める。結果を待つメッセージ（`blob/fetch` など）の失敗は、呼び出し元にエラーとして返し、どうするかは利用者が決める。
- `faulted` の activation から新しく送ろうとするメッセージ（`sink/emit`、`blob/fetch`、`activation/init` など）は、本層が拒否する。`faulted` になる前に outbox に積まれていたメッセージは、そのまま配送する（止まる前に確定した計算の結果であるため）。
- `activation/report` は制御の経路（§2.4）なので、再送の上限を持たない。親が一時的に止まっていても、再起動すれば `panic` は届く。
- 親は `panic` を受け取ったら、上の層（ライブラリ利用者・言語）に伝える。処理するなら子を dispose する（その後、新しい activation を起こし直すかどうかは親が決める）。処理しないなら、親自身も自分の親に `panic` を報告し、`faulted` になって待つ。失敗は木を上に伝わり、キャンセルは木を下に伝わる。
- `panic` は、型に現れないエラーを所有者に必ず届けるための組み込みの経路である。型に現れるエラー（v0.1 の `throw[T]` に相当するもの）は本層では定めず、上の層（標準ライブラリ）で、親が引数として渡す handler の capability を使う形で提供する。`panic` が capability にならないのは、(1) capability は引数として型に現れる、(2) panic は何の capability も受け取っていない場所（Runtime の再起動、資源の上限）でも起きる、(3) 届け先は木の構造で決まり、第三者に渡されてはならない、の三点による。

**状態**

```
working ──panic──▶ faulted ──dispose──▶ disposing ──disposed──▶ 終了
   └──────────────────dispose──────────────────┘
```

| 状態 | 意味 |
|---|---|
| `working` | 実行中 |
| `faulted` | `panic` を報告し、親の `dispose` を待っている |
| `disposing` | `dispose` を受け取り、L4 の手順を進めている。重複した `dispose` は何もせず受理し、`revise` は受理して無視する |
| 終了 | `disposed` を報告し終えた。activation の行は削除される |

終了の理由は、親の側（`started` の表）で次のいずれかとして記録する。名前は MCP tasks の状態に揃える。

| 終了の理由 | 意味 |
|---|---|
| `completed` | `working` から dispose され、`disposed` を受け取った |
| `failed` | `faulted` から dispose された、または応答しないまま強制終了した |
| `cancelled` | 緊急時の強制終了（§4.6）によって打ち切った |

本層のエラー：

| `code` | `data.type` | 意味 |
|---|---|---|
| 1201 | `tag:katari-lang.dev,2026:error:unknown-activation` | 該当する activation がない（送信者が所有者・子でない場合を含む） |
| 1202 | `tag:katari-lang.dev,2026:error:faulted` | `faulted` の activation に `dispose` 以外を送った |
| 1203 | `tag:katari-lang.dev,2026:error:panic` | `panic` の既定の種類。詳細は `data` に置く（実装は独自の `type` を定めてよい）。L3 の条件 I3 を破った場合は、外される参照、それをまだ引数に含んでいる子孫の activation、その revision を `data` に含め、どの revise を送り忘れているかが分かるようにする |

### 4.4 状態

```
子として動かしている activation（キーは activation の名前 katari:<parent_did>/activation/<aid> と同じ組）
hosted  : (parent_did, aid) → { component, targs, applied_rev, applied_args, instance, status }
            parent_did   : この activation を起動した親のエンドポイントの DID（init の送信者）
            component    : 動かしている component（定義の CID を含む）
            applied_args : 適用済みの revision の引数（受け取った Ref を含む値）
            instance     : 実行中の計算の状態（中身は component の実装が決める）

親として起動した activation（キーは自分が決めた aid）
started : aid → { child, component, targs, sent_rev, acked_rev, status, spawned_by }
            child        : activation を動かしている子のエンドポイントの DID（component の issuer）
            spawned_by   : この activation を起動した、hosted の activation の集まり

activation と capability 層の grant との対応
arg_grants  : (aid, grant_id) → { revs }
                started の activation aid の引数として、自分が発行した grant と、それを含む revision の範囲
arg_derived : (aid, issuer, grant_id) → { source }
                started の activation aid の引数に含めるために、他の issuer に derive させた sub-grant
                source : 派生元の Ref（spawned_by の activation が引数として受け取った grant の URI）
```

各エンドポイントの**局所 activation DAG** は、「hosted の activation X が、その実行中に started の activation Y を起動した」という辺（Y の `spawned_by`）でできている。X が起動した activation の集まり `spawned(X) = { Y ∈ started | X ∈ spawned_by(Y) }` は、この逆引きで得る（実装では索引を持てばよい）。一つの Y を、複数の X が共有して起動することもあるので、木ではなく DAG になる。

- **プロトコルの上の所有は、activation ごとに一つ**である（`parent_did`）。revise・dispose を送れるのは所有者だけであり、引数を決めるのも、終わらせるのも、`panic` を受け取るのも所有者だけである。複数の所有者を許すと、引数の食い違いや終わりの条件を決める必要が生じ、「引数全体を差し替える」「所有者だけが終わらせる」という意味が崩れるためである。
- **共有は、エンドポイントの中でだけ行う**（`spawned_by` が集合であること）。プロトコルから見た Y の親は、このエンドポイント一つである。
- エンドポイントをまたいで一つの処理を共有したい場合（二つの Runtime が同じチャンネルを見張るなど）は、所有者ごとに別の activation を作り、提供する側のサーバーが中で一つの実体（接続など）を共有する。購読者ごとに購読を持ち、サーバーが中でまとめるのと同じ形である。

同じエンドポイントの中で自分自身が提供する component を起動した場合、その activation は `started`（親として）と `hosted`（子として）の両方に現れる。

capability 層の表には activation の概念を持ち込まない。grant と activation の対応はすべて本層の表で持ち、寿命の管理（L3・L4）はこの表を引いて capability 層の `revoke` を呼ぶことで行う。grant の作成とこの表への記録は、同じトランザクションで確定させる（記録だけが欠けると、寿命の管理から外れた grant が残るため）。

### 4.5 寿命の規則

revision n の引数集合を `A_n` とする（init の引数が `A_0`）。

**規則 L1（grant の単位）**
親は、引数として渡す参照ごとに、`(holder, target, aid)` を単位として grant を一つ作る。

- 同じ activation の中で revision をまたいで同じ参照を渡す場合は、同じ grant を再利用する。子は grant の一致によって「参照は変わっていない」と判定できる。
- 同じリソースを複数の activation に渡す場合は、別々の grant とする。片方の解放はもう片方に影響しない。

**規則 L2（渡せるもの）**
started の activation `e` の引数に含めてよいのは、`spawned_by(e)` の activation が引数として受け取った参照と、自分自身のリソースだけである。受け取った参照を渡す場合は derive した sub-grant を用い、`arg_derived` に `e` との対応と、派生元（どの hosted の activation のどの引数の Ref から derive したか）を記録する。

L3・L4 は、本層が自動で行う手順ではなく、**本層が守らせる条件**と、**上の層（ライブラリの利用者・言語）が呼ぶ API とフック**として定める。いつ・どの順で・何をするか（子孫に送る新しい引数、解放処理など）は上の層が決め、本層は寿命の安全（§7.2）を壊さないことだけを確かめ、最後の後片付けを受け持つ。子孫に送る新しい引数は、プログラムにしか決められない（参照を引数から単に抜くと、型に合わない引数になりうる）ためである。

**規則 L3（revision の反映）**
revision n → n+1 で閉じられる参照を `C = A_n \ A_{n+1}` とする。hosted の activation を `X` とする。

1. 本層は revise を受け取ったら、上の層のフック `onRevise(aid, rev, targs, args)` を呼ぶ。
2. 上の層は、自分の方針（§4.3 の「revise をいつ・どう反映するか」）で新しい引数を反映する。必要なら、`spawned(X)` の activation に新しい引数で revise を送り、その `revised` を待つ。解放処理なども、ここで好きな順に行う。`revised` を返すまでは、`C` の参照を使い続けてよい。
3. 上の層は、反映を終えたら `commitRevision(aid, rev)` を呼ぶ。これは「`X` 自身はもう `C` を使わない」という宣言である。
4. 本層は、`revised(n+1)` を返す前に、次の条件を確かめる。

   **条件 I3**：`spawned(X)` のどの activation も、`C` から derive した参照（`arg_derived` の `source` が `C` に含まれるもの）を、適用済みの引数にも、まだ `revised` を受け取っていない revision の引数にも含んでいない。つまり、`C` を含まない revision の `revised` を受け取っているか、終了している。

   - 満たさない場合は、上の層のバグとして `X` を `panic` させる（§4.3）。`panic` により `spawned(X)` は dispose され、親は `revised(n+1)` を受け取らないので、`C` が失効した後に使われることはない。
   - 満たす場合は、`C` から derive させた sub-grant（`arg_derived` から引く）の revoke を outbox に積み、`revised(n+1)` を返す。

親は `revised(n+1)` を受け取った時点で、`C` に対応する grant（`arg_grants` から引く）を失効させる。

**規則 L4（dispose）**
dispose は、何も引き継がない revision（`A_{n+1} = ∅`）に、インスタンスの終了を加えたものである。

1. 本層は dispose を受け取ったら、上の層のフック `onDispose(aid)` を呼ぶ（`faulted` の activation でも呼ぶ）。
2. 上の層は、解放処理（Katari の `finally` など）を好きな順に行う。この間は、引数の Ref と子孫を使ってよい。子孫を自分で dispose してもよい。
3. 上の層は、終えたら `commitDispose(aid)` を呼ぶ。
4. 本層は、まだ終わっていない `spawned(X)` の activation に dispose を送り（cascade）、`disposed` をすべて受け取る。`spawned_by` のうち一つでも dispose された activation は、cascade して dispose する（その activation の引数には、dispose された activation の引数から derive した参照が含まれうるため）。
5. 本層は、`X` の引数から derive させた sub-grant（`arg_derived` の `source` が `X` の引数であるもの）をすべて revoke し（outbox に積む）、`disposed` を返す。

親は `disposed` を受け取った時点で、`arg_grants` に記録されたこの activation の grant をすべて失効させ、activation の行と対応の行を削除する。

**規則 L5（並行性）**
エンドポイントは、`revised` や `disposed` を待っている間も、他の activation のメッセージを処理し続けなければならない。

### 4.6 緊急時の強制終了

- 強制終了は例外的・緊急的な経路である。通常の終了は L3・L4 に従い、`revised` / `disposed` を受け取ってから行う。
- **強制終了は自動では行わない。** `revised` / `disposed` が一定時間（付録 A）届かない場合、本層は利用者にフック（`onStuck(aid)`）で知らせる。強制終了するかどうかは、利用者（プログラム）または運用者が決める。自動で強制終了すると、失効したリソースへの操作が通常の運用で起きるようになり、§7.2 の保証が弱まるためである。子の側の原則（下記）と対称である。
- 強制終了すると決めた場合、親は activation を強制終了する。親は `arg_grants` のすべての grant を失効させ、終了の理由を `failed`（`faulted` でない場合の打ち切りは `cancelled`）として activation の行を削除する。
- その後に子から `activation/report` が届いても、1201 で拒否する。子は、使おうとした Ref が `revoked` になること、または報告が拒否されることで、自分が切り離されたことを知る。
- 強制終了した場合、失効したリソースへの操作が発生しうる。受け取った側は、`revoked` のエラーを正常な経路として処理しなければならない。

**子の側の原則：沈黙では止まらない**

- 子が自分の判断で activation を終わらせてよいのは、親から**署名付きの** 1201 が返ったときだけである。これは「親がその activation を知らない（強制終了した）」ことの確かな証拠なので、子は L4 の手順で自分の部分木を片付ける（親への `disposed` は送らない）。
- 親が応答しないこと（届かない、署名のない拒否）は、止まる理由にならない。子は制御の経路の再送を続ける（§2.4）。子が勝手に止まると、親が再起動したときに、終わった子を待ち続けることになるためである。
- 親が二度と戻らない場合（エンドポイントの廃止など）、子は孤児として資源を持ち続ける。孤児は自動では片付けない。実装は、親に届かなくなってからの時間を運用者に見せ、運用者が孤児の activation を局所的に強制終了する手段を用意する。
- これは Kubernetes のガベージコレクタが、所有者の応答がないことではなく、所有者が存在しないと確かめられたときにだけ従属するオブジェクトを消すのと同じ考え方である。

### 4.7 スコープより長く残す結果（設計の指針）

Ref は下にだけ流れる（§3.4 の R1）ので、子が作ったリソースの Ref を親に返すことはできない。子の処理の結果を残す方法は、結果の寿命によって次の二つに分かれる。

**揮発してよい結果：継続を下に渡す**

結果が、それを作った activation の寿命の間だけ使えればよい場合は、結果を上に返さず、結果を使う処理（継続）を component として下に渡す。結果を作った activation は、結果の Ref を引数にして継続を起動する。結果のリソースの寿命は、継続の寿命に収まる。

例：issue を説明する画像は、issue から作られ、issue がなくなれば消えてよい。画像を作る component に issue と継続を渡し、継続が画像の Ref を受け取って使う。Haskell の `withFile :: FilePath -> (Handle -> IO r) -> IO r`（bracket）と同じ形である。

**長く残す結果：呼び出した側が置き場（プール）を用意する**

結果を、作った activation より長く残したい場合（チャットの中で作った画像など）は、呼び出した側が、結果を置く場所（プール）の Ref を引数で渡し、子はそこに書き込み、置いた項目の ID をデータとして返す。

1. どこかのサーバー S がプール（ドライブのようなもの）を提供する。長く残すもののプールは、木の根に近い、長生きの activation が持つ（root grant など）。
2. S は「プールの Ref と、書き込むデータ（または取得元）を受け取って保存し、保存が終わったら項目の ID を sink に `emit` する」component を提供する。
3. 結果を作るサーバー A（画像の生成など）は、プールの Ref を引数で受け取り、S の component を使って書き込み、項目の ID をデータとして返す。
4. 結果は、プールの Ref と ID の組で S から取り出す。永続化は S が受け持つ。

- 権限はプールの Ref にあり、ID は単なる名前（データ）である。ID を推測されても、プールの Ref を持たない者は取り出せない。WASI の preopened ディレクトリと相対パス、Capsicum の `openat` と同じ形である。
- これは region に基づくメモリ管理で、関数より長く生きる値を呼び出し側の region に確保するのと同じ規律である（Tofte–Talpin の region 推論、Rust で呼び出し側が渡した `&mut Vec` に書き込む形）。
- 例：Compiler は、コンパイルした IR をプールに置き、CID を ID として返す。Runtime は「CID を引数に取って起動する component」の Ref（上から渡されたもの）を使って、それを起動する。
- 代償として、サーバーをまたぐとデータのコピーが起き、権限の単位はプールごとになる（項目ごとに失効させたい場合は、プールを分ける）。
- 言語の層では、activation ごとに暗黙の置き場を持たせ、長く残すものだけ明示的にプールを使う形にすることで、利用者からこの手順を隠せる（Katari Language の仕様で定める）。

## 5. Katari Language の層への要求

Katari Language の処理系（Compiler・IR・インタプリタ）は別の仕様で定める。本仕様は、ライフサイクル層の上で動く Katari Runtime に対して、次を要求する。

- **暗黙の権限を持たせない**：言語には I/O の組み込み機能を持たせず、外界とのやり取りはすべて Ref を通して（sink への `emit`、blob の読み出し、component の起動で）行う。現在時刻や乱数の取得も Ref 越しに行う。これは durable execution の再生境界とも一致する。
- **Ref を偽造不能にする**：コードは文字列やリテラルから Ref を作れない。Ref は activation の引数（と、設定による root grant）としてのみ得られる。Runtime は activation ごとに保持している Ref の一覧を管理し、一覧にない Ref への操作を拒否する。Runtime の鍵で署名される以上、これを怠ると Runtime の権限がすべてのコードに漏れる。
- **Ref を不透明にする**：言語は Ref を文字列に変換する方法（表示、シリアライズ、文字列との連結など）を提供しない。Ref が値の中のどこにあるかは Runtime だけが知っており、送信時のシリアライズと R2 の derive は Runtime が行う。holder への紐づけ（§3.3）が言語の外の経路での漏洩を防ぐのに対し、こちらは言語の中での偽造と意図しない流出を防ぐ。
- **AI に Ref を見せない**：LLM に権限の選択をさせる場合は、Ref そのものではなく、Runtime が管理する番号や名前だけを LLM のコンテキストに入れ、Runtime が実際の Ref に対応づける。
- **計算資源に上限を設ける**：CPU 時間・メモリの上限を activation ごとに課す。超えた場合は `panic` を報告する。
- **情報流制御（IFC）のための足場**：sink などへの流出を言語の層で防げるように、Runtime は各 Ref について、その issuer の DID（データの送り先）と、その Ref をどの経路で受け取ったか（どの引数か、root grant か）を保持する。言語の IFC は、これを根拠に、送り先の信頼のラベルと、Ref 自体の完全性のラベルを決める。秘密のデータが信頼されていない issuer の sink に流れることを、型で禁じられるようにする（具体的な規則は Katari Language の仕様で定める）。
- **emit の順序**：同じ activation から同じ sink への `emit` は、プログラムに書いた順に届ける。そのため、Runtime は既定で `(aid, sink の URI)` を §2.4 のチャネルのキーとする。
- **失敗の扱い**：本層から `onFault` で知らされた activation の計算は、ただちに止める。結果を待つ呼び出し（`blob/fetch` など）が型に現れないエラーで失敗した場合も、その activation の `panic` とする。
- **自己発行の Ref を短絡する**：issuer が自分自身である Ref への操作と、自分自身が提供する component の起動は、署名とネットワークを省いてローカルに処理してよい。

## 6. 外部プロトコルとの接続（プロキシ）

Katari 以外のプロトコルとは、両方の側に参加するプロキシで接続する。外部のサービスとの境界は、できるだけ MCP に寄せる（ロードマップの前提）。プロキシは外部の資格情報（OAuth トークン、Bot トークンなど）を内部に保持し、Katari 側には権限を絞った grant だけを公開する。外部の資格情報そのものは Katari 側に出さない。

### 6.1 MCP

MCP も JSON-RPC 2.0 を用いるので、プロキシはエンベロープの付け外しとメソッドの対応付けを行えばよい。

| MCP | Katari |
|---|---|
| tool（`tools/call`） | component の `activation/init`。結果は引数の sink に `emit` する。tool の多くはその場で終わる component になる |
| resource（`resources/read`） | `blob/fetch` |
| `resources/subscribe` と `notifications/resources/updated` | 購読を component として起動し、引数の sink に `emit` する。購読の解除は dispose |
| task（長時間の処理） | activation |
| task のキャンセル | `activation/dispose` |
| task の状態 | activation の状態（§4.3） |

逆向きに、Katari の component を MCP の tool として公開するプロキシも同じ対応で作れる。

### 6.2 チャットサービス（Discord / Slack など）

- **投稿などの外向きの操作**は、チャンネル単位などに絞った sink（自分のリソース）として公開する。この部分は 1〜3 層で足りる。
- **受け取ったメッセージを届ける内向きの経路**は、「チャンネルを見張る」component として公開する。引数でチャンネルの指定と届け先の sink を受け取り、サービスから届く webhook（そのサービスの署名規約で検証したもの）を sink への `emit`（データ）に変換する。チャンネルの変更は revise、停止は dispose で行う。他人の sink を持ち続けるので、ライフサイクル層（1〜4 層）を用いる。
- 添付ファイルなどのデータは、イベントに含めるか、引数で受け取ったプールに書き込んで ID をイベントに含める（§4.7）。

### 6.3 一般の HTTP / webhook

- 外部への HTTP アクセスは、取得先を限定した `blob` や専用のリソースとして公開する。
- 外部に webhook を送る場合は、Standard Webhooks などの既存の署名規約に従う。

## 7. 保証される性質

### 7.1 権限の安全性（capability 層、局所的に成り立つ）

権限のない操作は通らない。使用時に issuer が grant 表を引いて確認するので、他のエンドポイントの状態や局所 DAG の整合性に依存しない。activation の制御も、受信者が自分の activation の表を引いて確認するので、同様に局所的に成り立つ。

### 7.2 プロトコル上の安全性（ライフサイクル層、通常の経路で成り立つ）

強制終了を用いない限り、解放済みのリソースへの操作は発生しない。これは、Ref が activation の引数でしか流れないこと（§3.4 の R1）、L2〜L4、完了通知の順序から導かれる。R1 により、root grant を除くすべての grant は、ある activation の引数として渡されたものであり、その activation のスコープの中でだけ使われる。L3・L4 は、スコープが閉じる前に使い終えることを保証する。

- **大域的な非循環性**：DAG の辺は常に「先に存在した activation から、その実行中に作られた activation へ」向く。辺は因果順序に沿うので、エンドポイントをまたいだ大域的なグラフも非循環である。
- **完了通知の停止性**：大域的なグラフが非循環であり、L5 が成り立つので、`revised` / `disposed` を待つ連鎖は有限で終わる（全エンドポイントがいずれ応答することが前提）。

意味論上は、各 revision の lifetime を region と見なし、L3 を region の付け替えとして形式化できる。

### 7.3 リークの範囲

derive した sub-grant の後始末は、derive したエンドポイントが行う。そのエンドポイントが永久に戻らない場合、sub-grant は残りうる。ただし、sub-grant は `derived_from` によって派生元の grant の寿命に縛られるので、問題はリークにとどまり、権限の安全性は損なわれない。

## 8. 参照実装に使えるライブラリ

| 用途 | 層 | TypeScript | Haskell |
|---|---|---|---|
| JWT の署名・検証 | 1 | `jose`（`jwtVerify` に、`kid` で鍵を引く関数を渡す） | `jose` |
| Ed25519 | 1 | WebCrypto（Node.js、主要ブラウザで標準対応） | `crypton` |
| did:key・CID（multiformats） | 1・3 | `multiformats` | multibase / multihash の各ライブラリ、または数十行の変換 |
| JSON-RPC 2.0 | 2 | 各種ライブラリ、または手書き（構造が単純） | 同左 |
| UUIDv7 | 2 | `uuid` | `uuid` |
| JSON Schema の検証（独自キーワードを含む） | 3 | `ajv`（`addKeyword` で `katariRef` を追加） | JSON Schema のライブラリ、または生成した検証関数 |
| DID の解決（did:web を加える段階） | 1 | `did-resolver`、`web-did-resolver` | — |
| SSRF 対策済みの HTTP クライアント（同上、外部の URL にアクセスするリソース） | 1・— | `request-filtering-agent` など、接続先の IP を確かめるもの | — |
| MCP プロキシ | — | MCP 公式 TypeScript SDK | — |

受信側の検証は、`jose` を用いて次のように書ける。

```ts
import { jwtVerify, decodeJwt, importJWK, type JWTVerifyGetKey } from "jose";

// 鍵は常に、iss を解決した文書の中から kid で探す（§1.4）。
const getKey: JWTVerifyGetKey = async (protectedHeader) => {
  // まだ検証していない iss。鍵を探す場所を決めるためだけに使う。
  const { iss } = decodeJwt(body);
  if (iss === undefined) throw new Error("missing iss");
  // 解決器は、文書の id が iss と一致することを確かめる。did:key では通信しない。
  const document = await resolver.resolve(iss);
  const method = document.verificationMethod.find((candidate) => candidate.id === protectedHeader.kid);
  if (method === undefined) throw new Error("unknown key");
  return importJWK(method.publicKeyJwk, "Ed25519");
};

const { payload } = await jwtVerify(body, getKey, {
  algorithms: ["Ed25519"],
  typ: "katari+jwt",
  audience: selfDid,
  maxTokenAge: "5m",
  clockTolerance: "30s",
});
```

実装前に、使用するライブラリのバージョンが JOSE のアルゴリズム識別子 `Ed25519`（RFC 9864）に対応していることを確認する。

## 9. 未決事項

| 層 | 事項 |
|---|---|
| 1 | 外部とつなぐ段階の DID の方式。選ぶ条件は「ID を変えずに鍵を更新できる」「鍵が漏れても回復できる」こと。候補は did:web（DNS と TLS を信頼し、文書を書き換える）と、did:webvh・KERI 系（次の鍵を先に約束する pre-rotation により、今の鍵が漏れても乗っ取られない）。アルゴリズムの移行（耐量子署名など）も同じ枠組みで扱う |
| 1 | did:web の解決器を加える時期と、DID 文書の `service` の形式（`type` の名前など） |
| 1 | 運用者の設定（`peers`）の形式と、CLI での鍵の作成・表の生成 |
| 1 | WebSocket など、一本の接続で多数のエンベロープを流す binding |
| 1 | `blob/fetch` で、JSON-RPC の中に base64 で入れる代わりに、binding の側でバイト列をそのまま返す形（HTTP の GET と Range、リクエストは署名する。AT Protocol の `getBlob` や OCI のレジストリと同じ形） |
| 1 | 送り先の方針（DID・ドメインのパターンの許可リスト）の書き方 |
| 3 | Katari の IR の型と JSON Schema の対応表（どの型をどのスキーマで表すか） |
| 3 | facet（権限を絞った別リソース）を作る操作を、組み込みの op として標準化するか |
| 3 | derive 時に権限を絞り込む制約（caveat）の形式。予算上限、プールの中の名前の絞り込みなど |
| 3 | 転送のたびの derive の往復を減らす方法。署名の連鎖による委任（UCAN・Biscuit・OCapN のハンドオフ方式）は将来の最適化として検討する。連鎖で省けるのは derive の往復だけで、寿命の規則による revoke は省けない |
| 4 | プール（§4.7）を標準の種別として定めるか（書き込み・取り出しの op、項目の ID の形式、CID との関係） |
| 3 | 公開サービス向けの、root grant 単位の利用制限 |
| 3 | ストリーミング。sink は単発のイベントのための種別なので、ストリームは別の種別（`stream` など。順序、背圧、再開を持つ）として後から追加する |
| 3 | promise pipelining（結果を待たずに、その結果に対する次の呼び出しを送る仕組み）。下の「空の引数」と同じ問題の別の表れである |
| 4 | **保留**：`activation/init` の応答で結果を直接返す最適化（init・結果の `emit`・dispose・`disposed` の往復を一つにまとめる）。意味を変えない最適化なので後から足せるが、オーケストレーターでは往復の数より抽象化を優先し、当面は入れない |
| 4・5 | **未決（慎重に決める）**：内部の呼び出し（同じ Runtime の中の component の呼び出し）もプロトコルの意味で行うか、言語の中の特別な経路とするか。前者なら内部と外部の component が同じ意味を持ち、置き換えられる（Runtime 同士で component を渡し合う用途に合う）が、言語が呼び出しに必要とするものをすべてプロトコルに入れることになる。後者ならプロトコルは小さいが、内部の component だけが使える機能が生まれる。この判断によって、次の二つをプロトコルに入れるかが決まる |
| 4・5 | **未決（慎重に決める）**：空の引数（`$pending`）。まだ値の決まっていない引数で init・revise し、子が決まっている部分だけで先に計算を進められるようにする（Oz の dataflow 変数、React Server Components の穴、GraphQL の `@defer` に相当）。規則の案：一つの完全な値だけを置き換える（キーや配列の長さは置き換えない）、置けるのは activation の引数と context だけ、スキーマの検査は埋まったときに行う、シグネチャで受け付けるかを宣言し、受け付けない component には呼び出す側が決まるまで送らない、外部への作用は依存する値がすべて決まってから行う |
| 4・5 | **未決（慎重に決める）**：暗黙の capability（`context`）。代数的エフェクトの handler のように、component の集合を呼び出しの連鎖の奥まで暗黙に引き継ぐ。案：init・revise に `context`（effect の名前（URI）→ component の Ref）を足し、component のシグネチャで要求する effect を宣言し（v0.1 の effect row に相当）、呼び出す側の Runtime が今の handler の文脈から埋める。寿命の規則は引数と同じく効く。effect の多相性（汎用の component が知らない effect を中継する）の扱いが残る |
| 4 | component のシグネチャ（型引数・引数の型）を、Katari 以外のサーバーから取得する方法（`component` 種別の問い合わせ用のメソッドなど） |
| 5 | 型に現れるエラー（v0.1 の `throw[T]` に相当）を、handler の capability を引数で渡す形で標準ライブラリとして提供する方法。v0.1 の effect handler を「capability として渡す handler」に写す全体の設計（`request`、`supervise`、region など） |
| 6 | MCP の仕様改訂への追従方針。特に Triggers and Events WG が定める server-initiated events（購読のライフサイクル、webhook、順序の保証）が確定したら、§6 の対応（購読 → component、イベント → sink への `emit`）を見直し、外部からのイベントの受け取りを MCP events に寄せる |
| 全体 | `katari:` の URI スキームの IANA への暫定登録（RFC 7595）。公開（ロードマップの Phase 12）までに行う |
| 全体 | エラーの `type` ごとの説明の文書を katari-lang.dev に置く（ドキュメントの整備とあわせて） |
