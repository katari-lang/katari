# v0.1.6 API 再設計 — prelude / packages の全面棚卸しと縮小 (2026-08-01)

prelude 19 モジュール + katari-packages 14 パッケージの全 API を、全使用側コーパス
(playground / examples 4 本 / tsukasa / e2e / katari-web docs) との突き合わせで再設計したもの。
ユーザー 0 人の今が最後の機会という前提で、後方互換は考慮しない。

## 設計原理 (razor)

**やりたいこと 1 つに、やり方 1 つ。** API 数の増加は DSL の価値を指数的に毀損する。
各シンボルは次のどれかでなければ削除する:

1. **primitive** — 合成では書けない最小能力 (`string.to_base64`, `time.zone_offset`, `json.validate`)。
2. **mechanism** — 一般機構 + 具体はデータ (`poll.subscribe`, `supervise.forever`, `mcp.provide_all`)。
3. **canonical spelling** — 合成で書けるが、合成形が「長い」のではなく「間違えやすい」もの。
   意味・判断を符号化している場合に限る (`string.fit` の cap−marker 算術、`crypto.pseudonym` の
   keyed-HMAC 判断)。単なる省略形 (合成形も同じく正しい) は使用数に関わらず削除。

「参照されている」は温存理由にしない。参照ゼロは削除の十分条件として使う。

## 検証済みの前提 (2026-08-01 probe)

設計判断はすべて実測に基づく。probe の結論:

| # | 検証内容 | 結果 |
|---|---|---|
| P-A | generic パラメータの `?= null` デフォルト | **不可** (rigid generic は宣言サイトで下界 never)。ただし nullary agent は幅サブタイピングで任意の agent 型に入る — `fork(task = agent () -> null {...}, argument = null)` は現行のまま通る |
| P-B | effect 多相 throw catch | **可**: `[T, Err, effect E lacks prelude.throw](task: agent (value: null) -> T with E \| prelude.throw[Err]) -> T \| Err with E` が完全推論込みで通る。部分捕捉 (throw の union を rigid に分離) は不可 — 全捕捉のみ |
| P-C | fallback 型駆動 reader `get_or[T]` | **可** (string / integer / data コンストラクタ 3 通りで推論成立) |
| P-D | デフォルト引数の範囲 | スカラー / `[]` / `{}` / object / tuple / null は可。**コンストラクタ適用・nominal data・文字列リテラル union 型は不可** |
| R-1 | cross-nursery `region.fork` | **成立**: routing はハンドルの `$katari_region_scope` のみ。呼び出し側の動的エクステント非依存。escalation はハンドル所有側の watch に届く |
| R-2 | dead nursery への fork | **panic** (typed error でない)。`supervise.once` + `signal_panics` で値に折れる。配達は at-most-once |
| R-3 | fiber の handler 継承 | **継承しない**。ただし root nursery の watch を包む位置に provider / breaker を置けば全 fiber を 1 個でカバー (parallel handler 必須 — var だと全 AI が直列化) |
| R-4 | marker 共有 | runtime 上の混線ゼロ (scope identity は provide ごとのランダム文字列)。merge は型レベルの現象のみ。規律: 1 nursery = 1 watch |
| R-5 | **cross-nursery のインライン closure fork は unsound** | 環境所有権が target の provide instance へ移転し、target 死亡時に生きている送り手の環境が回収され得る。**mail は named agent + 素データ引数で送ること** (captured owner が空なら移転は起きない) |
| P-E | fork のフラット contract (`task: agent A -> null, argument: A`、A = パラメータ record 全体) | **可**: A が task と argument リテラルの両方から完全推論。nullary は `argument = {}`、余分フィールドの幅も通る。なお言語には record 丸ごと適用 (spread) の構文がない — fork は external なので適用は runtime 側で行い、userland には現れない |

## 1. 新設 API (prelude)

### 1.1 `prelude.catch` — throw を値に折る唯一の一般形

```katari
agent catch[T, Err, effect E lacks prelude.throw](
  task: agent (value: null) -> T with E | prelude.throw[Err],
) -> T | Err with E
```

P-B の形そのまま。これ 1 つで以下が全て不要になる:
- `json.try_validate` (= catch ∘ validate)
- `credentials.check` / `preflight` (アプリの boot で catch ∘ resolve を並べる)
- store の `_as` 三兄弟 (= validate ∘ request、下記 4.9)
- アプリ頻出の guarded_* イディオム (union-catch-して-残余-再throw の定型 — docs に 3 回登場する
  workaround がそのまま消える)
- ai パッケージ内部の同文 attempt ハンドラ 6 個 (→ 1 本)

戻り値は素の union `T | Err`。T と Err が重なる instantiation では潰れるが、data 型どうしは
構造的に重ならないのが通常形。名前は time.ktr:97 の stale doc コメントが既に `prelude.catch` を
予告していたのでそれを実名化する。

### 1.2 `string.fit` — cut-and-say-so の唯一の実装

```katari
agent fit(value: string, cap: integer, marker: string) -> string
```

結果は常に ≤ cap code points。切ったら marker を含める。marker 単独が cap を超えるなら
marker を cap に切る。slack/discord の `fit_message` (byte 同等 ×2)、`web.truncate`、
`memory.bounded_summary` の同一算術 4 実装を置換。

### 1.3 `crypto.pseudonym` — keyed 仮名の canonical spelling

```katari
agent pseudonym(key: string of private, value: string, length: integer ?= 8) -> string
```

実装は hmac_sha256 + slice の 2 行だが、合成形は sha256 (辞書逆引き可能) を誘発する。
セキュリティ判断の符号化なので canonical spelling として置く。slack/discord の
`author_tag` (byte 同等 ×2) を置換。

### 1.4 `store.get_or[T]` — 型付き store 読みの唯一の形

```katari
agent get_or[T](key: string, fallback: T) -> T with get
```

P-C の形。実装は catch ∘ validate ∘ get。`get_text` (参照ゼロ) / `get_integer` を置換。
注意 1 点 (P-C): T 自身が null を含む instantiation では「検証失敗」と「保存された null」が
区別できない — docstring に明記する。

### 1.5 `http.fetch` のデフォルト化と `post_json` の再設計

```katari
external agent fetch(
  url: string,
  method: string ?= "GET",
  headers: record[string of private] ?= {},
  body: body | null ?= null,          // nominal data はデフォルト不能 (P-D) なので null で欠落を表す
) -> { status, headers, body } ...

agent post_json(
  url: string,
  body: unknown of private,
  headers: record[string of private] ?= {},
  context: string,
) -> unknown with io | throw[api_failure | fetch_error | parse_error]
```

- 素の GET は `http.fetch(url = ...)` 1 引数になり、`http.get` (参照ゼロ) は削除。
- `post_json` は **`status_error` を廃止**して `classify_status` を内蔵し、非 2xx を直接
  `api_failure = auth_error | api_error` で投げる。これで「同じ非 2xx が 2 つの型で飛ぶ」
  二重語彙が消え、tavily / imagegen の同形再分類 shim 2 箇所と google_common の手書き判定が
  1 行になる。`context` は api_failure の文脈フィールドに載せる。

### 1.6 `json.text` の fallback 化

```katari
agent text(target: unknown, fallback: string ?= "") -> string
```

これで `text_at` (= field ∘ text + fallback) が純粋な合成
`json.text(target = json.field(target = x, key = k), fallback = f)` になり削除できる。

### 1.7 `supervise.forever` / `exponential` のデフォルト化

アプリ 7 箇所中 6 箇所が逐語同一の `(1000.0, 2.0, 900000.0)` を書いている。
`initial_delay_milliseconds ?= 1000.0` / `factor ?= 2.0` / `max_delay_milliseconds ?= 900000.0`
をデフォルト化し、通常形を `use supervise.forever()` にする。`exponential` は
initial_delay / factor のみデフォルト化 — `max_attempts` は「何回で諦めるか」という判断なので
デフォルトを置かない (residual defaults を置かない原則)。

### 1.8 `region.fork` のフラット化 — 適用規約を言語の呼び出しと一致させる

```katari
external agent fork[effect Scope, effect E, A](
  nursery: nursery[Scope, E],
  task: agent A -> null with E | prelude.throw[unknown],
  argument: A,                        // A = task のパラメータ record 全体
  name: string ?= "",
) -> fiber[Scope] with Scope | io from "region"
```

現行の fork は `task: agent (input: A) -> null` に `{input: argument}` を適用する —
`input` というパラメータ名が API に固定され (E8 系の構造的名前強制)、payload が 1 段ネストする。
Katari の適用は常に named-argument record であり (`reflection.call_agent` の args も record 形)、
fork は「遅延された呼び出し」なのだから、その引数も**呼び出しの引数 record そのもの**であるべき。
フラット化で task は自分のパラメータ名を保ち、呼び出しは
`region.fork(nursery = box, task = deliver, argument = { source = "mail:core", hop = 1 })` になる。
nullary は `argument = {}` (P-A により rigid generic のデフォルトは置けないので儀式は残る —
現行の `argument = null` と等価コスト)。

**ゲート解決 (2026-08-01 runtime 実装で確証)**: デフォルト充填は callee 側の唯一機構として
runtime に既存 (ir.ts:123-135「the single defaults mechanism for every callable」、
thread-ops.ts の `applyDefaults` が instance root で充填)。fork の fiber も同経路を通るため
**fork される task の `?=` はそのまま効く** — 全 required 規約は不要。regression test 追加済み。
なお fork のフラット化は **IR の hard break**: 旧 snapshot (fork/post を呼ぶもの) は v0.1.6
runtime で動かない。pinned な tsukasa 等は runtime を上げる前に移行が必要 (後方互換なしの方針
どおりだが、運用順序として記録)。

**アップグレード順序の注意 (in-flight な旧 run)**。壊れるのは「次に呼ばれた 1 call」ではない。
削除された `region.cancel` の in-flight extension row は永続化されており、`kind: "cancel"` は
v0.1.6 の `decodeRegionExtension` の `default` 節に落ちて throw する — これは load pass の中
なので、落ちるのは project actor の reactivation **全体**であり、同じ project の無関係な run も
道連れになる (fork の `name` や provide の `names` が lenient に読まれているのは、まさにこの
「1 行で load pass ごと落とす」を避けるため — 削除された kind にはその逃げ道がない)。
dev フェーズの対応は 2 つだけ: アップグレード前に旧 run を drain する (in-flight な cancel を
持つ run を終わらせる) か、runtime 状態をリセットする。migration は書かない (ユーザー 0 人・
後方互換なしの方針どおり)。

### 1.9 `store.workspace` の一級化 — 空間と直列化を 1 語に融合 (owner 提案 2026-08-01)

scope (prefix) と serialize (FIFO) が分離して意味を持つ形は実在しない — 読み経路が scope だけを
開く現行例 (memory.index 等) も、workspace 越しの直列化された読みで意味論的に困らない。
逆に「直列化だけ欲しい」は名前空間なしの lane であり、これも workspace のネストで書ける
(内側 workspace = サブ prefix + サブ lane)。よって:

- 公開面: `workspace[R, E](path, continuation)` を**唯一の空間・直列化 provider** にし、
  `scope` / `serialize` は削除 (実装は workspace の body に 1 本でインライン化)。
- 残る store surface: `get/set/delete/list` + `found/absent/leaf/branch` + `get_or[T]` (1.4) +
  `exclusive` (複数 op を 1 turn に束ねる唯一の形) + `share/shared` (共有 place、v2 設計のまま) +
  `safe_segment`。
- 閉じ込め: ネストした workspace は自分の prefix の外に届かない (現行 scope の意味論を継承)。
- v0.1.6 の実装は現行の合成 (parallel prefix handler + sequential lane) を workspace 内部に
  畳むだけで runtime 変更なし。**workspace を runtime primitive にする** (per-op の
  handler 2 段 + durable frame を lane 化で削る) は §5 の follow-up として記録 — API を
  1 語に融合した後なら ABI を差し替えるだけで表面が動かない。

`credentials.source` と `mcp.auth` の統合は**しない**: 前者は「1 つの秘密の所在」、後者は
「接続の認証方法」(record 形の headers を含む) で intent が異なる。`oauth(name)` constructor の
同名は同義なので許容。`oauth.server_error` / `mcp.server_error` も統合しない — nominal な
エラー型はどのサブシステムが落ちたかという情報そのもの。

## 3. packages の設計

### 3.1 ai 0.5.0 — 1 つの serving 機構と、region 合成としてのマルチ AI

**中心決定: serving 機構は `serve_observations` の 1 本のみ。** 使用実態が根拠:
serve_session / serve_observations はアプリ使用ゼロで、全アプリ (concierge / tsukasa) は
routing を自作するために advance_desk を直接呼んでいた。マルチ AI が region 合成
(fiber-per-AI) で書けるようになれば routing の自作が不要になり、全員が serve_observations に
戻れる — desk の公開面ごと畳む。

**削除** (全て参照調査で確認済み):
- `serve_session` + `session_message` + `session_state` (参照ゼロ)。チャット bot の唯一の形は
  resident + deliver_to (実アプリが既にそうしている)。
- `desk_table` / `new_desk_table` / `keyed_desk` / `advance_in_table` / `serve_in_table` /
  `forget_desk` / `advanced` / `stale` / `table_outcome` / `table_turn` — 名前→会話 routing の
  第 2 機構。fiber identity (cancel_by_id + router 表からの削除) が generation 機構を置換する。
- `advance_desk` / `new_desk` / `desk` / `desk_turn` / `desk_outcome` (`answered`/`filed`/
  `step_failed`) / `desk_policy` / `default_desk_policy` / `reply_policy` の公開 API 性 —
  backlog / shed / compaction 接続のロジックは serve_observations の内部実装として存続。
- `infer_with_tools` (参照ゼロ、docs 5 ページで紹介されていたが実使用なし)
- `watch_prompt` (参照ゼロ、time.watch + observation の 3 行合成)
- `empty_reply_nudge` + `nudge_empty_reply` ノブ (文言ハードコードの heuristic)
- 内部: 6 個の同文 attempt ハンドラ → prelude.catch ベースの 1 本へ

**mail の一級化** (R-5 の unsoundness を構文で封じる)。1.8 のフラット fork を前提に、
`arrival` datum は廃止し、observation のパラメータ record そのものを mail の payload にする:

```katari
// observation = event→model チャネル (従来の arrival のフィールドを直接持つ)
request observation(
  source: string,
  content: string,
  hop: integer,                      // デフォルトなし (判断の隠蔽になるため) — 従来どおり
  files: array[file] ?= [],          // 1.8 ゲート解決済み: fork 経由でも runtime が充填する
  author: string | null ?= null,
) -> null

// mail = cross-nursery 配達のための named task。observation と同一のパラメータ record。
// named agent + 素データ record なので R-5 の環境移転が構造的に起きない。
agent mail(source: string, content: string, hop: integer,
           files: array[file] ?= [], author: string | null ?= null)
  -> null with observation {
  observation(source = source, content = content, hop = hop, files = files, author = author)
}
```

router は `region.fork(nursery = box, task = ai.mail, argument = { source = ..., content = ...,
hop = 1 }, name = ...)` と書く (files / author は省略可 — runtime の唯一デフォルト機構が充填)。
インライン closure を書く余地がなく、unsound 形が API 上存在しない。
dead-inbox 競合 (R-2 panic) は router 側で `supervise.once` + `signal_panics` に折るか、
root watch の `crashed`/`failed` で先に学ぶ — パターンの README に記載する。

**one-shot 面の命名統一** (owner 方針 + gate probe 2026-08-01): 統合案 A

**マルチ AI の一級化: `ai.resident`** (owner 裁定 2026-08-01: 「AI の追加が 1 行」を API にする)。
パターンの規律 (mailbox は自分の nursery と別 / self-watch 禁止 / 1 nursery = 1 watch /
mail は素データ) は合成で書くと**間違えやすい** — razor の canonical spelling 該当。
approval package を撤去した先例 (「mechanism が fork の facility は inline が安い」) との違いは、
resident が純 region 15 行ではなく serve_observations + mailbox 規律 + 登録チャネルの束であること。

```katari
effect mail_scope                                            // ai が所有する共有 marker (mcp.scope の先例)
type mailbox = region.nursery[mail_scope, observation]       // 全 mailbox の ceiling は observation で固定
request register(name: string, box: mailbox) -> null         // fiber → router の登録チャネル

// AI 1 体の全身。root nursery に fork される named task (パラメータは全て素データ + agent 値)。
agent resident(
  name: string,
  tools: array[agent never -> unknown with all],
  deliver_to: ...,          // 応答の行き先 (serve_observations へ透過)
  persona: string ?= "",    // 毎 turn 注入 note (with_context 経由)
  // max_steps / policy 等は serve_observations のパラメータをそのまま透過
) -> never with ... {
  // use region.provide[mail_scope, observation] → register(name, box)
  // → use with_context(persona) → use serve_observations(tools, deliver_to, ...)
  // → region.watch(nursery = box)
}
```

アプリに残るのは routing (= アプリ固有の判断) のみ:
- **AI の追加 = 1 行**: `region.fork(nursery = root, task = ai.resident, argument = { name = "core",
  tools = core_tools, ... }, name = "core")`。実行時追加も同じ 1 行 (tools / deliver_to の closure を
  argument に載せるのは root nursery への fork なので安全 — R-5 が禁じるのは provide が先に死ぬ
  cross-nursery 方向のみ)。
- **router**: `register` を受けて `record[mailbox]` を保持し、宛先に
  `region.fork(nursery = box, task = ai.mail, argument = {...})` する handler ~10 行。
  router 側の `mail_scope` discharge は `region.provide[ai.mail_scope, ai.observation]` 1 行
  (marker merge の意図的利用、R-4)。
- **provider / breaker**: root watch を包む parallel handler に 1 個 (R-3)。

**追補 2 (owner との共同設計 2026-08-01、最終形): 製品層 = `route` / `spawn` / `mail` / `dismiss`。**
当初の「routing はアプリ固有」を撤回し、さらに resident / register も内部化する。確定 surface:

```katari
let root = use ai.route()      // 透過 scoped provider (provider 家族の契約を守る — never は作らない)
ai.spawn(
  name, tools,
  persona: (agent () -> string with E) | null ?= null,     // 毎 step 再評価の注入 note。動的にしたければ
                                                            // この agent が effect を perform する (店は row 経由で
                                                            // アプリ handler / root-served store に届く)。静的なら
                                                            // 決定的に返すだけ。null = 注入なし
  deliver_to: (agent (reply) -> null with E) | null ?= null, // null = undelivered 注記
  sources ?= [], workspace ?= null, ...,
) -> spawned | already_running
ai.mail(to, source, content, hop, files ?= [], author ?= null) -> posted | no_recipient
ai.dismiss(name) -> dismissed | unknown
region.watch(nursery = root)   // never は従来どおりアプリの明示 tail (operator note の handler は route の上)
```

「AI が effect を起こす」は **closure の row を通じて**達成する (owner 裁定): 一度検討した
効果反転 (ai が `system_prompt` / `reply` request を宣言しアプリに serve を強制) は、必須 serve の
課税と「route 内デフォルトがアプリ override を shadow する」構造問題のため撤回。persona は
system prompt では**ない** (with_context の tail 注入 note — churn しても prefix cache は無事。
本物の system は provider の `system`) — この名実を docstring に明記する。probe の本丸は
effect-generic request の nullable-union closure param で E が推論されるか (P-A probe 2 の制約)。
落ちれば明示 `ai.spawn[E](...)` を正式綴りとする。

- route は自分の nursery (自 marker + ceiling を所有 — アプリから ceiling の綴りが消える) を開き、
  spawn / mail / dismiss / 内部 register handshake / `region.crashed`・`failed` の表 evict → proxy up
  を 1 handler で serve する。franking (marker discharge) も内蔵。
- spawn が resident と **sources** (`array[agent (self: string) -> null with E]`、self 宛 mail を
  投げる per-AI watcher 宣言) を route の nursery へ fork する。動的 spawn は request なので
  resident の tool からも 1 行 (fiber 内からの spawn は closure を素データ + named agent に限る —
  R-5 同族ハザード、docstring 規律 + §5 checker 宿題)。
- **observation と mail の関係**: observation は「位置が宛名」(serve する handler が AI の fiber 内に
  居るため宛名データ不要 = 共有不能)、mail は「データが宛名」(共有 root の route が to で選ぶ)。
  mail は宛先 mailbox に fiber を落とし正しい位置で observation を perform する配達人。
- **機構層は公開のまま**: `resident` / `register` / `serve_observations` / `observation` / `mailbox` /
  `mail_scope`。tsukasa 級 (per-fiber workspace / 動的 persona で resident を包む) はここに降り、
  自作 resident が `register` を perform すれば route の表に合流する — region と route の層関係と同じ。
- 未登録宛先の pending queue は入れない (呼び手が `no_recipient` で組む)。broadcast / 優先度 /
  型付き宛先 sum は機構層への退避で書く。

dismiss = `region.cancel_by_id`、死亡通知 = root watch の `crashed`/`failed` (fork の name で対応付け)。
**probe ゲート**: resident の effect 行 (mail_scope の discharge 位置、deliver_to の効果尾、
register が root watch まで届く綴り) は実装冒頭に型 probe で確定させる — owner の先行実験
(2026-07-31 会話) で類似形が 41 modules 通過済みなので成立見込みは高い。パターンの規律自体は
README に残す (resident を使わず手で組む読者向け)。

   **注 (2026-08-01)**: `ai.spawn[E]` の明示 instantiation はこのタスクの動機に**ならない** —
   E は route の nursery ceiling との完全一致 (invariant) が要求され、perform サイトの引数からは

   `spawn[E_route]`) に居るので、消したければ「row 主導の instantiation」という別機構になるが、
